DCL (Data Control Language) in Oracle SQL

DCL (Data Control Language) is a category of SQL commands used to control access to data and database objects. It focuses on managing permissions and user access.


DCL helps you:

  • Control who can access the database.
  • Control what users can do with specific data or objects.
  • Enforce security, data integrity, and privilege delegation.

Main DCL Commands in Oracle

DCL Command Purpose
GRANT To give privileges to users/roles
REVOKE To remove previously granted privileges

Types of Privileges Controlled by DCL

A. System Privileges.

Privileges that allow users to perform database-level actions:

  • CREATE SESSION (login)
  • CREATE TABLE, DROP TABLE
  • CREATE USER, GRANT ANY PRIVILEGE

B. Object Privileges

Privileges on specific objects (tables, views, sequences, procedures):

  • SELECT, INSERT, UPDATE, DELETE
  • EXECUTE (procedures/functions)
  • REFERENCES (foreign keys)

Roles in DCL

  • Roles are named groups of privileges.
  • You can grant privileges to roles and then assign roles to users.

CREATE ROLE hr_role ;
GRANT SELECT , INSERT ON employees TO hr_role ;
GRANT hr_role TO hr_user ;

Data Dictionary Views for DCL Monitoring

View Description
USER_SYS_PRIVS System privileges granted to current user
USER_TAB_PRIVS Object-level privileges granted to user
USER_ROLE_PRIVS Roles assigned to current user
DBA_SYS_PRIVS System privileges granted to all users/roles
DBA_TAB_PRIVS Object privileges on all tables
DBA_ROLE_PRIVS Role assignments to users and roles

Public Privileges

The keyword PUBLIC allows you to grant access to all users in the database.

GRANT SELECT ON employees TO PUBLIC ;

-- Avoid granting to PUBLIC unless absolutely necessary.

WITH ADMIN OPTION & WITH GRANT OPTION

Option Applies To Purpose
WITH ADMIN OPTION System privileges & roles Allows grantee to pass the privilege to others
WITH GRANT OPTION Object privileges Allows grantee to pass object access to others

Security Notes & Best Practices

  • Use roles to organize permissions
  • Audit privilege usage regularly
  • Avoid using WITH GRANT OPTION unless necessary
  • Avoid granting powerful privileges (DBA, ALL) casually
  • Revoke unneeded privileges periodically

Summary of DCL in Oracle SQL

Command Use Case Example
GRANT Assign access GRANT SELECT ON emp TO user1;
REVOKE Remove access REVOKE SELECT ON emp FROM user1;
WITH GRANT OPTION Allow re-granting object privileges GRANT SELECT ON emp TO user1 WITH GRANT OPTION;
WITH ADMIN OPTION Allow re-granting system privileges GRANT CREATE TABLE TO user1 WITH ADMIN OPTION;



GRANT in Oracle SQL

The GRANT command is used to give permissions (also called privileges) to users or roles so they can perform specific actions on the database. (or)


The GRANT statement is used to give privileges (permissions) to a user, role, or public for accessing and manipulating database objects or system features.


In simple terms:

    GRANT gives access to other users to use objects (like tables, views) or perform actions (like SELECT, INSERT, EXECUTE).

Why to Use GRANT

  • Control who can access and what actions they can perform on:
    • Tables, Views, Sequences, Procedures, System operations (e.g., CREATE TABLE).
  • Delegate limited access to other users without compromising data integrity or security.
  • To enforce data security by giving only necessary access.
  • To allow controlled collaboration between users or applications.

Types of Privileges in GRANT

System Privileges - Access to perform tasks at the database level

Example Privilege Purpose
CREATE SESSION Allows user to log into the database
CREATE TABLE Allows user to create tables
CREATE VIEW Allows user to create views
CREATE USER Allows user to create other users
DROP USER Allows user to drop (delete) users

Object Privileges - Access to perform tasks on a specific object (like a table)

Privilege Object Type Purpose
SELECT Tables, Views Allows reading data
INSERT Tables Allows inserting data
UPDATE Tables Allows modifying data
DELETE Tables Allows deleting data
EXECUTE Procedures, Packages Allows running PL/SQL code

Syntax of GRANT

Basic GRANT Syntax

GRANT privilege [, privilege2, ...]
TO user_or_role [, user2, ...]
[ WITH ADMIN OPTION ] ;

Granting Object Privileges

GRANT privilege ON object
TO user_or_role [, user2, ...]
[ WITH GRANT OPTION ] ;

Examples of GRANT in Oracle SQL

Grant SELECT on table to another user:- Gives user uday permission to run SELECT queries on employees table.

GRANT SELECT ON employees TO uday ;

Grant multiple privileges on a table ( object level).

GRANT SELECT , INSERT , UPDATE ON employees TO hr_user ;

Grant Multiple Privileges to a User

GRANT CREATE TABLE , CREATE VIEW , CREATE PROCEDURE TO hr_user ;

Grant EXECUTE on a stored procedure.

GRANT EXECUTE ON update_salary_proc TO hr_user ;

Grant a system privilege

GRANT CREATE TABLE TO developer1 ;

-- Allows developer1 to create tables in their schema.

Grant privilege to multiple users.

GRANT SELECT ON products TO user1, user2, user3 ;


Grant with WITH GRANT OPTION:- analyst_user can now grant SELECT on employees to others.

GRANT SELECT ON employees TO analyst_user WITH GRANT OPTION ;

WITH ADMIN OPTION vs WITH GRANT OPTION

Option Applies to Allows the grantee to...
WITH ADMIN OPTION System Privileges Grant system privileges to others
WITH GRANT OPTION Object Privileges Grant object privileges to others

View Granted Privileges

You can check privileges using data dictionary views:

-- System privileges granted to user
SELECT * FROM DBA_SYS_PRIVS WHERE GRANTEE = 'HR_USER' ;

-- Object privileges granted
SELECT * FROM DBA_TAB_PRIVS WHERE GRANTEE = 'HR_USER' ;

-- Roles granted to a user
SELECT * FROM DBA_ROLE_PRIVS WHERE GRANTEE = 'HR_USER' ;

Common Errors with GRANT

Error Description
ORA-00942: table or view does not exist You're trying to grant a privilege on an object that doesn't exist or isn't accessible
ORA-01031: insufficient privileges You don’t have the right to grant that privilege
Using incorrect privilege or object name For example, using GRANT UPDATE on a procedure

Do's and Don'ts of GRANT

Do's Don'ts
Grant only required privileges (principle of least privilege) Don’t grant ALL privileges unless absolutely needed
Use roles for managing groups of users Don’t grant privileges individually for each user if roles can be used
Use WITH GRANT OPTION only for trusted users Don’t allow excessive re-sharing of privileges
Revoke access when it’s no longer needed Don’t forget to review privilege usage periodically

Best Practices

  • Use roles for grouping privileges.
  • Use WITH GRANT OPTION/ADMIN OPTION cautiously.
  • Avoid granting to PUBLIC unless necessary.
  • Always audit privileges regularly.



REVOKE in Oracle SQL

The REVOKE statement in Oracle SQL is used to remove or take back privileges (system or object-level) that were previously granted using the GRANT statement.


It's a key component of Data Control Language (DCL) and is vital for maintaining database security by revoking unnecessary or risky privileges.


In simple words: If you gave someone access using GRANT, and now you no longer want them to have that access, you use REVOKE.


Why to Use REVOKE

  • To tighten access control.
  • Remove temporary privileges.
  • Remove accidental or inherited grants.
  • Adjust role-based security.

Syntax of REVOKE

REVOKE privilege [, privilege2, ...]
ON object_name
FROM user_or_role ;

Types of Privileges That Can Be Revoked

You can revoke:

  • 1. System Privileges (like CREATE TABLE, CREATE VIEW).
  • 2. Object Privileges (like SELECT, INSERT, UPDATE on tables or views).
  • 3. EXECUTE Privileges (on procedures or packages).
  • 4. GRANT OPTION rights (ability to further grant privileges to others).

Examples of REVOKE

Revoke System Privilege.

REVOKE CREATE TABLE FROM analyst_user ;

-- Removes the ability to create tables.

Revoke Object Privileges.

REVOKE SELECT , INSERT ON employees FROM hr_user ;

-- Takes away access to read or insert into employees

Revoke EXECUTE on a Procedure.

REVOKE EXECUTE ON calculate_bonus FROM hr_user ;

Revoke a Role.

REVOKE hr_role hr_user ;

Revoke From Multiple Users.

REVOKE SELECT ON employees FROM user1, user2 ;

Revoke GRANT OPTION

If a user was granted a privilege with GRANT OPTION, revoking it will also remove their ability to pass it on to others.

REVOKE SELECT ON employees FROM manager_user ;

Special Clauses

Oracle does not support CASCADE or RESTRICT with REVOKE like some other databases (e.g., PostgreSQL).


But:

  • If user A granted a privilege to user B using WITH GRANT OPTION, and you revoke the privilege from user A, it also revokes access from user B (called cascading revocation).

What Happens If the User Still Has Privileges

If a user has:

  • The same privilege from another grantor.
  • The privilege via a role.

Then revoking from one path won’t completely remove it. You must revoke all sources.


How to Track Granted Privileges

Use dictionary views to check what to revoke:

-- Object privileges granted.
SELECT * FROM DBA_TAB_PRIVS WHERE GRANTEE = 'HR_USER' ;

-- System privileges granted.
SELECT * FROM DBA_SYS_PRIVS WHERE GRANTEE = 'HR_USER' ;

-- Roles granted.
SELECT * FROM DBA_ROLE_PRIVS WHERE GRANTEE = 'HR_USER' ;

Important Notes

Behavior Description
Cascading Revoke If GRANT OPTION was used, revoking a privilege from one user also revokes it from users they granted it to.
No Error if Not Present If the privilege wasn't granted, Oracle won’t raise an error — the REVOKE just won’t do anything.
System Privileges Must be revoked at the user level, not object level.

Common Errors

Error Code / Issue Reason
ORA-01031: insufficient privileges You’re trying to revoke a privilege that you don’t have authority over.
Revoke fails silently The privilege wasn’t granted in the first place.

Do's and Don'ts of REVOKE

Do's Don'ts
Revoke unused or unnecessary privileges immediately. Don’t assume granting access once means it will always be needed.
Document changes when revoking critical access. Don’t forget to check cascading revoke if WITH GRANT OPTION was used.
Use roles to simplify grant/revoke management. Don’t manage individual user privileges manually for many users.
Review user access regularly (audits, security compliance). Don’t rely only on REVOKE — use user roles and least privilege.

Best Practices

  • Revoke unused or temporary privileges.
  • Always audit users with WITH GRANT OPTION.
  • Avoid granting powerful privileges unless essential.
  • Use roles to simplify revocation and maintenance.
  • Revoke from PUBLIC if you overexposed sensitive objects.
