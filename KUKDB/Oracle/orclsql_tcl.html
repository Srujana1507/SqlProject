TCL (Transaction Control Language) in Oracle SQL

TCL commands are used to manage changes made by DML statements (INSERT, UPDATE, DELETE) in a transaction.


  • They help you commit (save) or rollback (undo) those changes in the database.
  • A transaction is a group of operations that are treated as a single unit of work.
  • It is a set of SQL commands used to manage transactions in a database. A transaction is a group of SQL operations that are executed as a single unit of work.
  • If all the operations in a transaction succeed, the transaction is saved permanently. If something goes wrong, you can undo all changes made during that transaction.

Purpose / Importance of TCL in Oracle SQL

Purpose / Importance Description
Data Integrity Ensures that only valid and consistent data is saved to the database by grouping related operations into a single transaction.
Error Recovery Allows you to undo changes made during a transaction if an error occurs, using ROLLBACK.
Atomicity Guarantees that all operations within a transaction are completed successfully, or none are applied at all.
Consistency Keeps the database in a consistent state before and after a transaction.
Control Over Changes Gives you the ability to COMMIT (save) or ROLLBACK (undo) changes, providing flexibility and control over data modifications.
Savepoints Enables partial rollbacks to specific points within a transaction using SAVEPOINT, making error handling more granular.
Concurrency Control Helps manage concurrent access to the database, ensuring that multiple transactions can occur without conflicts.
Performance Optimization Allows you to group multiple DML operations into a single transaction, reducing the overhead of committing each operation individually.
Safe Testingts Allows testing of data changes before making them permanent.

TCL Commands in Oracle SQL

TCL Command Purpose Description
COMMIT Save changes Saves all changes made in the current transaction permanently to the database.
ROLLBACK Undo changes Undoes all changes made in the current transaction since the last COMMIT or ROLLBACK.
SAVEPOINT Set a savepoint Sets a point within a transaction to which you can later roll back, without affecting prior work.
SET TRANSACTION Set transaction properties Specifies characteristics for the current transaction, such as read consistency or isolation level.

Default Behavior in Oracle

  • DML operations (INSERT, UPDATE, DELETE) are not permanent until you run COMMIT.
  • You can undo them using ROLLBACK before commit.

Common Errors When Using TCL in Oracle

Error / Issue Description
ORA-01086: savepoint never established You tried to ROLLBACK TO a savepoint that does not exist in the current transaction.
ORA-01093: COMMIT or ROLLBACK not allowed in a trigger COMMIT or ROLLBACK statements are not permitted inside triggers.
ORA-01453: SET TRANSACTION must be first statement of transaction You issued SET TRANSACTION after DML or other statements; it must be the first statement in a transaction.
Changes lost due to missing COMMIT If you forget to COMMIT, changes may be lost if the session ends or you issue a ROLLBACK.
Unintended data changes due to auto-commit Some tools (like SQL Developer) may auto-commit by default, making ROLLBACK ineffective.
ROLLBACK undoes all changes since last COMMIT ROLLBACK will undo all uncommitted changes, not just the last statement, unless you use SAVEPOINT.
Using TCL with DDL statements DDL statements (CREATE, ALTER, DROP) auto-commit in Oracle, so TCL commands do not affect them.

Do’s and Don’ts of TCL


Do's Don'ts
Always use COMMIT after successful DML operations. Don't forget to ROLLBACK if an error occurs before COMMIT.
Use SAVEPOINT to create restore points within a transaction. Don't use COMMIT or ROLLBACK inside triggers.
Test your transactions in a safe environment before applying them to production. Don't assume changes are permanent without a COMMIT.
Use SET TRANSACTION to define transaction properties when needed. Don't mix DDL and TCL commands in the same transaction.

Do's and Don'ts of TCL

Do's Don'ts
Use COMMIT only after verifying all changes Don’t forget to commit — changes will be lost
Use SAVEPOINT for long or complex transactions Don’t assume ROLLBACK will work after COMMIT
Use TCL to protect data integrity Don’t use TCL on DDL — it’s auto-committed
Rollback if you catch an error in the transaction Don’t commit partial or unverified data
Use clear, meaningful savepoint names Don’t reuse savepoint names carelessly

Best Practices When Using TCL

Best Practice Why It’s Important
Commit regularly Prevents loss of important work during session disconnects
Group logical changes in one transaction Maintains data consistency and integrity
Use SAVEPOINT in long transactions Allows partial rollback without discarding all changes
Log significant transactions Helps in tracking and debugging
Always test before COMMIT Ensures that only clean, error-free data is saved
Handle exceptions in PL/SQL with rollback Protects data in case of run-time failures



COMMIT in Oracle SQL

COMMIT is a Transaction Control Language (TCL) command used to permanently save all the changes made by DML operations (INSERT, UPDATE, DELETE) during the current transaction.


Once a COMMIT is issued, the changes are made visible to all other users, and you cannot undo them using ROLLBACK.


Once you run COMMIT, your changes:

  • Become visible to other users.
  • Cannot be undone using ROLLBACK
  • Are stored permanently in the database

Syntax

COMMIT ;
-- You don’t need to specify anything else — just run it when you're ready to save your changes.

Purpose of COMMIT

Purpose Description
Permanency Saves all work done so far in a transaction
Data Sharing Makes your changes visible to other users
Ends Transaction Ends the current transaction and starts a new one automatically
Locks Released Releases any locks held on the rows by your session

Key Properties of COMMIT

Property Details
Irreversible Once committed, changes cannot be undone
Session-Based Only affects the current session’s changes
Auto-Starts Next Transaction New transaction begins immediately after COMMIT
DDL Implication Any CREATE, DROP, ALTER auto-commits changes

When to Use COMMIT

You should use COMMIT:

  • After completing a logical unit of work.
  • When you're sure your changes are correct.
  • Before releasing control to other users or applications.

Behavior of COMMIT

  • Releases row-level locks.
  • Ends the current transaction.
  • Starts a new transaction automatically.
  • Makes all changes made by the transaction permanent.

Real-Time Scenarios Using COMMIT

Scenario 1: Simple Insert with COMMIT.

INSERT INTO employees (emp_id, name, department)
VALUES (101, 'Alice', 'HR') ;

COMMIT ;

-- Now, all users can see this new row.

Scenario 2: Updating Data and Committing.

UPDATE employees
SET department = 'Finance' WHERE emp_id = 101 ;

COMMIT ;

-- This makes the department update permanent and visible to others.

Scenario 3: Insert + Update + Delete + Commit Together.

INSERT INTO employees
VALUES (102, 'Bob', 'IT' ) ;

UPDATE employees
SET department = 'Admin'
WHERE emp_id = 102 ;

DELETE FROM employees WHERE emp_id = 100 ; -- removing old record

COMMIT -- All these DML changes are committed as one logical unit. Either all changes are saved, or if you had rolled back earlier, all would be undone.

Scenario 4: Without COMMIT (Changes Lost).

UPDATE employees
SET department = 'R&D'
WHERE emp_id = 102 ;

DELETE FROM employees WHERE emp_id = 103 ;

-- Forgot to write COMMIT
-- Session crashes or user closes tool
-- Changes are lost because COMMIT wasn’t issued.

Scenario 5: COMMIT in a PL/SQL Block.

BEGIN
    INSERT INTO employees
    VALUES (104, 'Charlie', 'Legal' ) ;
    COMMIT ;
END ;
/
-- Useful when you want to commit changes inside procedures or anonymous blocks.

Real-Time Example: Bank Transfer

BEGIN
    UPDATE accounts
    SET balance = balance - 1000
    WHERE account_id = 1 ;

    UPDATE accounts
    SET balance = balance + 1000
    WHERE account_id = 2 ;
COMMIT -- Finalizes the transfer ;
END ;
/

If any issue had occurred, you could do:

ROLLBACK ;

-- But once COMMIT is issued, you cannot go back.

COMMIT vs DDL (Important)

Oracle automatically commits any DDL statement.

CREATE TABLE dept_backup AS SELECT * FROM departments ;
-- Auto-committed, no need for explicit COMMIT

DROP TABLE employees ;
-- Auto-committed, no need for explicit COMMIT

-- You cannot ROLLBACK a DROP, ALTER, or CREATE.

Internal Actions Triggered by COMMIT

When you issue COMMIT:

  • Oracle writes the data from the redo log buffer to the online redo log files.
  • Releases any locks held by the session.
  • Clears undo information.

Viewing Pending (Uncommitted) Transactions

SELECT * FROM v$transaction ;
-- You can also check DBA_BLOCKERS, DBA_WAITERS, and V$SESSION to troubleshoot locking and transaction issues.

Common Errors / Misunderstandings

td Avoid committing too early. Wait until entire transaction (all DML steps) are completed successfully.
Error Scenario Error Message Resolution / Fix
Committing incorrect or unverified data (No error — data gets saved) Always validate your data before issuing COMMIT. Use SELECT statements or test environments to review changes.
Trying to ROLLBACK after COMMIT (No error — but rollback has no effect) Understand that COMMIT is final. Plan carefully before committing, especially in scripts.
Assuming SELECT needs COMMIT (No error — COMMIT has no effect) SELECT queries do not require COMMIT, since they don’t change data. No fix needed — just awareness.
Committing in the middle of a faulty process (No error, but results in partial/incorrect data)
Auto-commit settings in tools like SQL Developer (No error, but implicit commits occur) Turn off auto-commit in SQL Developer, TOAD, etc., for better control. This setting can lead to unintended commits.
Transaction committed accidentally in script (No error, but transaction is saved) Review scripts to avoid placing COMMIT statements automatically. Use conditional logic in PL/SQL where needed.
Committing before exception handling in PL/SQL ORA-06510 or other unhandled exceptions after commit Structure PL/SQL blocks to handle exceptions before committing, or commit only when no errors occur.
Trying to commit read-only transactions ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction Change transaction mode using SET TRANSACTION READ WRITE or check user privileges.
Expecting COMMIT to make DDL changes reversible (No error — but DDL is auto-committed) Understand that DDL auto-commits, so COMMIT or ROLLBACK won’t affect those. Use with caution in mixed scripts.

Best Practices for COMMIT

Best Practice Reason
Use after successful data validation Prevents saving wrong or incomplete data
Group logical operations in one transaction Maintains data integrity
Use COMMIT in exception handling wisely Prevents committing in error conditions
Avoid unnecessary commits in large batch jobs Too many commits can slow performance
Log critical commits for audit trails in production systems Helps in tracking issues



ROLLBACK in Oracle SQL

ROLLBACK is a TCL (Transaction Control Language) command used to undo changes made by DML statements (INSERT, UPDATE, DELETE) in the current transaction, since the last COMMIT or a SAVEPOINT.


It is like an "Undo" button — it reverts the database to its previous stable state before the transaction began or to a specified SAVEPOINT.


Syntax

ROLLBACK ;
-- -- Undo all uncommitted changes.

ROLLBACK TO SAVEPOINT savepoint_name ;
-- Undo changes after a savepoint.

How ROLLBACK Works

  • Oracle uses undo segments to store the before image of rows.
  • ROLLBACK reverts the data using these undo records.
  • It releases locks held by the session after rollback.

Purpose of ROLLBACK

Purpose Description
Undo Changes Cancels uncommitted DML operations
Error Recovery Helps recover from logical errors or incorrect updates
Protect Data Integrity Ensures wrong data doesn’t get saved
Partial Undo Can roll back to a specific point using SAVEPOINT

Key Properties of ROLLBACK

Property Description
Session-Specific Only affects changes made in the current session.
Only Works Before COMMIT Once committed, data cannot be rolled back
Auto-Rollback on Exit If session ends without COMMIT, Oracle auto-rolls back.
Releases Locks Frees all row-level locks held by your session

Real-Time Scenarios Using ROLLBACK

Scenario 1: Rollback Entire Transaction

UPDATE employees
    SET department = 'Test'
    WHERE emp_id = 105 ;

    DELETE FROM employees
    WHERE emp_id = 100 ;


-- Realize there was a mistake
ROLLBACK ;

-- Both changes are undone, and data is back to its original state.

Scenario 2: Rolling Back After an Insert.

INSERT INTO employees
VALUES (106, 'Uday', 'IT' ) ;
ROLLBACK ;

--Now, emp_id = 106 will not exist in the table — the insert was undone.

Scenario 3: Using ROLLBACK TO SAVEPOINT

SAVEPOINT pointA ;

UPDATE employees SET department = 'R&D'
WHERE emp_id = 101 ;

SAVEPOINT pointB ;

UPDATE employees SET name = 'harsha'
WHERE emp_id = 101 ;

ROLLBACK TO SAVEPOINT pointA;

--Only changes after pointA are undone. department = 'R&D' remains, but name = 'harsha' is reverted.

Scenario 4: Session Closes Before COMMIT.

UPDATE employees SET department = 'HR'
WHERE emp_id = 102 ;

-- Oracle automatically ROLLBACKs since no COMMIT was issued.

Scenario 5: Using ROLLBACK in a PL/SQL Block (Error Handling).

BEGIN
    INSERT INTO employees
    VALUES (107, 'vardhan', 'Admin' ) ;

    -- Simulate error
    RAISE_APPLICATION_ERROR ( -20001, 'Error occurred' );

EXCEPTION
    WHEN OTHERS THEN
    ROLLBACK ;
    DBMS_OUTPUT.PUT_LINE ('Transaction rolled back due to error');
END ;
/
-- This prevents bad or partial data from being saved.

Scenario 6: ROLLBACK in PL/SQL Block.

BEGIN
    DELETE FROM employees
    WHERE department = 'TestDept';

    IF SQL%ROWCOUNT = 0THEN
      ROLLBACK ;
    ELSE
      COMMIT ;
    END IF ;
END -- If no rows were deleted, changes are rolled back.

System View to Monitor Transactions

You can check uncommitted transactions.

SELECT s.sid, s.serial#, t.status
FROM v$session s
JOIN v$transaction t
ON s.saddr = t.ses_addr ;

Common Mistakes / Errors with ROLLBACK

Error Scenario Error Message Resolution / Fix
ROLLBACK after COMMIT (No error message) - but nothing is rolled back Understand that ROLLBACK has no effect after a COMMIT. Make sure to verify data before committing.
ROLLBACK TO invalid SAVEPOINT ORA-01086: savepoint 'XYZ' never established in this session or is invalid Make sure the savepoint exists before you try to roll back to it. Check spelling and case-sensitivity.
Expecting ROLLBACK to undo DDL (e.g., CREATE TABLE) (No error, but doesn’t rollback) Oracle auto-commits before/after DDL. You cannot rollback CREATE, DROP, or ALTER commands. Use DDL carefully.
Issuing ROLLBACK with no prior transaction (No error, no effect) If no DML (INSERT, UPDATE, DELETE) occurred, ROLLBACK will do nothing. This is normal.
ROLLBACK inside an unhandled PL/SQL error block ORA-06510: PL/SQL: unhandled user-defined exception (or similar) Always use proper EXCEPTION handling inside PL/SQL to catch and rollback on errors.
Rollback fails due to lost connection ORA-03113: end-of-file on communication channel If the session is lost/crashed, Oracle auto-rolls back uncommitted changes. No manual action needed.
Mixing TCL and DDL improperly No rollback of DML due to DDL auto-commit Avoid placing DDL (like CREATE, DROP) in the middle of DML unless changes are committed separately.
Rollback fails in read-only session ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction Make sure you're not in SET TRANSACTION READ ONLY mode before DML. Change to READ WRITE

Best Practices for Using ROLLBACK

Best Practice Why It Matters
Use SAVEPOINT for long transactions Allows partial undo and flexibility
Rollback in case of exceptions Keeps database clean and consistent
Avoid auto-commit in dev tools Enables better control using ROLLBACK
Log failed transactions Helps with debugging and audits
Always test DML in safe environments first Prevents unnecessary rollbacks in production




SAVEPOINT in Oracle SQL

A SAVEPOINT is a named point within a transaction to which you can later ROLLBACK without undoing the entire transaction. It provides partial rollback capability.


It allows you to partially rollback the transaction up to that point without affecting the changes made before the savepoint.


Syntax

SAVEPOINT savepoint_name ;

-- To rollback to a savepoint:
ROLLBACK TO savepoint_name ;

When to Use SAVEPOINT

  • When your transaction has multiple DML operations.
  • When you want to rollback only a part of the transaction.
  • When you want to test operations step-by-step.
  • In complex PL/SQL blocks with conditional logic.

Purpose of SAVEPOINT

  • Partial Undo:- Allows undoing only a part of the transaction.
  • Safe Testing:- Try risky updates between savepoints and undo if needed.
  • Logical Grouping:- Break large transactions into smaller checkpoints.
  • No Auto-Rollback:- SAVEPOINTs survive unless manually rolled back or transaction is committed.

Key Properties

  • Session-specific:- SAVEPOINT is local to your session.
  • Lasts until COMMIT/ROLLBACK:- All SAVEPOINTs are removed on COMMIT or full ROLLBACK.
  • Can be reused:- You can reassign a SAVEPOINT name; it will override the earlier one.
  • Used with ROLLBACK TO:- Only useful if you plan to roll back partially.

Rules and Behavior

Rule Description
Multiple savepoints allowed Yes, in a single transaction
Rollback to any savepoint Yes, selectively undo work
Affects only changes after the savepoint Yes
Savepoints are released When you issue a COMMIT or full ROLLBACK
Same name reused Old one is replaced with the new one

Real-Time Scenarios Using SAVEPOINT

Scenario 1: Basic SAVEPOINT Usage

SAVEPOINT sp_before_insert ;
INSERT INTO employees VALUES (108, 'uday', 'Finance' ) ;

SAVEPOINT sp_before_update ;
UPATE employees SET department = 'HR'
WHERE emp_id = 108 ;

ROLLBACK TO SAVEPOINT sp_before_insert;

-- This rolls back both INSERT and UPDATE, effectively removing the new record.

Scenario 2: Rollback only second action

INSERT INTO employees
VALUES (202, 'Harsha', 'IT' ) ;

SAVEPOINT emp_added ;
UPATE employees SET department = 'Sales'
WHERE emp_id = 202 ;

ROLLBACK TO emp_added;

-- Only the update is rolled back. Insert stays and gets committed.
SELECT * COMMIT ;

-- Only the update is rolled back. Insert stays and gets committed.

Scenario 3: Reusing Savepoint Name (Overwriting).

SAVEPOINT stage1 ;
UPATE employees SET department = 'A'
WHERE emp_id = 101 ;

SAVEPOINT stage1 ; -- previous stage1 is now replaced.
UPATE employees SET department = 'B'
WHERE emp_id = 101 ;

ROLLBACK TO stage1 ;
-- Only the last update ('B') is rolled back. 'A' remains, as the original stage1 was overwritten.

Scenario 4: Commit clears all SAVEPOINTs

SAVEPOINT point1 ;
UPATE employees SET department = 'Legal'
WHERE emp_id = 203 ;

COMMIT ;

ROLLBACK TO point1 ; -- Error: ORA-01086: savepoint 'POINT1' never established — because COMMIT removes all SAVEPOINTs.

SAVEPOINT in PL/SQL Block

BEGIN
    SAVEPOINT start_point ;
    INSERT INTO logs VALUES ( 'Start Transaction', SYSDATE ) ;

    -- Error or unexpected condition
    IF some_condition THEN
      ROLLBACK TO SAVEPOINT start_point;
    END IF ;

    COMMIT ;

END ;

-- This gives you granular control over transaction flow in procedural code.

Common Errors with SAVEPOINT

Error Scenario Error Code & Message Resolution / Fix
Rolling back to a non-existent savepoint ORA-01086: savepoint 'SP1' never established in this session or is invalid Ensure that the savepoint exists in the current session and transaction before rolling back to it. Check for typos or wrong savepoint name.
Trying to use savepoint after COMMIT ORA-01086: savepoint 'SP2' never established in this session or is invalid Once you commit, all savepoints are lost. Declare new savepoints after a new transaction begins.
Savepoint name spelling/case mismatch ORA-01086: savepoint 'sp3' never established in this session or is invalid Oracle is case-insensitive, but avoid inconsistencies. Always double-check spelling. Use consistent naming.
Trying to rollback to a savepoint after full ROLLBACK ORA-01086: savepoint 'SP4' never established in this session or is invalid A full ROLLBACK; clears all savepoints. You must set a new savepoint before using ROLLBACK TO.
Using SAVEPOINT in read-only transactions ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction If you're in a READ ONLY transaction, you cannot perform DML or use savepoints. Use SET TRANSACTION READ WRITE instead.
Re-declaring same SAVEPOINT and expecting earlier one (No error, but logical error — earlier savepoint overwritten) Oracle allows reuse of savepoint names — it just overrides the previous one. Avoid reusing names unless intentional.
SAVEPOINT inside autonomous transactions not visible to main transaction (No error, but savepoint not accessible from outside) Each autonomous transaction has its own scope. Don’t expect savepoints declared in one block to be accessible in another.
Rollback to savepoint inside read-only mode ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction Same as Error #5 — change the transaction to READ WRITE mode if you want to use savepoints and rollback.

Do’s and Don’ts of SAVEPOINT in Oracle SQL

Do's Don'ts
Use SAVEPOINT to mark logical checkpoints in a long or critical transaction. Don’t expect SAVEPOINT to work after a COMMIT — all savepoints are cleared.
Name your savepoints descriptively (e.g., before_update, stage1) for clarity. Don’t use duplicate savepoint names unless you intend to overwrite the earlier one.
Use ROLLBACK TO SAVEPOINT to partially undo changes without affecting earlier successful operations. Don’t confuse SAVEPOINT with full ROLLBACK; savepoints are for partial rollbacks only.
Use savepoints in large or complex scripts to avoid redoing the whole transaction on errors. Don’t assume SAVEPOINT will persist between different PL/SQL blocks or sessions. They’re local to your session.
Combine SAVEPOINT with exception handling in PL/SQL to manage controlled rollbacks. Don’t use SAVEPOINT inside READ ONLY transactions — it only works in DML-active mode.
Remove unnecessary savepoints once you’re sure of the transaction outcome. Don’t overuse savepoints — they consume memory and can make your transaction logic confusing.
Test savepoint behavior thoroughly in nested PL/SQL blocks or with autonomous transactions. Don’t assume a ROLLBACK TO will automatically remove all changes after the savepoint — it only undoes changes made after the savepoint.
Document the use of savepoints in code comments when used in critical or multi-step processes. Don’t forget to COMMIT at the end of the transaction — savepoints don’t save data to the database permanently.




SET TRANSACTION in Oracle SQL

The SET TRANSACTION command is a part of TCL (Transaction Control Language) in Oracle SQL. It allows you to specify the properties of a transaction before any DML operation (INSERT, UPDATE, DELETE) is executed.


It is mainly used to:

  • Define the isolation level of a transaction.
  • Set the transaction to be read-only or read-write.
  • Assign a transaction name (optional, for identification/logging).

Syntax of SET TRANSACTION

SET TRANSACTION [ READ ONLY | READ WRITE ]
      [ISOLATION LEVEL isolation_level]
      [NAME transaction_name] ;

-- You must issue SET TRANSACTION before any DML or DDL statements in a session.

Purpose of Each Clause

Clause Purpose
READ ONLY You can only query data(Allows only SELECT statements), no DML operations allowed in this transaction.
READ WRITE Allows DML operations( INSERT, UPDATE, DELETE) in the transaction (default mode).
ISOLATION LEVELREAD COMMITTED Default mode. Prevents dirty reads but allows non-repeatable reads and phantom reads.
ISOLATION LEVEL SERIALIZABLE Makes the transaction behave as if all were executed in serial order. Prevents dirty, non-repeatable, and phantom reads.
NAME Useful for naming and tracking transactions (especially in tools or logs).

Key Properties of SET TRANSACTION

Property Description
Session-Specific Only affects the current session until COMMIT or ROLLBACK.
Isolation Levels Controls how data is read and locked during the transaction.
Read-Only vs Read-Write Defines whether DML operations are allowed in the transaction.
Transaction Name Optional name for easier identification in logs or monitoring.

Examples with Modes

Example 1: Setting a Transaction to Read-Only

SET TRANSACTION READ ONLY ;

-- This transaction can only perform SELECT statements.
SELECT * FROM employees ;
-- Any DML operation here will result in an error. -- Now, only SELECT statements are allowed in this transaction.

Example 2: Setting a Transaction to Read-Write

SET TRANSACTION READ WRITE ;

-- This transaction can perform DML operations.
INSERT INTO employees VALUES (109, 'Kumar', 'Marketing' ) ;
-- Now, you can perform INSERT, UPDATE, DELETE operations.

Example 3: Setting Isolation Level to SERIALIZABLE

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE ;

-- This transaction will behave as if all operations are executed in serial order.
SELECT * FROM employees ;
-- Prevents dirty reads, non-repeatable reads, and phantom reads.

Example 4: Naming a Transaction

SET TRANSACTION NAME 'MyTransaction' ;

-- This transaction can be identified by the name 'MyTransaction' in logs or monitoring tools.
INSERT INTO employees VALUES (110, 'Vardhan', 'Sales' ) ;

Example 5: Combining Multiple Clauses

SET TRANSACTION READ WRITE, ISOLATION LEVEL SERIALIZABLE, NAME 'ComplexTransaction' ;

-- This transaction allows DML, uses SERIALIZABLE isolation, and is named 'ComplexTransaction'.
INSERT INTO employees VALUES (111, 'Sita', 'HR' ) ;

Real-time scenarios

Scenario 1: Use READ ONLY to ensure consistent report data.

SET TRANSACTION READ ONLY ;

-- Generate a report without allowing any data changes during the transaction.
SELECT * FROM sales_data ;
-- Any attempt to INSERT/UPDATE will raise an error.

Scenario 2: Block unintended DML using READ ONLY.

SET TRANSACTION READ ONLY ;

-- Prevent accidental data changes in a critical reporting session.
UPDATE employees SET department = 'Admin' WHERE emp_id = 101 ;
-- Any DML operation will raise an error.
-- ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction.

Scenario 3: Using SERIALIZABLE for consistent reads in a multi-user app.

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE ;

-- Ensure no dirty reads or phantom reads in a multi-user environment.
SELECT * FROM inventory ;

-- This transaction will behave as if all operations are executed in serial order.
-- If another transaction updates the same rows, Oracle raises an error to maintain consistency.

Scenario 4: Using READ WRITE for a complex transaction with multiple DMLs.

SET TRANSACTION READ WRITE ;

-- Allow multiple DML operations in a single transaction.
INSERT INTO orders VALUES (201, 'Order1', SYSDATE ) ;
UPDATE customers SET status = 'Active'
WHERE customer_id = 101 ;
-- Commit the changes after all operations are done. COMMIT ;

Scenario 5: Naming a transaction for easier tracking.

SET TRANSACTION NAME 'OrderProcessing' ;

-- This transaction can be identified by the name 'OrderProcessing' in logs or monitoring tools.
INSERT INTO orders VALUES (202, 'Order2', SYSDATE ) ;
-- Useful for debugging and tracking complex transactions.

Key Points / Notes

  • SET TRANSACTION must be the first statement in a transaction.
  • It cannot be used after any DML or DDL operations.
  • READ ONLY transactions cannot perform any DML operations.
  • Isolation levels control how data is read and locked during the transaction.
  • Transaction names are optional but useful for tracking and debugging.

Common Errors with SET TRANSACTION

Error Scenario Error Code & Message Resolution / Fix
Using SET TRANSACTION after DML operations ORA-01086: savepoint 'SP1' never established in this session or is invalid SET TRANSACTION must be the first statement in a transaction. Move it before any DML statements.
Setting READ ONLY but trying to perform DML ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction Ensure you set READ WRITE if you need to perform DML operations.
Using an invalid isolation level ORA-02049: timeout: distributed transaction waiting for lock Check the isolation level syntax and ensure it is supported by your Oracle version.
Using SET TRANSACTION in a read-only session ORA-01456: may not perform insert/delete/update operation inside a READ ONLY transaction If you need to change transaction properties, switch to READ WRITE mode first.

Do’s and Don’ts of SET TRANSACTION in Oracle SQL

Do's Don'ts
Use SET TRANSACTION to define transaction properties before any DML operations. Don’t use SET TRANSACTION after executing any DML statements in the session.
Set READ ONLY for reporting transactions to prevent accidental data changes. Don’t try to perform DML operations in a READ ONLY transaction.
Use SERIALIZABLE isolation level for critical transactions requiring strict consistency. Don’t set an unsupported isolation level; check your Oracle version documentation.
Name your transactions for easier tracking and debugging. Don’t forget to COMMIT or ROLLBACK at the end of the transaction to save changes.
Test different isolation levels in a development environment before using them in production. Don’t assume that all isolation levels behave the same; they can have different locking and concurrency effects.
