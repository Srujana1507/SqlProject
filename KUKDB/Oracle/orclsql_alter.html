ALTER TABLE Statement in Oracle SQL

The ALTER TABLE statement in Oracle SQL is used to modify the structure of an existing table.


It allows you to:

  • Add, modify, or drop columns.
  • Rename a table or column.
  • Add or remove constraints.
  • Enable or disable constraints.
  • Add or drop indexes.
  • Modify storage properties and tablespace.

Syntax

Adding a New Column

ALTER TABLE table_name
ADD (
    column_name datatype [DEFAULT value ]
    [CONSTRAINT constraint_name ]
) ;

Modifying an Existing Column

ALTER TABLE table_name
MODIFY (
    column_name datatype [DEFAULT value ]
) ;

Dropping a Column

ALTER TABLE table_name
DROP (
    column_name
) ;

Renaming a Table

ALTER TABLE table_name
RENAME TO (
    new_table_name
) ;

Renaming a Column

ALTER TABLE table_name
RENAME COLUMN (
    Old_Column_Name TO New_Column_Name
) ;

Adding a Constraint

ALTER TABLE table_name
ADD CONSTRAINT (
    constraint_name CONSTRAINT Column_Name
) ;

Dropping a Column

Complete Syntax

CREATE TABLE [schema_name.]table_name (
    column1 datatype [ DEFAULT expr] [column_constraint],
    column1 datatype [ DEFAULT expr] [column_constraint],
    ---
    [constraint_name constraint_type (column_list)],
    ---
)
[SEGMENT CREATION {IMMEDIATE | DEFERRED}]
[ENABLE | DISABLE]
[PCTFREE integer]
[PCTUSED integer]
[TABLESPACE tablespace_name]
[STORAGE (INITIAL integer NEXT integer MAXEXTENTS integer)]
[ORGANIZATION {HEAP | INDEX | EXTERNAL}]
[CLUSTER cluster_name (column_list)] ;

Parameters Explanation

Parameter Description
schema_name The name of the schema where the table will be created. If omitted, it uses the current schema.
table_name The name of the table to be created (unique within the schema).
column1, column2 The names of the columns in the table.
datatype The data type of the column (e.g., VARCHAR2, NUMBER, DATE, etc.).
DEFAULT expr The default value for the column when no value is provided.
constraint Specifies integrity constraints (e.g., PRIMARY KEY, UNIQUE, NOT NULL, CHECK, FOREIGN KEY).
PCTFREE Percentage of free space reserved for future updates.
PCTUSED Minimum percentage of used space before inserting new rows.
TABLESPACE Specifies the tablespace for storage.
ORGANIZATION Specifies the table type (HEAP, INDEX, EXTERNAL).
CLUSTER Associates the table with an existing cluster.

Key Features

  • Supports various data types (VARCHAR2, NUMBER, DATE, CLOB, BLOB, etc.).
  • Allows adding integrity constraints (PRIMARY KEY, FOREIGN KEY, CHECK, etc.).
  • Supports partitioning for better performance.
  • Can define storage settings and tablespaces.
  • Allows defining virtual columns (computed values).
  • Supports external tables (data in files, not in the database).

Basic Examples

Create a simple EMPLOYEES table:

CREATE TABLE employees (
    employee_id NUMBER(6) PRIMARY KEY ,
    first_name VARCHAR2(50),
    last_name VARCHAR2(50) NOT NULL ,
    hire_date DATE DEFAULT SYSDATE,
    salary NUMBER(10, 2)
;

Explanation:-

  • Creates a table EMPLOYEES with five columns.
  • employee_id is the primary key.
  • last_name column cannot be NULL.
  • hire_date defaults to the current date.
  • salary is defined with a precision of 10 and scale of 2.

Data Types Supported

Data Type Description
NUMBER(p, s) Numeric value with precision p and scale s.
VARCHAR2(size) Variable-length character string.
CHAR(size) Fixed-length character string.
DATE Date and time values.
TIMESTAMP Date and time with fractional seconds.
CLOB Large text data.
BLOB Binary large object data.
RAW(size) Binary data.
FLOAT Floating-point number.
BOOLEAN Logical true or false values.

Constraints in CREATE TABLE

constraint Description
NOT NULL Ensures the column cannot store NULL values.
UNIQUE Ensures all values in the column are unique.
PRIMARY KEY Uniquely identifies a row in the table.
FOREIGN KEY Establishes a relationship with another table.
CHECK Ensures values in the column meet specific conditions.
DEFAULT Assigns a default value if no value is specified.

Scenarios:

Scenario 1:- Create a table CUSTOMERS with UNIQUE and NOT NULL constraints.

CREATE TABLE customers (
    customer_id NUMBER(6) PRIMARY KEY,
    customer_name VARCHAR2(100) NOT NULL,
    email VARCHAR2(100) UNIQUE,
    phone_number VARCHAR2(15)
) ;

  • customer_id is the primary key.
  • customer_name cannot be NULL.
  • email must be unique.

Scenario 2:- (Creating a Table with FOREIGN KEY Constraint) Create an ORDERS table with a FOREIGN KEY reference to CUSTOMERS

CREATE TABLE orders (
    order_id NUMBER(6) PRIMARY KEY,
    order_date DATE DEFAULT SYSDATE,
    customer_id NUMBER(6),
    CONSTRAINT fk_customer
    FOREIGN KEY (customer_id)
    REFERENCEScustomers (customer_id)
) ;
  • customer_id references customer_id in the customers table.
  • If the referenced customer_id is deleted, Oracle will prevent deletion unless CASCADE is defined.

Scenario 3:- (Creating a Table with CHECK Constraint) Create a PRODUCTS table with a CHECK constraint.

CREATE TABLE products (
    product_id NUMBER(6) PRIMARY KEY,
    product_name VARCHAR2(100) NOT NULL ,
    price NUMBER(10,2) CHECK (price > 0)
) ;
  • CHECK ensures that the price is greater than 0

Scenario 4:- (Creating a Partitioned Table) Create a SALES table partitioned by year.

CREATE TABLE sales (
    sale_id NUMBER(6),
    sale_date DATE,
    sale_amount NUMBER(10, 2)
) PARTITION BY RANGE (sale_date) (
    PARTITION sales_2024 VALUES LESS THAN ( TO_DATE('2025-01-01', 'YYYY-MM-DD') ), PARTITION sales_2025 VALUES LESS THAN ( TO_DATE('2026-01-01', 'YYYY-MM-DD') )
) ;
  • Data is stored in separate partitions based on year.
  • Improves query performance on large datasets.

Scenario 4:- (Creating a Partitioned Table) Create a SALES table partitioned by year.

CREATE TABLE sales (
    sale_id NUMBER(6),
    sale_date DATE,
    sale_amount NUMBER(10, 2)
) PARTITION BY RANGE (sale_date) (
    PARTITION sales_2024 VALUES LESS THAN ( TO_DATE('2025-01-01', 'YYYY-MM-DD') ), PARTITION sales_2025 VALUES LESS THAN ( TO_DATE('2026-01-01', 'YYYY-MM-DD') )
) ;
  • Data is stored in separate partitions based on year.
  • Improves query performance on large datasets.

Scenario 5:- (Creating a Table with VIRTUAL Column) Create a table with a computed (virtual) column.

CREATE TABLE employee_salary (
    mployee_id NUMBER PRIMARY KEY,
    salary NUMBER(10, 2),
    tax_rate NUMBER(5, 2),
    net_salary AS (salary - (salary * tax_rate / 100)) VIRTUAL
) ;
  • net_salary is computed based on salary and tax_rate.
  • The VIRTUAL column is not physically stored but computed on demand.

Advanced Clauses

Clause Description
PCTFREE Percentage of free space in each block.
PCTUSED Minimum percentage of space that must be used.
INITRANS Number of transaction slots for a block.
MAXTRANS Maximum number of concurrent transactions.
LOGGING/NOLOGGING Controls redo logging behavior.
COMPRESS Enables or disables table compression.

Best Practices

  • Use meaningful and consistent table names.
  • Define primary keys and foreign keys for data integrity.
  • Choose appropriate data types to minimize storage.
  • Avoid using VARCHAR2 with large sizes unless necessary.
  • Always define NOT NULL for mandatory fields.
  • Create indexes for frequently used columns to improve performance.

Do's and Don'ts of CREATE TABLE in Oracle SQL

Do's Don'ts
Use meaningful and consistent table and column names (e.g., employee_id, hire_date). Don’t use reserved keywords as table or column names (e.g., DATE, TABLE).
Always define a PRIMARY KEY for uniquely identifying rows. Don’t create tables without a primary key unless necessary.
Use NOT NULL for mandatory columns to prevent null values. Don’t leave important columns without a NOT NULL constraint.
Use FOREIGN KEY constraints to maintain referential integrity. Don’t define foreign keys without ensuring that referenced tables and values exist.
Use VARCHAR2 for variable-length strings to save space. Don’t use CHAR unless fixed-length data is required.
Choose appropriate data types for each column (e.g., NUMBER, DATE) Don’t use oversized data types — it wastes storage and impacts performance.
Use DEFAULT values where appropriate to ensure consistent data. Don’t define complex logic in DEFAULT values — keep it simple.
Create indexes on frequently searched columns for better performance. Don’t create too many indexes — it slows down INSERT and UPDATE operations.
Partition large tables to improve query performance and manageability. Don’t partition small tables — it increases complexity without benefits.
Use CHECK constraints to enforce business rules. Don’t overuse CHECK constraints — complex logic should be handled at the application level.
Use ORGANIZATION INDEX for read-intensive tables. Don’t use ORGANIZATION INDEX for frequently updated tables.
Use TEMPORARY tables for session-based data processing. Don’t store large data sets in TEMPORARY tables — they are meant for short-term use.
Use SEGMENT CREATION DEFERRED for large tables if you expect future data growth. Don’t use SEGMENT CREATION IMMEDIATE unless data will be inserted immediately.
Test table creation in a development environment before deploying to production. Don’t create tables directly in the production environment without testing.
