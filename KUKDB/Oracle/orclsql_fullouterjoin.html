FULL OUTER JOIN in Oracle SQL

A FULL OUTER JOIN combines the results of both a LEFT OUTER JOIN and a RIGHT OUTER JOIN.

  • All matching rows from both tables.
  • Unmatched rows from the left table with NULL for columns from the right table.
  • Unmatched rows from the right table with NULL for columns from the left table.

Key Features of FULL OUTER JOIN

Feature Description
Comprehensive Data Retrieval Ensures that all rows from both tables are included in the result.
NULL Values for Missing Matches Displays NULL for columns where no match is found in the corresponding table.
Combines Left and Right Outer Joins Functions as a union of LEFT OUTER JOIN and RIGHT OUTER JOIN.
Use Case Ideal for scenarios where you need a comprehensive view of both tables, including their unmatched data.

Syntax

SELECT column_list
FROM table1
FULL OUTER JOIN table2 ON table1.column_name = table2.column_name ;
  • table1: The left table
  • table2: The right table.
  • ON: Specifies the condition for the join.
  • column_list: Columns to retrieve in the result.

Examples / Scenarios

Scenario 1:- Retrieve all customers and all orders, even if there are customers without orders or orders without associated customers.

SELECT c.customer_id, c.customer_name, o.order_id, o.order_date, o.total_amount
FROM customers c
FULL OUTER JOIN orders o
ON c.customer_id = o.customer_id ;
  • All customers with their associated orders.
  • Customers without any orders (order columns will show NULL).
  • Orders without any customer (customer columns will show NULL).

Scenario 2:- Retrieve all departments and employees, including departments without employees and employees not assigned to a department.

SELECT p.product_id, p.product_name, s.sale_id, s.sale_date, s.quantity
FROM products p
FULL OUTER JOIN sales s
ON p.product_id = s.product_id ;
  • Combines all employees and their departments.
  • Lists departments without any employees (employee_id and first_name will show NULL).
  • Lists employees not assigned to any department (department_id and department_name will show NULL).

Scenario 3:- Retrieve all departments and employees, including departments without employees and employees not assigned to a department.

SELECT p.product_id, p.product_name, s.sale_id, s.sale_date, s.quantity
FROM products p
FULL OUTER JOIN sales s
ON p.product_id = s.product_id ;
  • Retrieves all products with their sales data.
  • Lists products with no sales (sale_id, sale_date, and quantity will show NULL).
  • Lists sales that do not match any product (product_id and product_name will show NULL).

Scenario 4:- Retrieve a list of all employees and their projects, including employees without projects and projects without employees.

SELECT e.employee_id, e.name AS employee_name, p.project_id, p.project_name
FROM employees e
FULL OUTER JOIN projects p
ON e.project_id = p.project_id ;

Scenario 5:- ( with WHERE Clause ) Retrieve all products and their corresponding sales, but only include products with stock greater than zero.

SELECT p.product_id, p.product_name, s.sales_amount
FROM products p
FULL OUTER JOIN sales s
ON p.product_id = s.product_id
WHERE p.stock_quantity > 0 OR s.sales_amount > 0 ;

Scenario 5:- ( with Aggregate Function ) Retrieve a list of all departments and the total salaries paid, including departments with no employees and employees not assigned to departments.

SELECT d.department_id, d.department_name, SUM (e.salary) AS total_salary
FROM departments d
FULL OUTER JOIN employees e
ON d.department_id = e.department_id
GROUP BY d.department_id, d.department_name ;

Scenario 6:- ( With ORDER BY ) Retrieve a list of all courses and enrolled students, sorted by course name.

SELECT c.course_id, c.course_name, s.student_id, s.name AS student_name
FROM courses c
FULL OUTER JOIN courses c
ON c.course_id = s.course_id
ORDER BY c.course_name ;

Scenario 7:- ( With Subquery ) Retrieve all customers and their most recent orders. Include customers who have never placed an order and orders with no associated customer.

SELECT c.customer_id, c.customer_name, o.order_date, o.order_id FROM customers c
FULL OUTER JOIN orders o
ON c.customer_id = o.customer_id
WHERE o.order_date = (
    ( SELECT MAX (order_date )
    FROM orders
    WHERE customer_id = customer_id
) ;

Scenario 8:- ( Complex Query ) Combine historical sales data from the sales_archive table and real-time sales data from the sales_live table. Include -

  • Products that are only in historical data.
  • Products that are only in real-time data.
  • Products that exist in both datasets, and calculate the total sales, sales difference, and indicate whether sales increased, decreased, or remained constant.

SELECT
    COALESCE (a.product_id, l.product_id) AS product_id,
    COALESCE (a.product_name, l.product_name) AS product_name,
    NVL (a.total_sales, 0) AS historical_sales,
    NVL (l.total_sales, 0) AS real_time_sales,
    NVL (l.total_sales, 0) - NVL (a.total_sales, 0) AS sales_difference,
    CASE
      WHEN NVL (l.total_sales, 0) > NVL (a.total_sales, 0) THEN 'Increased'
      WHEN NVL (l.total_sales, 0) < NVL (a.total_sales, 0) THEN 'Decreased'
      ELSE 'Unchanged'
    END AS sales_trend
FROM sales_archive a
FULL OUTER JOIN sales_live l
ON a.product_id = l.product_id ;

Scenario 9:- ( Complex Query ) Retrieve a comprehensive list of all employees and their managers from two tables -

  • employees (lists employees and their manager IDs).
  • managers (lists managers and their details).

Additionally:

  • Include employees without assigned managers.
  • Include managers who currently have no employees.
  • Calculate the difference between employee and manager salaries and indicate whether the employee earns more or less than the manager.

SELECT
    COALESCE ( e.employee_id, m.manager_id ) AS person_id,
    COALESCE ( e.employee_name, m.manager_name ) AS person_name,
    CASE
      WHEN e.employee_id IS NOT NULL AND m.manager_id IS NOT NULL THEN 'Employee with Manager'
      WHEN e.employee_id IS NOT NULL AND m.manager_id IS NOT NULL THEN 'Employee without Manager'
      WHEN m.manager_id IS NOT NULL AND m.manager_id IS NOT NULL THEN 'Manager without Employees'
    ELSE AS role,
    NVL (e.salary, 0) AS employee_salary,
    NVL (m.salary, 0) AS manager_salary,
    CASE
      WHEN NVL (e.salary, 0) > NVL (m.salary, 0) THEN 'Employee earns more'
      WHEN NVL (e.salary, 0) < NVL (m.salary, 0) THEN 'Manager earns more'
      ELSE 'Equal salary'
    END AS salary_comparison
FROM employees e
FULL OUTER JOIN managers m
ON e.manager_id = m.manager_id ;

Common Errors in RIGHT OUTER JOIN

Error Description Solution
Incorrect Join Condition A wrong or incomplete ON clause can produce incorrect results or omit rows. Ensure the ON clause defines the correct column relationships.
Ambiguous Column Names Columns with the same name in both tables may cause ambiguity errors. Use table aliases or fully qualify column names (e.g., table1.column_name).
Performance Issues Joining large datasets without proper indexing can lead to slow query performance. Index the join columns to optimize query execution.
NULL Misinterpretation Misunderstanding how NULL values appear for unmatched rows. Recognize that unmatched rows will display NULL for columns of the other table.

Limitations of RIGHT OUTER JOIN

Limitation Description
Performance Can be slower on large datasets compared to other join types due to the inclusion of all rows from both tables.
NULL Values Requires handling NULL values explicitly in queries (e.g., using NVL or COALESCE for replacements).
Complex Queries Adding multiple FULL OUTER JOINs can make queries harder to read and debug.
Incorrect Join Condition Using unrelated or mismatched columns in the ON clause.

Do's and Don'ts of RIGHT OUTER JOIN

Do's Don'ts
Use FULL OUTER JOIN when you need all rows from both tables. Don't assume rows without matches in either table will be excluded (they'll include NULL).
Use meaningful aliases for better readability. Don't ignore NULL values in result processing, especially for calculations or conditions.
Filter rows early with ON and WHERE clauses. Don't apply FULL OUTER JOIN unnecessarily for queries that could use simpler joins.
Test queries on smaller datasets before running on production. Don't use FULL OUTER JOIN indiscriminately on large tables without analyzing performance.
