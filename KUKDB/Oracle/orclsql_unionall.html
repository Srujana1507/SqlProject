UNION ALL Set Operator in Oracle SQL

The UNION ALL operator in Oracle SQL is used to combine the result sets of two or more SELECT queries without removing duplicate rows.


Unlike UNION, it does not perform a DISTINCT operation, making it faster.


Key Features of UNION ALL

  • Combines multiple SELECT query results into a single result set.
  • Does not remove duplicates (i.e., includes all occurrences).
  • The number of columns in all SELECT statements must be the same.
  • The columns in all queries must have compatible data types.
  • More performance-efficient than UNION since it avoids sorting and deduplication.

Syntax of UNION ALL

SELECT column1, column2, ... FROM table1
UNION ALL SELECT column1, column2, ... FROM table2 ;

Examples of UNION Statement

1. Using ORDER BY with UNION ALL:- The ORDER BY clause is only allowed at the end of the last SELECT statement.

  • Combine employee and customer records and sort the final result by ID using UNION ALL.
SELECT emp_id, emp_name FROM employees
UNION ALL SELECT cust_id, cust_name FROM customers
ORDER BY emp_id ;

2. Using WHERE with UNION ALL:- Filters data before merging the results.

  • Retrieve high-earning employees and customers with their IDs and names using UNION ALL.
SELECT emp_id, emp_name FROM employees
WHERE emp_salary > 50000
UNION ALL SELECT cust_id, cust_name FROM customers
WHERE cust_income > 50000 ;

3. Using UNION ALL with GROUP BY:- Groups data before applying UNION ALL.

  • Get the count of employees per department and customers per region using UNION ALL.
SELECT department, COUNT (*) FROM employees
GROUP BY department
UNION ALL SELECT region, COUNT (*) FROM customers
GROUP BY region ;

4. Using UNION ALL with Aggregate Functions:- Allows aggregation before merging result sets.

  • Retrieve average salary by department and average income by region using UNION ALL.
SELECT department, AVG (emp_salary) AS avg_salary FROM employees
GROUP BY department
UNION ALL SELECT region, AVG (cust_income) AS avg_income FROM customers
GROUP BY region ;

5. Using UNION ALL with Joins:- Can be used in queries that contain joins.

  • Retrieve employee details with department names and customer details with region names using UNION ALL.
SELECT e.emp_id, e.emp_name, d.dept_name FROM employees e JOIN departments d ON e.dept_id = d.dept_id
UNION ALL SELECT c.cust_id, c.cust_name, r.region_name FROM customers c
JOIN regions r ON c.region_id = r.region_id ;

Performance Considerations

Aspect UNION UNION ALL
Duplicate Handling Removes duplicates (DISTINCT) Retains all rows (no duplicate removal)
Performance Slower due to sorting & deduplication Faster, no sorting required
Use Case When duplicates must be removed When performance is preferred over duplicate removal

Limitations of UNION ALL

Limitation Description
Column Compatibility All queries must have the same number of columns with compatible data types.
ORDER BY Restriction The ORDER BY clause can only be applied at the end of the last SELECT.
Data Duplication Since duplicates are not removed, it can lead to redundancy in reports.
Larger Result Sets If source tables contain many duplicates, result sets can be significantly larger.

Common Errors in UNION ALL (with Error Codes)

Error Cause Solution
ORA-01790: Expression must have same datatype Mismatched column data types between queries Ensure all SELECT statements return columns with the same data type.
ORA-00904: Invalid identifier Using incorrect column names in ORDER BY Use column aliases if needed
ORA-00933: SQL command not properly ended Incorrect syntax in UNION ALL query Ensure ORDER BY is only at the last SELECT

Do's and Don'ts of UNION ALL in Oracle SQL

Do's Don'ts
Use UNION ALL when you want to retain duplicate rows Don't use UNION ALL when you want to eliminate duplicates – use UNION instead
Ensure the number and data types of columns match in both SELECTs Don’t mismatch column data types or counts – this causes ORA-01789
Use ORDER BY only once at the end of the final SELECT Don’t apply ORDER BY in intermediate SELECTs – it's not allowed
Use aliases to standardize output column names Don’t expect aliases from earlier SELECTs to persist across the entire output
Leverage UNION ALL for better performance when duplicates are acceptable Don’t assume UNION ALL performs deduplication – it doesn't
Use UNION ALL in ETL and audit logs where every record matters Don’t use UNION ALL in reports where cleaned unique records are expected
Apply filters (WHERE) to individual SELECTs before unioning Don’t apply filters after UNION ALL thinking it affects both sides
Use UNION ALL for combining partitioned or archived datasets Don’t forget to validate data quality, especially with logs or history tables

Best Practices

  • Use UNION ALL for performance if duplicates are acceptable.
  • Filter data before applying UNION ALL to reduce dataset size.
  • Ensure column data types match across all SELECT statements.
  • Use indexing on filtered columns for better query performance.
  • Always use ORDER BY at the end of the last query to sort the final result set.
