    Having Clause in Oracle SQL


    The HAVING clause is used to filter grouped data after applying the GROUP BY clause.


    • It is typically used in conjunction with the GROUP BY clause.
    • While the WHERE clause filters rows before grouping, the HAVING clause filters groups created by the GROUP BY clause.
    • It is used to apply conditions on aggregated data (e.g., SUM, AVG, COUNT, MIN, MAX).

    Syntax

    SELECT column1 ,column3 ,aggregate_function(column3)
    FROM table_name
    GROUP BY column1 ,column2 HAVING Condition ;

    Purpose of HAVING Clause

    Purpose Description
    Filter Aggregated Data Applies conditions on grouped data after the GROUP BY operation is performed.
    Refine Query Results Helps to limit the final output to only the groups that meet specific conditions.
    Advanced Filtering Allows complex conditions using aggregate functions that cannot be applied in the WHERE clause.
    Supports Subqueries Enables filtering based on aggregate results compared to values calculated in subqueries.
    Conditional Group Selection Facilitates the selection of groups that meet criteria based on multiple aggregate functions.
    Enhances Data Analysis Simplifies the process of identifying meaningful patterns or exceptions in grouped data.


    Key Rules for Using GROUP BY

    1. Used After GROUP BY:

    • The HAVING clause is applied after the GROUP BY operation to filter grouped records based on aggregate function results.

    2. Works with Aggregate Functions:

    • The HAVING clause supports aggregate functions like SUM, AVG, COUNT, MIN, and MAX. It is designed specifically to filter groups based on these results.

    3. Cannot Replace WHERE:

    • The HAVING clause is used for filtering aggregated data, whereas the WHERE clause is used for filtering individual rows before aggregation.

    4. No Aliases in HAVING:

    • Column aliases defined in the SELECT clause cannot be directly used in the HAVING clause. The full aggregate function must be specified.


    Key Features of HAVING Clause

    Feature Description
    Filtering After Grouping Filters grouped data after the GROUP BY clause is applied.
    Works with Aggregates Filters rows based on aggregate function results (e.g., SUM, COUNT).
    Used with GROUP BY Typically used alongside the GROUP BY clause but can also be used without it in certain cases.
    Supports Conditions Allows conditions such as >, <,=, BETWEEN, LIKE, etc., on aggregate functions.


    Difference Between WHERE and HAVING

    Aspect WHERE Clause HAVING Clause
    Purpose Filters rows before grouping. Filters groups after aggregation.
    Works With Raw data in rows. Aggregate functions and grouped data.
    Execution Order Applied before GROUP BY. Applied after GROUP BY.


    Examples

    Scenario 1: Retrieve departments where the total salary exceeds 50,000:

    SELECT Department ,SUM(Sales) AS TotalSales
    FROM Employees
      GROUP BY Department
        HAVING SUM(Sales) > 50000 ;

    Scenario 2: Retrieve job titles with more than 5 employees.

    SELECT job_id ,COUNT(*) AS EmployeeCount
    FROM Employees
      GROUP BY Department
        HAVING COUNT(*) > 5 ;

    Scenario 3: Retrieve departments with a total salary greater than 50,000 and an average salary greater than 5,000:

    SELECT department_id ,SUM(salary) AS Total_salary ,
    AVG(salary) AS Average_salary ,
    FROM Employees
      GROUP BY department_id
        HAVING AVG(salary) > 5000 AND SUM(salary) > 50000 ;

    Scenario 4: ( HAVING Without GROUP BY ) Retrieve the total salary of all employees if it exceeds 1,000,000

    SELECT SUM(salary) AS Total_Salary
    FROM Employees
      HAVING SUM(salary) > 100000 ;

    Scenario 5: Find departments where at least 3 employees have salaries over 10,000

    SELECT department_id
    FROM employees
    GROUP BY department_id
    HAVING COUNT (
      CASE
        WHEN salary > 10000 THEN 1
        END
      ) >= 3 ;

    Scenario 7: ( HAVING with Subqueries ) List departments with total salary higher than the average total salary across all departments.

    SELECT department_id , SUM( Salary ) AS Total_Salary
    FROM employees
      GROUP BY
        HAVING SUM( Salary ) > (
          SELECT AVG( Total_Salary )
            FROM ( SELECT SUM( Salary ) AS Total_Salary
              FROM employees
              GROUP BY department_id )
            )

    Scenario 8: ( with JOIN ) List product categories with total sales greater than 1,000,000 and average sales per product above 50,000

    SELECT p.category_id ,SUM (s.amount) AS Total_Sales , AVG (s.amount) AS Avg_Sales
      FROM sales s
    JOIN products p ON s.product_id = p.product_id
      GROUP BY p.category_id
        HAVING SUM(s.amount) > 1000000 AND AVG (s.amount) > 50000 ;


    Limitations of HAVING Clause

    Limitations Description
    Depends on GROUP BY Requires a GROUP BY clause, except when aggregating the entire dataset.
    Cannot Use Aliases Directly Column aliases cannot be used in the HAVING clause; you must repeat the aggregate function.
    Performance Filtering large datasets with complex aggregates can be resource-intensive.


    Common Errors with HAVING Clause

    Error Cause Solution
    ORA-00979: Not a Group By Expression Using non-aggregated columns in the HAVING clause without including them in GROUP BY. Include all non-aggregated columns in GROUP BY or use an aggregate function.
    ORA-00904: Invalid Identifier Misspelling column names or using columns not in the result set. Check column names and ensure correct usage in HAVING conditions.
    ORA-01722: Invalid Number Applying invalid conditions (e.g., comparing text with numbers). Ensure proper data types in aggregate functions and conditions.


    Limitations of GROUP BY Clause

    Limitations Description
    Aliased Columns Aliases cannot be used in the GROUP BY clause; use the original column names.
    Aggregate Filters Filtering aggregate results requires the HAVING clause, not WHERE.
    LOB Data Types Columns with CLOB, BLOB, or similar data types cannot be grouped directly.
    Performance on Large Data Grouping on large datasets can be resource-intensive without proper indexing or optimization.


    Do's and Don'ts of HAVING Clause

    Category Do's Don'ts
    Purpose Use HAVING to filter grouped data based on aggregate functions. Don’t use HAVING to filter individual rows; use WHERE instead.
    Aggregate Functions Always use aggregate functions like SUM, AVG, COUNT, etc., in the HAVING clause. Don’t apply HAVING without an aggregate function unless it's applied on grouped columns.
    Combined Usage Combine WHERE and HAVING to filter rows before and after aggregation. Don’t use HAVING for conditions that can be handled more efficiently with WHERE.
    Performance Use HAVING for filtering data based on complex aggregate conditions. Don’t use HAVING unnecessarily, as it processes data after the aggregation step.
    Complex Conditions Use ORDER BY to sort the grouped results if required. Don’t use overly complex aggregate functions without understanding their performance cost.
    GROUP BY Ensure HAVING is used after GROUP BY to filter grouped data. Don’t forget to include all non-aggregated columns in the GROUP BY clause.
    Subqueries Use subqueries with HAVING to compare aggregated values dynamically. Don’t create deeply nested subqueries without analyzing query execution plans.
    Column Aliases Use the full aggregate expression in the HAVING clause instead of column aliases. Don’t reference column aliases directly in the HAVING clause; they are not allowed.
    Sorting Results Use ORDER BY for sorting grouped results after filtering with HAVING. Don’t assume HAVING will automatically sort the grouped data (sorting is not implied).


    Best Practices / Perfor Tips for HAVING

    • Filter Early :- Use the WHERE clause to filter rows before grouping, reducing the number of rows processed.
    • Indexing :- Index columns used in the WHERE and GROUP BY clauses to improve performance.
    • Use Aggregate Caching :- Avoid recalculating the same aggregate functions by using subqueries or Common Table Expressions (CTEs).
    • Avoid Redundant Conditions :- Null values are treated as a distinct group.
    • Combine GROUP BY with ORDER BY :- Simplify the HAVING clause to focus only on essential filters.
