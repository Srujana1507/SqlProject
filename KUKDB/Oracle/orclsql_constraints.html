What are Constraints in Oracle SQL

A constraint is a rule enforced on data in a table to ensure the validity, integrity, and consistency of the data. Oracle applies constraints either at the column level or table level.


Constraints are enforced automatically by Oracle and help prevent invalid data entry, such as duplicate values in a unique column, null values in required fields, or invalid references between tables.


It ensures data accuracy, integrity, and reliability in a database.


Why Constraints are Important

  • Maintain data integrity (accuracy and reliability).
  • Prevent invalid data entry.
  • Enforce relationships between tables (e.g., foreign key).
  • Enhance query performance through indexing (e.g., primary key).
  • Provide business rule enforcement at the database level.

Benefits of Using Constraints

  • Prevents invalid data entry
  • Enforces business rules
  • Improves data quality
  • Reduces the need for complex data validation logic in applications

Categories of Constraints

Constraint Type Keyword Meaning
PRIMARY KEY PRIMARY KEY Combines NOT NULL and UNIQUE — ensures each row is uniquely identifiable
FOREIGN KEY FOREIGN KEY Ensures the value in a column matches a value in another table
NOT NULL NOT NULL Column must have a value (cannot be NULL)
UNIQUE UNIQUE No two rows can have the same value in this column
CHECK CHECK Ensures that the values meet a specific condition
DEFAULT DEFAULT Automatically inserts a default value if no value is provided
DEFERRABLE DEFERRABLE This is useful in complex transactional logic.

Constraints can be defined in two ways

1. Inline (Column Level) Constraints :

  • An inline constraint is written directly along with the column definition when creating or altering a table.
  • It applies to that specific column only.
  • Defined directly after the column definition

Syntax Example

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100) NOT NULL,
    salary NUMBER CHECK(salary > 0)
) ;

  • PRIMARY KEY is defined inline on emp_id
  • NOT NULL is inline on emp_name
  • CHECK (salary > 0) is inline on salary

Key Points

Feature Details
Applies to One column only
Used with NOT NULL, UNIQUE, PRIMARY KEY, CHECK, DEFAULT
Easier for Simple constraints related to a single column
Cannot be used for Multi-column constraints (e.g., composite primary keys)

2. Out-of-line (Table Level) Constraints

  • An out-of-line constraint is written separately after all columns are defined, usually at the end of the table definition.
  • Defined at the end of the column definitions in a CREATE TABLE or ALTER TABLE statement.
  • This method is used for:
    • Naming constraints
    • Applying constraints to multiple columns (like composite keys)
    • Better readability for complex rules

Syntax Example

CREATE TABLE employees (
    emp_id NUMBER ,
    emp_name VARCHAR2(100) ,
    salary NUMBER ,
    CONSTRAINT pk_emp_id PRIMARY KEY (emp_id),
    CONSTRAINT chk_salary CHECK (salary > 0)
) ;

  • pk_emp_id is the name given to the primary key constraint.
  • chk_salary is the name given to the check constraint.

Key Points

Feature Details
Can apply to Single or multiple columns
Used with All types of constraints
Allows naming You can explicitly name the constraint
Required for Composite constraints (e.g., PRIMARY KEY(emp_id, dept_id))
Improves readability Keeps column definitions clean

Summary Table

Feature Inline (Column Level) Out-of-line (Table Level)
Placement Directly on column After all column definitions
Best for Single-column constraints Multi-column or named constraints
Allows constraint names Optional (rarely used) Common and recommended
Types supported All (except multi-column) All
Readability for complex logic Low High

Important Points to Remember !!

  • A table can have only one PRIMARY KEY.
  • A table can have multiple UNIQUE constraints.
  • A FOREIGN KEY must match the primary or unique key of another table.
  • NOT NULL is the only constraint that must be defined at the column level.
  • Constraints can be named for easy reference or Oracle will give them a system-generated name.

Benefits of Constraints in Oracle SQL

Benefit Details
Ensures Data Integrity Prevents invalid or inconsistent data from being entered.
Enforces Business Rules Makes sure the data follows specific rules (e.g., age must be > 18).
Reduces Application Errors Less need to validate data in application code.
Improves Data Consistency All rows follow the same structure and rules.
Prevents Duplicate or Missing Data With PRIMARY KEY, UNIQUE, and NOT NULL, ensures required and unique data.
Supports Relationships Between Tables FOREIGN KEY maintains links between parent and child tables.
Makes Debugging Easier Clearly see what rule was violated when data errors occur.

How to View Constraints in Oracle

You can view constraints using these data dictionary views:

  • USER_CONSTRAINTS - shows all constraints owned by the current user
  • ALL_CONSTRAINTS - shows constraints accessible to the user
  • DBA_CONSTRAINTS - shows all constraints in the database (requires DBA access)

Constraint Names

  • If you don't specify a name, Oracle generates a system name like SYS_C005401.
  • Best practice: Always name your constraints for better readability and management.

Managing Constraints

Operation Syntax
Enable Constraint ALTER TABLE table_name ENABLE CONSTRAINT constraint_name;
Disable Constraint ALTER TABLE table_name DISABLE CONSTRAINT constraint_name;
Drop Constraint ALTER TABLE table_name DROP CONSTRAINT constraint_name;
View Constraints SELECT * FROM user_constraints WHERE table_name = 'YOUR_TABLE';

Behavior Notes

  • Constraints are checked on DML (INSERT, UPDATE) and sometimes on DDL (ALTER).
  • If a constraint is violated, Oracle throws an ORA error (e.g., ORA-00001, ORA-02291).
  • You can defer constraint checking using DEFERRABLE INITIALLY DEFERRED (for foreign keys or check constraints).

System Views for Constraints

  • USER_CONSTRAINTS - Constraints on user's own tables.
  • ALL_CONSTRAINTS - Constraints accessible to the user.
  • DBA_CONSTRAINTS - All constraints in the database (requires DBA access).

Summary Table of Constraints

Constraint Null Allowed Duplicate Allowed Multiple per Table? Enforces Relation
PRIMARY KEY No No No NA
FOREIGN KEY Yes Yes Yes Yes
UNIQUE Yes No Yes NA
NOT NULL No Yes Yes NA
CHECK Yes Yes Yes NA

Do's of Using Constraints

Do's Why
Use meaningful constraint names Easier to understand and manage (e.g., CHK_EMP_AGE instead of SYS_C001234).
Apply NOT NULL to mandatory columns To make sure required data is always entered.
Use PRIMARY KEY to identify each row Ensures uniqueness and prevents nulls.
Use FOREIGN KEY to link related tables Maintains referential integrity.
Use CHECK for business validations Like ensuring age > 18, or salary > 0.
Document constraint rules in your design Helps developers understand the data rules.

Don'ts of Using Constraints

Don'ts Why
Don’t use system-generated constraint names They're hard to understand and maintain.
Don’t overuse CHECK constraints for complex logic Use them only for simple conditions, not for business workflows.
Don’t apply FOREIGN KEYs without proper indexing May lead to poor performance during joins or deletes.
Don’t forget to add NOT NULL for important columns Data might be saved without key information.
Don’t disable constraints in production without reason It risks data corruption or inconsistency.
Don’t assume constraints will improve performance Constraints are for validation, not optimization

Use Case Recommended Constraint(s)

Employee ID must be unique and mandatory PRIMARY KEY (auto applies NOT NULL + UNIQUE)

PRIMARY KEY in Oracle SQL

A PRIMARY KEY is a constraint that uniquely identifies each record in a table. It ensures two things:

  • Cannot have duplicate values:- No two rows can have the same value(s) in the primary key column(s).
  • Cannot have NULL values:- A primary key column cannot have NULL values.
  • Is used to enforce uniqueness and not-null condition in a table.

Key Rules of PRIMARY KEY

Rule Description
Only one PRIMARY KEY per table But it can consist of one or more columns
Automatically NOT NULL You don’t need to define NOT NULL separately
Automatically creates an index Helps improve performance in searches/joins
Must be unique across the table Duplicate values are not allowed

Key Properties of PRIMARY KEY

Property Description
Uniqueness No duplicates allowed.
NOT NULL Cannot contain NULL values.
One per table A table can have only one primary key.
Single or Composite Can consist of one or more columns.
Index Creation Automatically creates a unique index.

Syntax of PRIMARY KEY

1. Inline (Column Level)

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100)
    ) ;

2. Out-of-line (Table Level) with Name

CREATE TABLE employees (
    emp_id NUMBER ,
    emp_name VARCHAR2(100) ,
    CONSTRAINT pk_emp PRIMARY KEY (emp_id)
    ) ;

Examples:

Scenario 1: Single Column PRIMARY KEY:- ( Creating a new table (customers) with a column (customer_id) defined as the primary key to enforce uniqueness and not-null constraints automatically. )

CREATE TABLE customers (
    customer_id NUMBER PRIMARY KEY ,
    name VARCHAR2(50)
    ) ;

  • customer_id uniquely identifies each customer.
  • No duplicate customer_id allowed.
  • No NULLs allowed.

Scenario 2: Composite PRIMARY KEY (Multiple Columns):- a composite (or compound) primary key is created using two columns (student_id and course_id) together to ensure the uniqueness of each enrollment record.

CREATE TABLE enrollments (
    student_id NUMBER ,
    course_id NUMBER,
    CONSTRAINT pk_enrollment PRIMARY KEY (student_id, course_id)
    ) ;

  • A combination of student_id and course_id is unique.
  • Same student can enroll in different courses.
  • Same course can be taken by different students.
  • But the same student cannot enroll in the same course twice.


Scenario 3: Define Primary Key After Table Creation

ALTER TABLE employees ;

ADD CONSTRAINT pk_emp PRIMARY KEY (emp_id) ;

  • Used when the table already exists.
  • You can also drop and re-add if needed.


Scenario 4: Trying to Insert Duplicate or NULL - Error

INSERT INTO customers (customer_id, name) VALUES (1, 'Uday') ;
INSERT INTO customers (customer_id, name) VALUES (1, 'Kankati') ;
- - Error: Duplicate
INSERT INTO customers (customer_id, name) VALUES (, 'Harsha') ;
- - Error: NULL not allowed


Scenario 5: Dropping a PRIMARY KEY

ALTER TABLE employees ;

DROP CONSTRAINT pk_emp ;
  • Removes the primary key.
  • Also drops the associated index.


Scenario 6: Using PRIMARY KEY with FOREIGN KEY (Parent Table)

CREATE TABLE departments (
    dept_id NUMBER PRIMARY KEY,
    dept_name VARCHAR2(50)
    ) ;


    Then used in another table:
CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    emp_name VARCHAR2(100),
    dept_id NUMBER,
    CONSTRAINT fk_dept FOREIGN KEY (dept_id)
    REFERENCES departments(dept_id) ) ;

    -- Here, emp_id is the primary key in employees, and dept_id is a foreign key referencing departments.


Scenario 7: Primary Key + Unique Together

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    email VARCHAR2(100) UNIQUE
    ) ;

  • user_id is the primary key.
  • email must be unique but can be NULL.


Scenario 8: Check Existing Constraints

SELECT constraint_name, constraint_type, table_name
    FROM user_constraints
    WHERE table_name = 'EMPLOYEES'

  • CONSTRAINT_TYPE = 'P' indicates a Primary Key.


Common Errors with PRIMARY KEY

Error Message Reason
ORA-00001: unique constraint violated Inserting duplicate primary key value
ORA-01400: cannot insert NULL Trying to insert NULL in primary key
ORA-02260: table can have only one primary key You tried to create more than one PK

Best Practices for PRIMARY KEY !!

  • Always name your constraint (CONSTRAINT pk_table_name).
  • Use a meaningful, immutable column (like emp_id, invoice_no) as PK.
  • Avoid using large VARCHARs as PKs (prefer NUMBER or smaller types).
  • Don’t use frequently updated columns as primary keys.
  • Avoid NULLable columns – not allowed in PK.
  • Prefer single-column PKs unless business rules demand a composite.

Do's and Don'ts for PRIMARY KEY

Do's Don'ts
Name your primary key constraints clearly Don’t use system-generated names like SYS_C00123
Use single column PK if possible Don’t overcomplicate with multi-column PKs unless required.
Index foreign key columns that reference PK Don’t drop primary key in production without full check
Use composite PK only when natural key exists Don’t use meaningless combinations unless needed



FOREIGN KEY in Oracle SQL

  • A FOREIGN KEY is a constraint used to link two tables.
  • It ensures that the value in one column (or columns) matches a value in another table’s PRIMARY KEY or UNIQUE column.
  • It makes sure that a record in one table must be related to a record in another table.

Purpose of FOREIGN KEY

  • Maintains referential integrity between tables.
  • Prevents inserting invalid values into the child table.
  • Prevents deleting rows from the parent table if they are being referenced in the child table (unless cascading is used).

Basic Terminology

  • Parent Table:- The table that has the primary or unique key (e.g., departments).
  • Child Table:- The table that refers to the parent using a foreign key (e.g., employees).
  • Referential Integrity:- Ensures that references between tables remain valid.

Syntax of FOREIGN KEY

1. Inline (Column Level)

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100),
    dept_id NUMBER REFERENCES departments(dept_id)
    ) ;

2. Out-of-line (Table Level with Constraint Name)

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100),
    dept_id NUMBER,
    CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
    ) ;

Properties of FOREIGN KEY

Property Description
Can allow NULLs Yes (unless NOT NULL is also applied)
Can be composite Yes, referencing multiple columns
Can reference PRIMARY or UNIQUE keys Yes
Cascade options ON DELETE CASCADE, ON DELETE SET NULL
Deferred constraints Optional: DEFERRABLE INITIALLY DEFERRED

How It Works

  • When inserting or updating in the child table, the referenced value must exist in the parent table.
  • Deleting from the parent table is restricted unless handled with ON DELETE rules or the value is not referenced.

Scenario of FOREIGN KEY in Oracle SQL

Scenario 1:- Basic Foreign Key Relationship.

CREATE TABLE departments (
    dept_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100)
    ) ;


CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY ,
    emp_name VARCHAR2(100),
    dept_id NUMBER,
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
    ) ;

  • employees.dept_id must match a dept_id from departments
  • You cannot insert an employee with a dept_id that does not exist.

Scenario 2:- Attempt to Insert Orphan Record.

INSERT INTO employees (emp_id, emp_name, dept_id)
    VALUES (101, 'Uday', 999) ;
    -- ORA-02291: integrity constraint (SCHEMA.FK_EMP_DEPT) violated - parent key not found
  • dept_id 999 does not exist in the parent table.

Scenario 3:- Insert with Matching Parent.

INSERT INTO departments
    VALUES (10, 'HR') ;

INSERT INTO employees
    VALUES (101, 'Uday', 10) ;

  • Works fine - dept_id exists in both tables.

Scenario 4:- Deleting Parent Row (Default Behavior)

DELETE FROM departments dept_id = 10 ;
--ORA-02292: integrity constraint (SCHEMA.FK_EMP_DEPT) violated - child record found
  • By default, Oracle prevents deletion if the child row exists.

Scenario 5:- Deleting Parent with CASCADE (Optional)

  • To allow automatic delete of child rows when a parent is deleted, use ON DELETE CASCADE.
CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    emp_name VARCHAR2(100),
    dept_id NUMBER,
    CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id) ON DELETE CASCADE
) ;
  • Now if you delete a department, all its employees will be deleted automatically.

Scenario 6:- Composite FOREIGN KEY

  • If parent table has a composite primary key, then foreign key must reference both columns.

Parent:

CREATE TABLE orders (
    emp_id NUMBER ,
    order_id NUMBER,
    product_id NUMBER,
    PRIMARY KEY (order_id, product_id)
) ;
  • Now if you delete a department, all its employees will be deleted automatically.

Child:

CREATE TABLE order_items (
    order_id NUMBER,
    product_id NUMBER,
    quantity NUMBER,
    CONSTRAINT fk_order FOREIGN KEY (order_id, product_id) REFERENCES orders(order_id, product_id)
) ;

Scenario 7:- ON DELETE SET NULL

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    emp_name VARCHAR2(100),
    dept_id NUMBER,
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id)
    REFERENCES departments(dept_id) ON DELETE SET NULL
) ;
  • When a department is deleted, the dept_id of all associated employees is set to NULL.

Scenario 8:- Foreign Key to a UNIQUE Column

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    email VARCHAR2(100) UNIQUE
) ;
CREATE TABLE user_profiles (
    profile_id NUMBER PRIMARY KEY,
    email VARCHAR2(100) ,
    CONSTRAINT fk_profile_email FOREIGN KEY (email)
    REFERENCES users(email)
) ;

Scenario 9:- Deferrable Foreign Keys

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    manager_id NUMBER,
    CONSTRAINT fk_mgr FOREIGN KEY (manager_id)
    REFERENCES employees(emp_id)
    DEFERRABLE INITIALLY DEFERRED
) ;
  • Useful for self-referencing tables (like manager → employee).
  • You can delay constraint checking until commit.

Scenario 10:- View Foreign Keys

SELECT constraint_name, table_name, r_constraint_name
FROM user_constraints
WHERE constraint_type = 'R' ;
  • constraint_type = 'R' → Referential (foreign key).

Common Errors with FOREIGN KEY

Error Message Reason
ORA-02291: integrity constraint violated Inserting a value in child table that doesn't exist in parent
ORA-02298: parent key not found Inserting or updating a child row with no matching parent key
ORA-02266: unique/primary keys in table referenced by foreign keys Trying to drop a parent table or column that is referenced elsewhere

Do's and Don'ts of Foreign Key

Do's Don'ts
Always index the foreign key column Don’t leave foreign keys without indexing (causes performance issues)
Use meaningful constraint names (e.g., fk_dept) Don’t use system-generated names (e.g., SYS_C00012)
Use ON DELETE CASCADE carefully Don’t use it unless you're sure you want child rows deleted
Use foreign keys to model real-world relationships Don’t create artificial or unnecessary relationships



UNIQUE Constraint in Oracle SQL

  • A UNIQUE constraint ensures that all values in a column or a set of columns are different across all rows in the table.
  • It allows NULLs, but does not allow duplicate non-null values.

Purpose

  • Prevents duplication of data in a column or group of columns.
  • Enforces data integrity for alternate identifiers (e.g., email, username, national_id).

Key Characteristics of UNIQUE Constraint

Feature Description
Ensures uniqueness All non-null values must be unique in the column(s)
NULLs allowed Yes — multiple NULL values are allowed
Multiple UNIQUE constraints You can have more than one UNIQUE constraint per table
Index creation Oracle automatically creates a unique index on the column(s)
Can be composite You can apply it to one or more columns together
Primary key vs. unique Only one PRIMARY KEY, but multiple UNIQUE constraints allowed

Difference Between PRIMARY KEY and UNIQUE

Feature PRIMARY KEY UNIQUE
Allows NULLs Not allowed Allowed (only once)
Max per table 1 per table Multiple allowed
Index Unique B-tree index Unique B-tree index
Reference target Yes (via FK(Foreign key)) Yes (via FK(Foreign key))

Syntax of UNIQUE Constraint

1. Inline (Column Level):-

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    email VARCHAR2(100) UNIQUE ) ;

2. Out-of-line (Table Level with Name):-

CREATE TABLE users (
    user_id NUMBER ,
    email VARCHAR2(100),
    CONSTRAINT uq_email UNIQUE (email) ) ;

Examples of UNIQUE Constraint

Scenario 1: Email Address Must Be Unique

CREATE TABLE customers (
    customer_id NUMBER PRIMARY KEY ,
    email VARCHAR2(100) UNIQUE ) ;
  • Prevents two customers from using the same email.
  • Allows NULL if a customer doesn't provide an email.

Scenario 2: Mobile Number Should Be Unique, But Not Mandatory

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY ,
    phone_no VARCHAR2(15) UNIQUE
    ) ;

  • Same phone number cannot be registered by two users.
  • Multiple users can have NULL in phone_no.

Scenario 3: Composite UNIQUE Constraint.

CREATE TABLE orders (
    order_id NUMBER,
    product_id NUMBER,
    quantity NUMBER,
    CONSTRAINT uq_order_product UNIQUE (order_id, product_id)
    ) ;

  • The combination of order_id and product_id must be unique.
  • Same order_id or product_id can repeat alone.

Scenario 4: Add UNIQUE Constraint After Table Creation.

ALTER TABLE employees
ADD CONSTRAINT uq_email UNIQUE (email) ;
  • Applies to existing data.
  • Fails if duplicates exist.

Scenario 5: Named UNIQUE Constraint.

CREATE TABLE customers (
    cust_id NUMBER PRIMARY KEY,
    phone_number VARCHAR2(15),
    CONSTRAINT uq_phone UNIQUE (phone_number)
    ) ;

  • The constraint is named uq_phone, useful for debugging and dropping later.

Scenario 6: Insert Duplicate Value.

INSERT INTO customers (cust_id, phone_number) VALUES(101, '1234567890'); ;
INSERT INTO customers (cust_id, phone_number) VALUES(102, '1234567890'); ;

-- ORA-00001: unique constraint (SCHEMA.UQ_PHONE) violated.

Scenario 7: Insert NULLs in UNIQUE Column.

INSERT INTO customers (cust_id, phone_number) VALUES(103, NULL); ;
INSERT INTO customers (cust_id, phone_number) VALUES(104, NULL); ;

-- Allowed - Oracle treats NULLs as unique values in the context of UNIQUE constraints.

Scenario 8: Drop UNIQUE Constraint.

ALTER TABLE customers
DROP CONSTRAINT uq_phone ;

Scenario 9: Using UNIQUE Constraint with Foreign Key.

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    national_id VARCHAR2(20) UNIQUE
    ) ;

CREATE TABLE payroll (
    payroll_id NUMBER PRIMARY KEY,
    national_id VARCHAR2(20),
    CONSTRAINT fk_nid FOREIGN KEY (national_id) REFERENCES employees(national_id)
    ) ;


-- A foreign key can reference a UNIQUE key, not just a PRIMARY KEY.

Scenario 10: Check Existing UNIQUE Constraints.

SELECT constraint_name, table_name, constraint_type
FROM user_constraints
WHERE constraint_type = 'U' ;

-- constraint_type = 'U' means UNIQUE constraint.

Scenario 11: Index Created by UNIQUE Constraint.


When you create a UNIQUE constraint, Oracle automatically creates a unique index.

SELECT index_name, uniqueness
FROM user_indexes
WHERE table_name = 'USERS' ;

Common Errors with UNIQUE Constraint

Error Message Reason
ORA-00001: unique constraint violated Trying to insert a duplicate unique value
ORA-01452: cannot CREATE UNIQUE index Duplicate values already exist when adding constraint
ORA-02261: such unique or primary key exists You tried to create a duplicate index/constraint name

Do's and Don'ts of UNIQUE Constraint

Do's Don'ts
Use UNIQUE when values must be different Don’t confuse UNIQUE with PRIMARY KEY
Name your constraints clearly (uq_email) Don’t rely on system-generated names (SYS_C00992)
Index the column if it’s often used in searches Don’t leave unique constraints on rarely-used columns
Combine multiple columns only if necessary Don’t create unnecessary composite UNIQUE constraints

Best Practices

  • Always name your UNIQUE constraint.
  • Use UNIQUE for columns like:
    • Emails
    • Username
    • National IDs
    • Document Numbers
  • Do not confuse UNIQUE with NOT NULL - they serve different purposes.
  • Combine UNIQUE + NOT NULL if you want both uniqueness and required values.



CHECK Constraint in Oracle SQL

  • A CHECK constraint in Oracle SQL is used to enforce a condition or rule on a column's values.
  • It ensures that only values satisfying a specific logical condition can be inserted or updated.
  • In simple terms: It makes sure that the value stored in a column meets a certain condition.
<

Purpose of CHECK Constraint

  • To limit the range, type, or format of data values.
  • To enforce business rules directly at the database level.
  • Acts as a data validation mechanism inside the table structure.

Key Points

Feature Description
Applied to One or more columns
Logical expressions Must evaluate to TRUE or UNKNOWN
Fails when Condition evaluates to FALSE
Supports functions Yes (deterministic ones)
NULL behavior NULL values are allowed unless restricted separately

Syntax of CHECK Constraint

1. Inline (Column Level):-

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    age NUMBER CHECK (age >= 18)
    ) ;

2. Out-of-line (Table Level with Constraint Name):-

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    age NUMBER ,
    salary NUMBER,
    CONSTRAINT chk_salary CHECK (salary >= 10000) ) ;

Examples of CHECK Constraint

Scenario 1: Age Should Be 18 or Above.

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    age NUMBER CHECK (age >= 18) ) ;

-- Prevents inserting users younger than 18.

Scenario 2: Salary Must Be Within a Range.

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    salary NUMBER CHECK (salary BETWEEN 10000 AND 200000) ) ;

-- Makes sure salary is within valid company limits.

Scenario 3: Gender Must Be M or F.

CREATE TABLE persons (
    person_id NUMBER PRIMARY KEY,
    gender CHAR(1) CHECK ( gender IN ( 'M', 'F' ) )
    ) ;

-- Prevents inserting invalid gender values.

Scenario 5: CHECK on Multiple Columns.

CREATE TABLE products (
    product_id NUMBER PRIMARY KEY ,
    price NUMBER,
    discount NUMBER,
    CONSTRAINT chk_price_discount CHECK ( price >= discount ) ;

-- Ensures discount is not greater than price.

Scenario 6: Multiple CHECK Constraints on the Same Column.

CREATE TABLE products (
    product_id NUMBER PRIMARY KEY ,
    price NUMBER,
    CONSTRAINT chk_price_min CHECK ( price >= 0 )
    CONSTRAINT chk_price_max CHECK ( price <= 10000 )
    ) ;

-- price must be > 0 and ≤ 10000.

Scenario 7: CHECK on Multiple Columns (Table-level).

CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY ,
    quantity NUMBER,
    unit_price NUMBER,
    CONSTRAINT chk_total_value CHECK (quantity * unit_price <= 100000)
    ) ;

-- Ensures that the total order value doesn’t exceed ₹100,000.

Scenario 8: Add CHECK Constraint After Table Creation.

ALTER TABLE employees
ADD CONSTRAINT chk_comm CHECK (commission_pct BETWEEN 0 AND 0.5 ) ;

Scenario 9: Drop CHECK Constraint.

ALTER TABLE employees
DROP CONSTRAINT chk_comm ;

Scenario 10: View Existing CHECK Constraints.

SELECT constraint_name, search_condition, table_name
FROM user_constraints
WHERE constraint_type = 'C' ;

-- constraint_type = 'C' → Check constraints.

Common Errors of CHECK Constraint

Error Message Reason
ORA-02290: check constraint violated You inserted a value that violates the rule
ORA-02438: column check constraint You tried to define an invalid condition

Do's and Don'ts

Do's Don'ts
Use for business rules (e.g., age, range) Don’t use for complex logic (use triggers instead)
Name constraints clearly (e.g., chk_age) Don’t use system-generated names (SYS_C0001234)
Use simple expressions (e.g., age >= 18) Don’t use functions or subqueries inside CHECK
Validate existing data before adding new CHECKs Don’t add a constraint if data already violates the rule

Best Practices

  • Name your constraints explicitly.
  • Use table-level syntax if referencing multiple columns.
  • Combine with NOT NULL if needed.
  • Avoid complex or non-deterministic functions in CHECK constraints.
  • Use CHECK constraints for data logic, not business workflows.



NOT NULL Constraint in Oracle SQL

  • The NOT NULL constraint ensures that a column cannot contain NULL values.
  • In other words, every row must have a non-null value for that column.

Purpose of NOT NULL Constraint

  • Enforces that critical columns always have a value.
  • Prevents incomplete or missing data.
  • Commonly used for columns like username, password, order date, etc.

Key Points About NOT NULL

Feature Description
Applied to Only single columns (not multiple)
Allows NULL? No — value must be provided
Default value? No — value must be explicitly provided, unless default is specified
Constraint type Not enforced via user_constraints, but as a column attribute
Unique? No — does not enforce uniqueness, only non-null

Syntax of NOT NULL Constraint

During Table Creation (Column-level Only)

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    username VARCHAR2(50) NOT NULL
) ;

During Modifying Table

ALTER TABLE users (
    MODIFY username VARCHAR2(50) NOT NULL
) ;

Behavior

If you try to insert or update a row with a NULL value in a NOT NULL column, Oracle will throw an error:

INSERT INTO users (user_id, username)
VALUES (1, NULL) ;

-- ORA-01400: cannot insert NULL into ("USERS"."USERNAME")

Examples of NOT NULL Constraint

Scenario 1: Username Should Never Be Empty.

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY,
    username VARCHAR2(50) NOT NULL
) ;

  • Every user must have a username.
  • Cannot be left blank or NULL.

Scenario 2: Order Date is Mandatory in Sales System

CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    customer_id NUMBER,
    order_date DATE NOT NULL
) ;

  • You must provide the order date during insert.
  • Useful for tracking and billing.

Scenario 3: Applying NOT NULL to Existing Table

ALTER TABLE employees
MODIFY hire_date DATE NOT NULL ;

-- Oracle will allow this only if all existing rows have a non-null value in hire_date.

Scenario 4: Remove NOT NULL Constraint.

ALTER TABLE employees
MODIFY emp_name VARCHAR2(50) NULL ;

-- This allows emp_name to accept NULL values.

Scenario 5: Check Which Columns Are NOT NULL.

SELECT column_name, nullable
FROM user_tab_columns
WHERE table_name = 'EMPLOYEES' ;

-- nullable = 'N' → means column has NOT NULL constraint.

Scenario 6: Using DEFAULT with NOT NULL.

CREATE TABLE customers (
    cust_id NUMBER PRIMARY KEY ,
    country VARCHAR2(30) DEFAULT 'India' NOT NULL
) ;

  • If country is omitted in INSERT, it gets 'India'.
  • If explicitly set to NULL, it still fails due to NOT NULL.

Scenario 7: NOT NULL vs CHECK (col IS NOT NULL).

Both enforce non-nullability, but

-- Not recommended

CONSTRAINT chk_col_not_null CHECK (col IS NOT NULL ) ;

Works, but NOT NULL is:

  • More efficient.
  • Recognized directly by Oracle's internal structures.

Scenario 8: Combining with UNIQUE.

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY ,
    email VARCHAR2(100) UNIQUE NOT NULL
) ;

  • email must be unique AND non-null.

Scenario 9: With Foreign Key

CREATE TABLE departments (
    dept_id NUMBER PRIMARY KEY
) ;

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY , dept_id NUMBER NOT NULL , CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
) ;
  • dept_id must be provided for every employee — ensures referential integrity.

Key Differences from Other Constraints

Constraint Allows NULL? Enforces Uniqueness Description
NOT NULL No No Just prevents NULLs
PRIMARY KEY No Yes Prevents NULLs + Duplicates
UNIQUE Yes Yes Prevents Duplicates but allows NULLs

Common Mistakes & Errors

Error Code Reason
ORA-01400 Trying to insert NULL into NOT NULL column
ORA-01735 Attempting to define NOT NULL as table-level
ORA-01442 Column to be modified to NOT NULL contains NULL values

Do's and Don'ts

Do's Don'ts
Use for mandatory fields Don’t use if column can logically be NULL
Apply only after verifying existing data Don’t blindly apply on large tables (may cause failure)
Combine with UNIQUE or CHECK if needed Don’t confuse NOT NULL with data type defaults
Name the column meaningfully (e.g., email) Don’t leave critical columns without NOT NULL

Best Practices

  • Use NOT NULL on primary business-required fields (e.g., names, dates, codes).
  • Add it during table creation, not after — avoids data cleanup.
  • Combine with DEFAULT when appropriate.
  • Avoid using CHECK (col IS NOT NULL) instead of NOT NULL.



DEFAULT Constraint in Oracle SQL

The DEFAULT constraint is used to assign a predefined value to a column when no value is explicitly specified during an INSERT operation.


In simple words: If you don't give a value for the column, Oracle will automatically fill it with the default value.


Purpose of DEFAULT

  • Ensures non-null default behavior without forcing NOT NULL.
  • Reduces the need for application logic to supply default values.
  • Reduces the need to specify every column in INSERT statements.
  • Enhances data consistency and minimizes NULLs.
  • Ensures that some value is always present (not necessarily NOT NULL).

Key Features

Feature Description
Applies to Column-level only
Automatically inserts value Yes, when omitted from INSERT
Can be used with NOT NULL Yes
Can be any expression Constants, SYSDATE, sequences (via trigger)

Syntax of DEFAULT Constraint

1. While Creating a Table.

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    status VARCHAR2(10) DEFAULT 'ACTIVE'
) ;

2. While Altering a Table.

ALTER TABLE employees MODIFY status DEFAULT 'ACTIVE' ;

Exampl of DEFAULT Constraint

Scenario 1: Default Status as 'ACTIVE'

CREATE TABLE users (
    user_id NUMBER PRIMARY KEY ,
    username VARCHAR2(50),
    status VARCHAR2(10) DEFAULT 'ACTIVE'
) ;

-- -- Insert without providing 'status'
INSERT INTO users (user_id, username) VALUES (1, 'Uday' ) ;
-- -- status will automatically be 'ACTIVE'

Scenario 2: Default Join Date as Current Date.

CREATE TABLE staff (
    staff_id NUMBER PRIMARY KEY,
    name VARCHAR2(50),
    join_date DATE DEFAULT SYSDATE
) ;

-- Oracle will insert the current system date if not provided.

Scenario 3: Default Quantity to 1 in Orders.

CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    product VARCHAR2(50),
    quantity NUMBER DEFAULT 1
) ;

-- If customer forgets to mention quantity, system will assume 1.

Scenario 4: Adding DEFAULT to Existing Column.

ALTER TABLE orders MODIFY quantity DEFAULT 1 ;

Scenario 5: Insert NULL Still Overrides DEFAULT.

INSERT INTO orders (order_id, product, quantity)
(101, 'Mouse', NULL ) ;

-- DEFAULT won't apply here; NULL will be stored.

Important Note:- DEFAULT works only when the column is not mentioned in the insert, not when it is explicitly given as NULL.


Scenario 6: Remove DEFAULT Constraint.

ALTER TABLE employees
MODIFY status DEFAULT NULL ) ;

-- Removes default — NULL is used if column is omitted.

Scenario 7: DEFAULT with NOT NULL.

CREATE TABLE accounts (
    acc_id NUMBER PRIMARY KEY ,
    acc_status VARCHAR2(20) DEFAULT 'Open' NOT NULL
    ) ;

-- Ensures every record has a non-null status — either by default or explicitly.

Scenario 9: DEFAULT Not Used When NULL Given.

INSERT INTO accounts (acc_id, acc_status) VALUES (201, NULL);
  • Inserts NULL explicitly — default is not used.
  • Use NOT NULL if NULLs should never be accepted.

Scenario 10: View Column Defaults.

SELECT column_name, data_default
FROM user_tab_columns
WHERE table_name = 'EMPLOYEES' ;

Common Mistakes of DEFAULT Constraint

Mistakes Why It's Wrong
Assuming DEFAULT replaces NULL If you insert NULL, it stays NULL — default won't be used
Using invalid data types Default value must match column data type
Forgetting quotes around strings Use 'value', not value for string columns

Important Notes

Case Behavior
Column omitted in INSERT DEFAULT applies
Column explicitly set to NULL DEFAULT is ignored
DEFAULT expression Can be a constant, SYSDATE, or simple function
Sequences in DEFAULT? Not supported directly — use triggers instead

Best Practices

  • Use DEFAULTs to ensure application-independent behavior.
  • Combine with NOT NULL to make sure defaults are always used.
  • Do not rely on DEFAULT for complex logic — use triggers instead.
  • Always verify default values for DATE, BOOLEAN-like flags, and numeric codes.

Do's and Don'ts

Do's Don'ts
Use for frequently repeated values (e.g., 'ACTIVE') Don’t rely on DEFAULT for required fields (use NOT NULL)
Use SYSDATE, constants, or literals as default values Don’t use subqueries or functions like SELECT
Document default values for clarity Don’t assume it overrides explicitly inserted NULLs
Set defaults on config-driven or status fields Don’t add defaults without confirming with business team



READ-ONLY Constraint in Oracle SQL

Oracle does not have a traditional "read-only constraint" as a named constraint type like PRIMARY KEY, CHECK, or FOREIGN KEY.


  • A READ-ONLY constraint is a restriction applied to a table or a column that makes it non-updatable.
  • You cannot INSERT, UPDATE, or DELETE data in that table or column when it is set to READ ONLY.

Instead, Oracle allows making a table (or view) or specific columns read-only using other mechanisms, such as:

  • Making a table read-only.
  • Creating read-only views.
  • Using Virtual Private Database (VPD) policies.
  • Marking a pluggable database as read-only.
  • Using INVISIBLE columns to hide from DML

Use Cases

  • Prevent accidental updates in critical reporting tables.
  • Protect data in archive or audit tables.
  • Enforce security or business rules without changing privileges.

Syntax:-

1. Making a Table Read-Only:-

  • You can prevent DML operations (INSERT, UPDATE, DELETE) on a table using:
ALTER TABLE table_name READ ONLY ;

Example:

1. Make Entire Table Read-Only.

ALTER TABLE employees READ ONLY ;

  • SELECT * FROM employees; → Works
  • INSERT INTO employees ... → Error
  • UPDATE employees ... → Error
  • DELETE FROM employees ... → Error

Make Table Writable Again

ALTER TABLE employees READ WRITE ;

Column-Level Read-Only (Virtual Columns only).

You cannot make regular columns read-only directly, but you can create a virtual column which is automatically read-only:

CREATE TABLE sales (
    product_id NUMBER,
    price NUMBER,
    tax NUMBER,
    total_amount AS (price + tax) -- This is a virtual column (read-only by default)
    ) ;
-- You cannot insert or update the total_amount column directly.

Creating a Read-Only View.

Views can be made read-only by simply not including WITH CHECK OPTION, or by marking them explicitly:

CREATE VIEW emp_view AS
SELECT emp_id, emp_name FROM employees
WITH READ ONLY ;

-- This prevents INSERT/UPDATE/DELETE on the view.

Marking Pluggable Database as READ ONLY.

  • For Oracle Multitenant environments (CDB/PDB):
ALTER PLUGGABLE DATABASE pdb_name CLOSE IMMEDIATE ;
ALTER PLUGGABLE DATABASE pdb_name OPEN READ ONLY ;

-- All objects in that pluggable DB are now read-only.

Using INVISIBLE Columns (Limited Protection).


Marking columns as INVISIBLE doesn’t make them read-only but hides them from:

  • SELECT *
  • Tools
  • INSERT (unless explicitly listed)

ALTER TABLE employees MODIFY emp_salary INVISIBLE ;

Key Notes

Behavior Oracle Support
Column-level read-only Not natively (simulate with triggers)
Table-level read-only Yes (ALTER TABLE)
View-level read-only Yes (WITH READ ONLY)
Conditional read-only VPD / triggers
Schema/database read-only Via PDBs or roles
Scope Table-level only (not individual columns)
Data Modification INSERT, UPDATE, DELETE are blocked
DDL (like ADD column) Still allowed

Summary: "Read-Only" Mechanisms in Oracle

Use Case Approach
Entire table read-only ALTER TABLE ... READ ONLY
View read-only WITH READ ONLY clause
Column read-only Simulate with BEFORE UPDATE triggers
Schema/PDB read-only ALTER PLUGGABLE DATABASE
Condition-based security VPD / Fine-Grained Access Control

Do's and Don'ts of Read-Only constraint

Do's Don'ts
Use READ ONLY for archived, historical, or static data. Don’t apply to transactional tables unless necessary.
Document purpose in data dictionary or team notes. Don’t confuse with SELECT-only privileges (different)
Remove read-only flag before planned updates. Don’t forget to switch back to READ WRITE if needed.
Use in dev/stage environments to prevent test damage. Don’t use as a replacement for proper user permissions.




DEFERRABLE Constraints in Oracle SQL

A DEFERRABLE constraint is a constraint (typically FOREIGN KEY, UNIQUE, or CHECK) that can be deferred until the end of the transaction rather than being enforced immediately at each SQL statement.


This is useful in complex transactional logic, such as:

  • Mutually dependent rows
  • Cross-inserts or updates
  • Temporary violations that will be fixed before commit

Key Concepts

Tearm Meaning
DEFERRABLE Constraint can be deferred
NOT DEFERRABLE Constraint is always enforced immediately (default)
INITIALLY IMMEDIATE Constraint is checked immediately by default
INITIALLY DEFERRED Constraint is checked at the end of the transaction by default

Syntax for Creating DEFERRABLE Constraints

CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    cust_id NUMBER,
    CONSTRAINT fk_customer
      FOREIGN KEY (cust_id)
      REFERENCES customers(cust_id)
      DEFERRABLE INITIALLY IMMEDIATE

) ;

Changing Deferral Mode in a Transaction

If a constraint is defined as DEFERRABLE, you can switch its behavior at runtime using:

SET CONSTRAINT fk_customer DEFERRED ;

-- or

SET CONSTRAINT fk_customer IMMEDIATE ;

All deferrable constraints can also be switched at once:

SET CONSTRAINTS ALL DEFERRED ;

Example Scenario

Scenario: Circular Foreign Keys.

CREATE TABLE employees (
    emp_id NUMBER PRIMARY KEY,
    mgr_id NUMBER,
    CONSTRAINT fk_mgr
      FOREIGN KEY (mgr_id)
      REFERENCES employees(emp_id)br DEFERRABLE INITIALLY IMMEDIATE

) ;

Now, in a transaction, you can:

BEGIN ;

-- Insert two mutually dependent rows
INSERT INTOemployees (emp_id, mgr_id) VALUES (1, 2) ;

INSERT INTOemployees (emp_id, mgr_id) VALUES (2, 1) ;

COMMIT ;

  • If fk_mgr were not deferrable, this would fail.

Important Rules and Limitations

  • Only FOREIGN KEY, UNIQUE, and CHECK can be DEFERRABLE.
  • NOT NULL cannot be deferrable
  • Must be defined at creation — you can’t later alter a NOT DEFERRABLE constraint to DEFERRABLE
  • Useful only in multi-step transactions
  • Slight overhead — use only when needed

How to Check if a Constraint is DEFERRABLE

SELECT constraint_name, deferrable, deferred
FROMuser_constraints
WHERE table_name = 'EMPLOYEES' ;

Summary

Feature Supported
Useful for cross-row validation Yes
Applies to PK/FK/Check/Unique Partially
ALTERABLE after creation No
Helps avoid temporary violations Yes
Default state NOT DEFERRABLE INITIALLY IMMEDIATE
