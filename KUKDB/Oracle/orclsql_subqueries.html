Subquery in Oracle SQL

A subquery (also known as an inner query or nested query) is a query within another query.


It is used to retrieve data that will be used by the main query (also called the outer query).


Subqueries can return a single value, a row, or even a full table result.


It is enclosed within parentheses and executed first, returning a result set that the outer query uses.


Why Use Subqueries

Subqueries helps you to:

  • Breaking down complex problems into smaller, manageable parts.
  • Writing dynamic and flexible queries.
  • Fetching data based on conditions that depend on another query.
  • Improving readability and maintainability of SQL statements.

Importance of Subqueries

Importance Description
Flexibility Allows complex logic that can't be easily handled with simple joins or filters.
Data Isolation The outer query doesn’t directly need to know the data logic of the subquery — subqueries isolate that logic.
Improved Readability Sometimes simplifies complex queries by breaking them into smaller, manageable parts.
Dynamic Conditions Allows you to dynamically retrieve values to filter the outer query.

Key Features of Subqueries

Key Feature Description
Nested Queries Subqueries can be nested within SELECT, FROM, WHERE, HAVING clauses.
Multiple Return Types Can return a single value, a single row, or a full table (multiple rows and columns).
Used in Various Clauses Subqueries can work in SELECT, UPDATE, DELETE, INSERT, WHERE, FROM, HAVING clauses.
Supports Correlated Logic Subqueries can reference columns from the outer query (Correlated Subqueries).
Works with All Operators Subqueries work with operators like IN, EXISTS, ANY, ALL, =, !=, <,> etc.

Types of Subqueries

Subquery Type Description
Single Row Subquery Returns only one row with one column. Usually used with =, <,>, <=,>= operators.
Multiple Row Subquery Returns multiple rows, usually used with IN, ANY, ALL.
Multiple Column Subquery Returns multiple columns, often used with EXISTS or for comparison with tuples.
Correlated Subquery References a column from the outer query. This subquery executes once for each row processed by the outer query.
Nested Subquery A subquery within another subquery (multi-level nesting).
Inline View A subquery used in the FROM clause as a temporary table.
Scalar Subquery Returns a single value and can be used in SELECT, WHERE, HAVING clauses.

Where Can we use Subqueries

  • SELECT - A Subquery can act as a column to fetch some computed value.
  • FROM - A Subquery can act as a table, called Inline View.
  • WHERE - A Most common — subquery filters rows dynamically.
  • HAVING - A Subquery helps apply aggregate conditions.
  • INSERT - A Subquery can be used to insert rows fetched from another table.
  • UPDATE - A Subquery can be used to update rows based on values fetched.
  • DELETE - A Subquery can help delete rows based on a condition derived from another table.

Operators Used with Subqueries

  • = :- Used in single-row subqueries when expecting exactly one result.
  • IN :- Used in multi-row subqueries to check for multiple matching values.
  • ANY :- Compares a value to any result returned by the subquery.
  • ALL :- Compares a value to all results returned by the subquery.
  • EXISTS :- Checks if the subquery returns any records (true/false).
  • NOT IN :- Excludes values returned by the subquery.
  • NOT EXISTS :- Returns true if the subquery finds no matching records.

Rules for Subqueries

Rule Description
Column Count Subquery must return only 1 column when used in WHERE or HAVING.
Row Count Subquery must return 1 row when used with =, <,> operators.
Placement Subqueries can be placed in any SQL clause — SELECT, FROM, WHERE, HAVING.
Nesting Limit Oracle supports up to 255 nested subqueries.
Data Type Matching Columns compared between subquery and outer query should have compatible data types.
Correlated Subquery When using correlated subqueries, outer query columns should be referenced in subquery condition.

Subqueries vs. Joins

Feature Subquery Join
Performance Slower in some cases, as it executes separately for each row. Faster for large datasets, especially with indexed columns.
Readability Easier to read and understand for filtering or aggregation. Better for retrieving related data from multiple tables.
Use Case Used when a query depends on a dynamic condition from another table. Used when data needs to be combined from multiple related tables.

Limitations of Subqueries

Limitation Description
Performance Subqueries (especially correlated subqueries) can be slow on large datasets.
Nesting Limit Maximum nesting is limited to 255 levels.
Data Type Matching Subquery results must match the data type of the outer query columns being compared.
Readability Deeply nested subqueries become hard to read and maintain.
Not Always Optimized Sometimes subqueries prevent the optimizer from performing efficient operations like join elimination.
Cannot Modify the Same Table In UPDATE or DELETE, the subquery cannot reference the same table being modified.
Single-Row Subquery Errors Using a single-row operator (=) with a subquery that returns multiple rows causes an error.
Correlated Subqueries Can Be Slow They execute once per outer row, leading to performance degradation.

Common Errors in Subqueries

Error Code Cause Solution
ORA-01427 Subquery returns more than one row where only one row is expected. Use IN, ANY, EXISTS, or revise subquery logic.
ORA-00913 Too many values (when comparing columns). Ensure the subquery returns only matching columns for comparison.
ORA-01799 Column not allowed in correlated subquery. Ensure the correlated column is correctly used and referenced.
ORA-00936 Missing expression — Subquery not returning expected column. Ensure correct SELECT list and column names.
ORA-00904 Invalid identifier. Column or table referenced is incorrect or misspelled.

Disadvantages of Subqueries

Disadvantage Description
Performance Impact Subqueries are often slower than joins.
Hard to Debug Deeply nested subqueries are hard to debug.
Readability Complex subqueries reduce query readability.
Optimizer Issues Oracle Optimizer might fail to apply certain performance improvements when subqueries are involved.


Single Row Subquery in Oracle SQL

A Single Row Subquery is a subquery that returns only one row and one column.


It is typically used in the WHERE or HAVING clause of the outer query to filter results based on a single value.


Characteristics of Single Row Subqueries:

  • They return exactly one row and one column.
  • They are often used with comparison operators, such as:
    • =, >, <,>=, <=, <>

Key Features

Feature Description
Number of Rows Returns exactly 1 row
Columns Returns exactly 1 column
Operators Used =, >, <,>=, <=, <>
Common Use Case To compare a column to a single computed value (e.g., highest salary, average revenue)

Syntax

SELECT column1, column2
FROM table_name
WHERE columnX operator (
    SELECT columnY
    FROM table_name2
    WHERE condition
) ;

Examples

Scenario 1:- Find Employee with the Highest Salary in the Company

SELECT employee_id, first_name, salary
FROM employees
WHERE salary = (
    SELECT MAX (salary)
    FROM employees
) ;

Scenario 2:- Find the Department with the Lowest Budget

SELECT department_id, department_name, budget
FROM departments
WHERE salary = (
    SELECT MIN (budget)
    FROM departments
) ;

Scenario 3:- Find Employee in 'Sales' Department with Highest Commission

SELECT employee_id, first_name, department_id, commission_pct
FROM employees
WHERE department_id = (
    SELECT department_id
    FROM departments
    WHERE department_name = 'Sales'
) AND commission_pct = (
    SELECT MAX (commission_pct)
    FROM employees
    WHERE department_id = (
      SELECT department_id
      FROM departments
      WHERE department_name = 'Sales'
    )
) ;

Scenario 4:- Find Product with the Highest Revenue in 2024

SELECT product_id, product_name, revenue
FROM product_sales
WHERE revenue = (
    SELECT MAX (revenue)
    FROM product_sales
    WHERE sales_year = 2024
) ;

Scenario 5:- Find Manager with the Highest Number of Direct Reports

SELECT manager_id, first_name, department_id
FROM employees
WHERE employee_id = (
    SELECT manager_id
    FROM (
      SELECT manager_id, COUNT (*) AS report_count
      FROM employees
      WHERE manager_id IS NOT NULL
      GROUP BY manager_id
      ORDER BY report_count DESC
    ) WHERE ROWNUM = 1
) ;

Common Errors with Single Row Subqueries

Error Code Error Message Cause Solution
ORA-01427 single-row subquery returns more than one row Subquery returned more than 1 row when used with = Review subquery logic to ensure only 1 row is returned (limit with MAX, MIN, or ROWNUM = 1)
ORA-00932 inconsistent datatypes: expected X got Y Column type in subquery doesn't match outer query Ensure subquery and outer query columns have compatible data types

Advantages of Single Row Subqueries

  • Simple Logic :- Easy to implement for single value lookups.
  • Flexible Use :- Can be used in SELECT, WHERE, and HAVING.
  • Efficient :- If properly indexed, performs well.

Limitations of Single Row Subqueries

  • Only 1 Row Allowed :- Fails if more than 1 row is returned.
  • Performance :- May be slower than JOINs if not optimized.
  • Dependency :- Changes in subquery logic directly impact outer query.

Do's and Don'ts of Single Row Subqueries

Do's Don'ts
Use when you need exactly 1 value Don't use when subquery might return multiple rows
Use functions like MAX, MIN, AVG to ensure 1 row Don’t forget to handle nulls if the subquery might return nothing
Use proper data type matching Don’t over-nest if you can rewrite with a join



Multi-Row Subqueries in Oracle SQL

A Multi-Row Subquery is a subquery that returns more than one row.


Unlike Single Row Subqueries (which return only one row and one column), these subqueries can return multiple rows with a single column.


They are typically used with set operators or multi-row comparison operators, such as:

  • IN, ANY, ALL, EXISTS

Key Features

Feature Description
Number of Rows Returns one or more rows
Columns Typically returns one column, but can return more for EXISTS
Operators Used IN, ANY, ALL, EXISTS
Common Use Case When you need to compare a value against a set of values

Syntax

SELECT column1, column2
FROM table1
WHERE columnX operator(IN, ANY, ALL, EXISTS) (
    SELECT columnY
    FROM table2
    WHERE condition
) ;

Examples

Scenario 1:- list all employees working in departments located in 'New York' or 'Los Angeles'.

SELECT employee_id, first_name, department_id
FROM employees
WHERE department_id IN (
    SELECT department_id
    FROM departments
    WHERE location IN ( 'New York', 'Los Angeles' )
) ;

Scenario 2:- Find all orders placed by VIP customers (customers with a loyalty level of 'Gold' or 'Platinum').

SELECT order_id, customer_id, order_date, total_amount
FROM orders
WHERE customer_id IN (
    SELECT customer_id
    FROM customers
    WHERE loyalty_level IN ( 'New York', 'Los Angeles' )
) ;

Scenario 3:- Find Products Sold in More Than One Region

SELECT product_id, product_name
FROM products
WHERE product_id IN (
    SELECT product_id
    FROM sales
    GROUP BY product_id
    HAVING COUNT ( DISTINCT region) > 1
) ;

Scenario 4:- Find Employees Who Report to More Than One Manager

SELECT employee_id, first_name
FROM employees
WHERE employee_id IN (
    SELECT employee_id
    FROM employee_manager_log
    GROUP BY employee_id
    HAVING COUNT ( DISTINCT manager_id) > 1
) ;

Scenario 5:- Find list of products whose prices were changed more than once in the past year.

SELECT product_id, product_name
FROM products
WHERE product_id IN (
    SELECT product_id
    FROM product_price_history
    WHERE change_date >= ADD_MONTHS (SYSDATE, -12)
    GROUP BY product_id
    HAVING COUNT ( DISTINCT price) > 1
      ) ;

Multi-Row Subquery Operators

Operator Description Use Case
IN Matches any value in the subquery result set Employees in specific departments
ANY Compares a value to any value in the subquery (works with =, >, <, etc.) Find products more expensive than any in a specific category
ALL Compares a value to all values in the subquery (works with =, >, <, etc.) Find employees with salary higher than all in 'Marketing'
EXISTS Checks if the subquery returns any rows (boolean test) Check if a customer has placed any orders

Common Errors with Multi-Row Subqueries

Error Code Error Message Cause Solution
ORA-01427 Single-row subquery returns more than one row Multi-row subquery used with a single-row operator like = Use multi-row operators like IN, ANY, ALL, or EXISTS
ORA-00904 invalid identifier Column in subquery is not recognized Check for typos or missing aliases
ORA-01722 invalid number Data type mismatch between subquery column and outer query column Ensure column types match (number vs. varchar)

Advantages of Multi-Row Subqueries

  • Flexibility :- Handles cases where you need to match against a set of values.
  • Works with Groups :- Works well with aggregated subqueries (like HAVING COUNT)
  • Nesting Power :- Can be nested inside other subqueries for complex logic

Limitations of Multi-Row Subqueries

  • Performance :- Can be slower than JOINs if not properly indexed.
  • Readability :- Complex nested multi-row subqueries can be difficult to understand.
  • Data Type Issues :- Outer and inner query columns must match in data type.

Do’s and Don’ts for Multi-Row Subqueries

Do's Don'ts
Use with IN, ANY, ALL, EXISTS Don’t use with = or other single-row operators
Make sure subquery columns match outer query columns in type Don’t forget to handle null values in subqueries if needed
Use for dynamic filtering based on lookup tables Don’t use if a simple JOIN would work faster



Multiple Column Subquery in Oracle SQL

A Multiple Column Subquery is a subquery that returns more than one column.


It can return one row with multiple columns or multiple rows with multiple columns, depending on the logic.


This is different from single row subqueries (which return only one value) and multiple row subqueries (which typically return one column but many rows).


Key Characteristics

  • Result Set :- Multiple columns (could be single or multiple rows).
  • Comparison Type :- Column-to-column comparison (pairwise).
  • Usage :- Mostly in WHERE, IN, EXISTS, or in FROM (inline views).
  • Operator Support :- Supports (col1, col2) IN syntax for pairwise comparison.
  • Common Use Case :- Comparing two or more columns from a main query to matching columns from a subquery.

Syntax for Multiple Column Subquery

SELECT column1, column2
FROM table1
WHERE (column1, column2) IN (
    SELECT columnA, columnB
    FROM table2
    WHERE condition
) ;

Where Multiple Column Subqueries are Used

  • WHERE :- Matching column pairs like (dept_id, job_id).
  • FROM (Inline View) :- Subqueries returning multiple columns used in a join.
  • EXISTS :- Checking for the existence of rows with matching column pairs.

Examples

Scenario 1:- List employees whose department and job role match an open job posting.

SELECT employee_id, name
FROM employees e
WHERE (e.department_id, e.job_id) IN (
    SELECT department_id, job_id
    FROM job_openings
    WHERE status = 'OPEN'
) ;

Scenario 2:- Find sales orders that match a customer and product combination eligible for a discount.

SELECT order_id, customer_id, product_id, order_date
FROM sales_orders so
WHERE (so.customer_id, so.product_id) IN (
    SELECT customer_id, product_id
    FROM promotions
    WHERE valid_until >= SYSDATE
) ;

Scenario 3:- Find product price changes where the product ID and region match an entry in the new price table.

SELECT product_id, region, old_price, new_price
FROM product_prices p
WHERE (p.product_id, p.region) IN (
    SELECT product_id, region
    FROM regional_price_updates
    WHERE update_date > SYSDATE - 30
) ;

Scenario 4:- Identify employees who have transferred to a new department and new location matching a list of authorized transfers.

SELECT employee_id, name, department_id, location_id
FROM employee_transfers
WHERE (department_id, location_id) IN (
    SELECT department_id, location_id
    FROM approved_transfers
) ;

Scenario 5:- Validate Supplier and Product Combinations.

SELECT supplier_id, product_id, product_name
FROM supplier_products
WHERE (supplier_id, product_id) IN (
    SELECT supplier_id, product_id
    FROM approved_suppliers_products
) ;

Comparison with Single Column Subqueries

Attribute Single Column Subquery Multiple Column Subquery
Returns 1 column Multiple columns
Matches 1 value Combination of values (pairs, triples, etc.)
Operators IN, ANY, ALL, EXISTS IN, EXISTS
Complexity Low Medium to High
Common Example Department IDs (Department ID, Job ID) pairs

Advantages & Disadvantages

Advantages Disadvantages
Directly handles pairwise (or multi-column) comparisons May have performance overhead when subquery returns many rows
Reduces need for multiple JOINs for pair checking Not all Oracle tools and ORMs easily handle multi-column subqueries
Works well for historical comparisons Syntax can get complex for more than 2 columns

Common Errors of Multiple Column Subqueries

Error Code Cause Solution
ORA-00913 Too many values Ensure subquery returns the exact number of columns being compared
ORA-00904 Invalid column name Check column names are correct
ORA-01427 Single-row subquery returning too many rows Use pair comparison with (col1, col2) format

Limitations for Multiple Column Subqueries

  • Column Pair Limit :- Limited to reasonable number of columns (pairs/triplets manageable, larger gets messy).
  • Performance :- Can degrade if the subquery returns too many rows without proper indexing.
  • Readability :- Complex subqueries with many columns are harder to read and debug.




Correlated Subquery in Oracle SQL

A Correlated Subquery is a type of subquery that refers to a column from the outer query.


This means that the subquery is executed once for each row processed by the outer query.


Because of this dependency, the subquery cannot be executed independently.

Key Features

  • Dependency :- Subquery depends on values from the outer query.
  • Execution :- Subquery runs once for each row in the outer query.
  • Performance :- Generally slower than standard subqueries.
  • Use Case :- Row-by-row comparisons (like "find the maximum order date for each customer")

Syntax

SELECT column1, column2
FROM table1 outer_alias
WHERE columnX = (
    SELECT columnY
    FROM table2
    WHERE table2.related_column = outer_alias.outer_column
) ;

Examples

Scenario 1:- Find employees whose salary is higher than the average salary in their own department.

SELECT e.employee_id, e.first_name, e.salary, e.department_id
FROM employees e
WHERE e.salary > (
    SELECT AVG (salary)
    FROM employees sub
    WHERE sub.department_id = e.department_id
) ;

Scenario 2:- Find Products That Have Higher Price Than Category Average (Retail).

SELECT p.product_id, p.product_name, p.price, p.category_id
FROM products p
WHERE p.price > (
    SELECT AVG (price)
    FROM products sub
    WHERE sub.category_id = p.category_id
) ;

Scenario 3:- Find employees who earn more than the average salary for their department.

SELECT e.employee_id, e.first_name, e.salary, e.department_id
FROM employees e
WHERE e.salary > (
    SELECT AVG (salary)
    FROM employees sub
    WHERE sub.department_id = e.department_id
) ;

Scenario 4:- Identify Most Recent Orders per Customer (E-commerce).

SELECT o.order_id, o.customer_id, o.order_date
FROM orders o
WHERE o.order_date = (
    SELECT MAX (order_date)
    FROM orders sub
    WHERE sub.customer_id = o.customer_id
) ;

Scenario 5:- Find the most senior employee (earliest hire date) in each department.

SELECT e.employee_id, e.first_name, e.department_id, e.hire_date
FROM employees e
WHERE e.hire_date = (
    SELECT MIN (hire_date)
    FROM employees sub
    WHERE sub.department_id = e.department_id
      ) ;

Scenario 6:- Identify customers whose orders are higher than their personal average order value.

SELECT o.order_id, o.customer_id, o.total_amount
FROM orders o
WHERE o.total_amount > (
    SELECT AVG (total_amount)
    FROM orders sub
    WHERE sub.customer_id = o.customer_id
      ) ;

Common Errors in Correlated Subqueries

Error Code Error Message Cause Solution
ORA-00904 Invalid identifier Outer query column is not accessible in subquery Make sure outer query table alias is correctly referenced
ORA-01427 Single-row subquery returns more than one row Using single-row operator (=) with subquery returning multiple rows Review subquery logic; use IN if necessary
ORA-00942 Table or view does not exist Subquery references invalid table/view Double-check table names and schema

Advantages of Correlated Subqueries

  • Row-wise Comparison :- Great for comparing a row against an aggregated or calculated value specific to that row.
  • Flexibility :- Enables dynamic calculations based on the outer row.
  • Complex Conditions :- Good for finding "most recent", "earliest", "highest" type of queries within groups.

Limitations of Correlated Subqueries

  • Performance :- Executes the subquery once per outer row, which can be slow for large datasets.
  • Readability :- More difficult to read and debug compared to JOIN-based solutions.
  • Index Dependency :- Performance relies heavily on proper indexing of join columns.

Do’s and Don’ts of Correlated Subqueries

Do's Don'ts
Use for row-specific comparisons Don’t use for simple lookups where a JOIN would work better
Optimize with indexes on subquery columns Don’t use if performance is critical on large datasets
Use clear table aliases in both queries Don’t forget to correlate properly (outer query column in subquery)

Correlated vs Non-Correlated Subqueries

Feature Correlated Subquery Non-Correlated Subquery
Dependency Depends on outer query columns Independent of outer query
Execution Runs once per outer query row Runs once per entire query
Performance Generally slower Generally faster
Use Case Row-specific calculations Static filtering using unrelated table

Performance Comparison Example

Business Case

Requirement:- Find all orders where the order amount is greater than the average order amount for the same customer.


Approach 1: Using Correlated Subquery

EXPLAIN PLAN FOR SELECT o.order_id, o.customer_id, o.order_amount
FROM orders o
WHERE o.order_amount > (
    SELECT AVG (sub.order_amount)
    FROM orders sub
    WHERE sub.customer_id = o.customer_id
      ) ;

Explanation:

  • The subquery calculates the average order amount per customer.
  • This subquery runs once for each order in the outer query (row-by-row correlation).
  • On a large dataset, this is highly inefficient.


Approach 2: Using Inline View with JOIN (Better Option)

EXPLAIN PLAN FOR SELECT o.order_id, o.customer_id, o.order_amount
FROM orders o
JOIN (
    SELECT AVG (order_amount) AS avg_order_amount
    FROM orders
    GROUP BY customer_id
      )avg_orders
      ON o.customer_id = avg_orders.customer_id
      WHERE o.order_amount > avg_orders.avg_order_amount ;

Explanation:

  • The average order amount per customer is pre-calculated using an inline view.
  • Then the outer query joins each order to its customer’s average order amount.
  • This removes the row-by-row subquery execution, making it much faster.


Compare Performance Using DBMS_XPLAN.DISPLAY

SELECT * FROM TABLE (DBMS_XPLAN.DISPLAY) ;

Sample Output - Correlated Subquery (Bad Plan Example)

Id Operation Name Rows Cost
0 SELECT STATEMENT 100K 150K
1 TABLE ACCESS FULL ORDERS 100K 150K
2 FILTER
3 SORT AGGREGATE 1
4 TABLE ACCESS FULL ORDERS 100K 150K

Explanation:

  • TABLE ACCESS FULL (Line 1): Full table scan of orders.
  • TABLE ACCESS FULL inside the correlated subquery (Line 4) is executed once for each row of the outer query — a serious performance hit.


Sample Output - Inline View with JOIN (Good Plan Example)

Id Operation Name Rows Cost
0 SELECT STATEMENT 100K 25K
1 HASH JOIN 100K 25K
2 VIEW 10K 1K
3 HASH GROUP BY 10K 1K
4 TABLE ACCESS FULL ORDERS 100K 15K
5 TABLE ACCESS FULL ORDERS 100K 15K

Explanation:

  • HASH JOIN (Line 1) efficiently joins the orders to the pre-aggregated average amounts.
  • Only one full scan of orders is needed (Line 4) to precompute averages.
  • Overall cost is dramatically lower.


Key Takeaways

Metric Correlated Subquery Inline View with Join
Execution Time Slow (Runs Subquery per Row) Fast (Precompute Once)
Table Scans Multiple Single
Plan Cost High Low
Scalability Poor Good
Use Case Rare cases (row-specific checks) Recommended for aggregated comparisons


Inline View in Oracle SQL

An Inline View is a subquery that appears in the FROM clause of a SELECT statement.


It acts as a temporary view that exists only for the duration of the query.


Purpose of Inline View

  • Used to simplify complex queries by breaking them into manageable subqueries.
  • Enables pre-aggregation (like totals or averages) before joining with other tables.
  • Allows filtering or sorting on aggregated or derived data.

Key Features of Inline Views

  • Location :- Defined inside the FROM clause.
  • Temporary :- Exists only for the current query execution.
  • Alias Required :- Must always have an alias to reference it.
  • Optimization :- Can help Oracle’s optimizer choose better execution plans.
  • Nested Queries :- Can contain aggregations, joins, or even other inline views.

Syntax of Inline View

SELECT columns
FROM (
    SELECT columns
    FROM table_name
    WHERE conditions
) inline_view_alias WHERE outer_conditions ;

Benefits of Inline Views

Benfit Explanation
Query Simplification Breaks down complex logic into smaller, manageable steps.
Pre-aggregation Allows aggregation (SUM, AVG, etc.) in the inline view before final filtering or joining.
Performance In some cases, pre-aggregating data in inline views can improve performance.
Flexibility Can combine multiple tables, filters, or calculations inside the inline view.
Temporary No need to create physical views in the database — it's a one-time use view.

Common Use Cases of Inline Views

Use Case Example
Aggregation Calculate total sales per region inside an inline view, then filter regions with sales > 1M.
Ranking Data Use ROW_NUMBER() or RANK() inside an inline view to filter top N rows.
Complex Joins Pre-join two tables in an inline view before joining to a third table.
Pre-filtering Filter data inside an inline view to reduce rows before outer joins.
Subqueries with Aggregates Aggregate by customer, then join back to orders for detailed analysis.

Scenario 1:- Get departments where the average salary exceeds $5000.

SELECT department_id, avg_salary
FROM (
    SELECT AVG (salary) AS avg_salary
    FROM employees
    GROUP BY department_id
) dept_avg WHERE avg_salary > 5000 ;

Scenario 2:- Find the top 2 orders per customer based on order amount.

SELECT customer_id, order_id, order_amount
FROM (
    SELECT customer_id, order_id, order_amount,
      ROW_NUMBER () OVER ( PARTITION BY customer_id ORDER BY order_amount DESC ) AS Rank
    FROM orders
) ranked_orders
WHERE rank <= 2 ;

When to Use Inline Views

Use inline views when:

  • Pre-calculating aggregates.
  • Performing ranking or window functions.
  • Simplifying deeply nested subqueries.
  • Filtering data before final joins.

Avoid inline views when:

  • A simple join or filter can achieve the same result.
  • The same logic is reusable (consider a physical view instead).
  • Inline view returns too much unnecessary data (filter as early as possible).

Scenario 3:- Retrieve the total sales per product category where the total sales exceed $50,000.

SELECT c.category_id, c.category_name, sales_summary.total_sales
FROM (
    SELECT p.category_id, SUM (s.sale_amount)AS total_sales
    FROM sales s
    JOIN products p ON s.product_id = p.product_id
    GROUP BY p.category_id
) sales_summary
JOIN categories c ON sales_summary.category_id = c.category_id
WHERE sales_summary.total_sales > 50000 ;

Scenario 4:- Find the top 2 highest-paid employees in each department.

SELECT department_id, employee_id, salary
FROM (
    SELECT employee_id, department_id, salary,
      ROW_NUMBER () OVER ( PARTITION BY department_id ORDER BY salary DESC ) AS Rank
    FROM employees
) ranked_employees
WHERE rank <= 2 ;

Scenario 5:- Join orders with customers, but only include active orders placed in the last 30 days.

SELECT c.customer_id, c.customer_name, o.order_id, o.order_date, o.order_status
FROM (
    SELECT order_id, customer_id, order_date, order_status
    FROM orders
    WHERE order_status = 'Active' AND order_date >= SYSDATE - 30
) o
JOIN customers c ON o.customer_id = c.customer_id ;

Scenario 6:- For each product with inventory below the reorder threshold, calculate how many items need to be ordered.

SELECT p.product_id, p.product_name, inventory_summary.current_stock, p.reorder_level,
(p.reorder_level - inventory_summary.current_stock) AS order_quantity
FROM (
    SELECT product_id, SUM (current_stock) AS current_stock
    FROM inventory
    GROUP BY product_id
) inventory_summary
JOIN products p ON inventory_summary.product_id = p.product_id
WHERE inventory_summary.current_stock < p.reorder_level ;

Scenario 7:- Find the total revenue and total number of orders for each customer who placed orders this year.

SELECT customer_orders.customer_id,
customer_orders.total_orders,
customer_revenue.total_revenue
FROM (
    SELECT customer_id, COUNT (order_id) AS total_orders
    FROM orders
    WHERE EXTRACT ( YEAR FROM order_date ) = EXTRACT ( YEAR FROM SYSDATE )
    GROUP BY customer_id
) customer_orders
JOIN ( SELECT customer_id, SUM (order_amount) AS total_revenue
FROM orders
WHERE EXTRACT ( YEAR FROM order_date ) = EXTRACT ( YEAR FROM SYSDATE )
GROUP BY customer_id ) customer_revenue
ON customer_orders.customer_id = customer_revenue.customer_id ;

Inline View vs Subquery

Criteria Inline View Subquery (Non-Inline)
Location From Clause SELECT, WHERE, HAVING
Scope Temporary table within query Conditional filtering or value fetching
Alias Required Optional
Use Case Pre-aggregating, sorting, or filtering before main query Conditions or value lookups for each row
Optimization More optimizer-friendly in complex queries May lead to performance issues if not designed well

Common Errors with Inline Views

Error Code Cause Solution
ORA-00904 Column not found in outer query (forgot alias) Use the correct alias.column_name reference.
ORA-00942 Table or view does not exist Ensure inline view query is correct and all tables exist.
ORA-00933 SQL command not properly ended Check for missing parentheses or misplaced commas.
ORA-00918 Column ambiguously defined Use aliases to prevent column name conflicts.
ORA-00979 Not a GROUP BY expression If using aggregation, ensure non-aggregated columns are in GROUP BY.

Do's and Don'ts for Inline Views

Do's Don'ts
Use aliases for the inline view and its columns. Don’t forget the inline view alias — it's mandatory.
Use inline views to pre-aggregate or pre-filter data. Don’t over-nest too many inline views — it hurts readability and performance.
Optimize inline views by selecting only necessary columns. Don’t select unnecessary columns inside the inline view.
Use inline views to simplify complex joins. Avoid using inline views to just hide bad logic — use them purposefully.
Use EXPLAIN PLAN to review performance impact. Don’t assume inline views always improve performance — test your queries.


Correlated Subquery in Oracle SQL

A correlated subquery is a subquery that refers to a column from the outer query (parent query).


This type of subquery is evaluated once per row processed by the outer query — making it row-by-row dependent.


Key Features of Correlated Subqueries

  • Row Dependency :- Each subquery execution depends on data from the current row being processed in the outer query.
  • Performance Impact :- Due to row-by-row execution, correlated subqueries tend to be slower than joins or non-correlated subqueries.
  • Use Case :- Useful when comparing each row to a set of data derived from the same table or related tables.
  • Typical Use :- Exists in WHERE, HAVING, or SELECT clauses.

Syntax of Correlated Subquery

SELECT column1, column2, ...
FROM outer_table o
WHERE columnX (operator) (
    SELECT columnY
    FROM inner_table i
    WHERE i.related_column = o.related_column
) ;

  • outer_table: Parent query table
  • inner_table: Subquery table (refers to outer table columns)

Scenario 1:- Find Employees Earning More Than the Average Salary of Their Own Department.

SELECT e.employee_id, e.department_id, e.salary
FROM employees e
WHERE e.salary > (
    SELECT AVG (salary) FROM employees sub
    WHERE sub.department_id = e.department_id
) ;

Scenario 2:- Find Orders With Total Amount Greater Than the Customer's Average Order Amount.

SELECT o.order_id, o.customer_id, o.order_amount
FROM orders o
WHERE o.order_amount > (
    SELECT AVG (order_amount) FROM orders sub
    WHERE sub.customer_id = o.customer_id
) ;

Scenario 3:- Find Products Priced Higher Than The Category’s Average Price.

SELECT p.product_id, p.category_id, p.price
FROM products p
WHERE p.price > (
    SELECT AVG (price) FROM products sub
    WHERE sub.category_id = p.category_id
) ;

Scenario 4:- Retrieve Customers Who Placed Orders After Their First Order Date.

SELECT c.customer_id, c.customer_name
FROM customers c
WHERE EXISTS (
    SELECT orders o
    WHERE o.customer_id = c.customer_id
    AND o.order_date > (
      SELECT MIN (order_date)
      FROM orders sub WHERE sub.customer_id = o.customer_id
    )
) ;

Scenario 5:- Identify Employees Earning Above Their Department's Median Salary.

SELECT e.employee_id, e.department_id, e.salary
FROM employees e
WHERE e.salary > (
    SELECT MEDIAN (salary)
    FROM employees sub
    WHERE sub.department_id = e.department_id
) ;

Scenario 6:- Compare Orders Against Maximum Order Amount Per Product.

SELECT o.order_id, o.product_id, o.order_amount
FROM orders o
WHERE o.order_amount = (
    SELECT MAX (order_amount)
    FROM orders sub
    WHERE sub.product_id = o.product_id
) ;

Limitations of Correlated Subqueries

Limitation Description
Performance They can be slow on large tables since they execute once per row in the outer query.
Index Dependence If properly indexed columns are missing, performance degrades further.
Limited Optimization Oracle's optimizer has fewer rewrite options compared to joins or inline views.
Complex Logic Writing and debugging becomes complex with multi-level correlations.

Common Errors in Correlated Subqueries

Error Code Description Cause Solution
ORA-00904 Invalid Identifier Outer query column referenced in subquery may be misspelled or not qualified correctly.
ORA-01427 Single-row subquery returns more than one row Subquery expected to return only one row, but it returned multiple. Use IN or EXISTS instead of = where applicable.
ORA-01722 Invalid Number Column type mismatch when comparing numeric and string. Verify column data types in the outer and inner queries

Do’s and Don’ts of Correlated Subqueries

Do's Don'ts
Use correlated subqueries for row-by-row comparisons where no alternative exists Don’t use correlated subqueries for simple joins — use JOINs instead
Ensure indexes exist on columns in the subquery filter Don’t forget to test performance on large datasets
Use EXISTS for existence checks to improve performance Don’t overuse them inside highly nested queries
Use EXPLAIN PLAN to check query cost Don’t ignore rewriting to INLINE VIEWS if performance is critical


Nested Subquery in Oracle SQL

A Nested Subquery (also called Inner Subquery) is a subquery placed inside another query (usually inside a WHERE, FROM, or SELECT clause).


This is the most common type of subquery where one query is nested inside another to filter, compute, or derive data.


Key Features of Nested Subqueries

  • Nesting Level :- Can have single-level or multi-level nesting (nested inside another subquery).
  • Independence :- Inner subquery can run independently of the outer query (in most cases).
  • Common Use :- Typically used for filtering, conditional checks, and dynamic data retrieval.
  • Location :- Can appear in WHERE, HAVING, FROM, SELECT clauses.
  • Performance :- If not optimized, they can cause performance issues especially in multi-level nested scenarios.

Syntax of Nested Subquery

SELECT column_list
FROM table1
WHERE column1 = (
    SELECT column2
    FROM table2
    WHERE condition
) ;

Scenario 1:- Find Employees with Maximum Salary.

SELECT employee_id, name, salary
FROM employees
WHERE salary = (
    SELECT MAX (salary) FROM employees
) ;

Scenario 2:- Find Customers Who Have Placed Orders.

SELECT customer_id, customer_name
FROM customers
WHERE customer_id IN (
    SELECT customer_id
    FROM orders
) ;

Scenario 3:- Find Products That Cost More Than The Average Product Price.

SELECT product_id, name, price
FROM products
WHERE p.price > (
    SELECT AVG (price) FROM products
) ;

Scenario 4:- Find Employees in Departments With Above-Average Salaries.

SELECT employee_id, department_id, salary
FROM employees
WHERE salary > (
    SELECT AVG (salary)
    FROM employees
    WHERE department_id = employees.department_id
) ;

Scenario 5:- Find Orders Placed by VIP Customers.

SELECT order_id, customer_id, order_date
FROM orders
WHERE customer_id IN (
    SELECT customer_id
    FROM customers
    WHERE status = 'VIP'
    AND customer_id IN (
      SELECT DISTINCT customer_id
      FROM orders
      WHERE order_date > ADD_MONTHS(SYSDATE, -12)
    )
) ;

Scenario 6:- ( Subquery in SELECT Clause ) Retrieve each employee’s department name using a subquery in the SELECT clause.

SELECT employee_id
    ( SELECT department_name
    FROM departments
    WHERE department_id = e.department_id ) AS department_name
FROM employees e ;

Scenario 7:- ( Subquery in FROM Clause ) Retrieve departments where the total salary of employees exceeds 50,000 using a subquery in the FROM clause.

SELECT department_id, total_salary
FROM (
    SELECT department_id, SUM (salary) AS total_salary
    FROM employees
    GROUP BY department_id
) dept_salary
WHERE total_salary > 50000 ;

Advantages & Disadvantages

Advantage Disadvantage
Modular way to break down logic Slower on large data sets compared to joins
Great for dynamic filters & calculations Can get complex & hard to debug
Works well for hierarchical or multi-level filters Nested queries may execute multiple times (in unoptimized cases)

Common Errors & Solutions for Nested Subqueries

Error Code Cause Solution
ORA-01427 Subquery returns more than 1 row in a single-row context Use IN, ANY, or EXISTS instead of =.
ORA-00904 Column name not found in subquery Double-check column names & aliases.
ORA-00933 SQL command not properly ended Misplaced parenthesis or wrong syntax

Do’s and Don’ts for Nested Subqueries

Do's Don'ts
Use for multi-level filtering when required Don’t over-nest (keep maximum nesting to 2-3 levels)
Use EXISTS for better performance in existence checks Don’t use nested subqueries if the logic can be rewritten using JOINs
Ensure subqueries return the correct number of columns & rows Avoid deeply nested queries unless absolutely necessary
Use inline views (subquery in FROM) for derived aggregates Avoid subqueries with unindexed columns in large datasets


Scalar Subquery in Oracle SQL

A Scalar Subquery is a type of **subquery that returns exactly one single value (one row, one column).


It can be used in places where a single value (or expression) is expected — such as:

  • In the SELECT list (for computed columns)
  • In WHERE, HAVING, ORDER BY clauses (for comparisons)

Key Characteristics of Scalar Subqueries

  • Returns :- Exactly one value (one row, one column).
  • Common Usage :- Used in SELECT, WHERE, HAVING, ORDER BY, etc.
  • Failure on Multi-Row Output :- If it returns more than one row, Oracle raises ORA-01427: single-row subquery returns more than one row.
  • Flexibility :- Often used to dynamically compute column values or filter conditions based on other tables.
  • Performance :- Faster than correlated subqueries in most cases, but still should be used carefully for large datasets.

Syntax

In SELECT Clause

SELECT employee_id,
    ( SELECT department_name
    FROM departments
    WHERE department_id = e.department_id ) AS department_name
FROM employees e ;

In WHERE Clause

SELECT employee_id, salary
FROM employees
WHERE salary > (
    SELECT AVG (salary)
    FROM employees
) ;

When to Use Scalar Subqueries

  • To dynamically fetch a related value in a SELECT query.
  • To perform comparisons with dynamically calculated values (in WHERE, HAVING).
  • To replace a JOIN if you only need one value and don't want row duplication (but with caution).

Where Scalar Subqueries Can Be Used

  • SELECT :- To fetch a related or computed column.
  • WHERE :- To compare with a dynamic value.
  • HAVING :- To filter aggregated data with a subquery result.
  • ORDER BY :- To sort using a dynamically computed value.

Scenario 1:- Fetch Each Employee's Department Name (Scalar in SELECT).

SELECT e.employee_id, e.name,
    ( SELECT d.department_name
    FROM departments d
    WHERE d.department_id = e.department_id ) AS department_name
FROM employees e ;

Scenario 2:- Find Employees with Above-Average Salary (Scalar in WHERE).

SELECT employee_id, name, salary
FROM employees
WHERE salary > (
    SELECT AVG (salary)
    FROM employees
) ;

Scenario 3:- Get Customer Order Count in Each Row (Scalar in SELECT)

SELECT customer_id, customer_name,
    ( SELECT COUNT (*)
    FROM orders o
    WHERE o.customer_id = c.customer_id ) AS order_count
FROM customers c ;

Scenario 4:- Compare Employee Salary With CEO's Salary (Scalar in WHERE).

SELECT employee_id, name, salary
FROM employees
WHERE salary < (
    SELECT salary
    FROM employees
    WHERE job_title = 'CEO'
) ;

Scenario 5:- Order Products by Most Recent Order Date (Scalar in ORDER BY)s.

SELECT p.product_id, p.product_name
FROM products p
ORDER BY (
    SELECT MAX (order_date)
    FROM orders o
    WHERE o.product_id = p.product_id ) DESC ;

Advantages & Disadvantages

Advantage Disadvantage
Easy way to dynamically fetch data in non-join cases Can be slower than joins for large datasets
Great for single value lookups If the subquery returns more than 1 row, it throws an error (ORA-01427)
Works well for dynamic column values in SELECT Can cause performance bottlenecks if unindexed columns are used

Common Errors & Solutions

Error Code Cause Solution
ORA-01427 Subquery returned more than 1 row Check logic, ensure proper filters for single row.
ORA-00904 Column not found Double-check column names in subquery.
ORA-00933 SQL command not properly ended Misplaced brackets or wrong nesting syntax

Do’s and Don’ts for Nested Subqueries

Do's Don'ts
Use scalar subqueries for single value lookups Avoid for large datasets where JOINs are more efficient
Ensure subquery returns only 1 row Don’t use scalar subqueries if you need multiple rows
Use indexes on columns in subquery filters Don’t use deeply nested scalar subqueries — it’s costly
Check using EXPLAIN PLAN Don’t forget to handle cases where subquery returns NULL
