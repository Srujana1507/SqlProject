Oracle SQL

  • Oracle SQL (Structured Query Language) is the standard language used to interact with Oracle Database.
  • It enables users to perform a wide variety of operations, such as querying data, modifying records, and managing database objects.
  • It's a dialect of the standard SQL language, meaning it shares many commonalities with SQL used in other database systems.
  • However, Oracle SQL also includes unique extensions and features specific to the Oracle database platform.
  • Oracle SQL is foundational for anyone working in Oracle-based environments, enabling robust data manipulation and querying.
  • Understanding Oracle SQL opens doors to advanced features like partitioning, parallel execution, and in-memory capabilities.
  • The combination of SQL and PL/SQL makes Oracle a powerhouse for data-driven applications.

Data Type in Oracle SQL

What is Data Type?

A Data Type defines the type of data that can be stored in a column, variable, or parameter.


  • It specifies the characteristics of the data, such as its size, format, and allowed operations.
  • Data types ensure that only valid and compatible data is stored in the database, thus maintaining data integrity.

Purpose of Data Types

  • Consistency:- Ensures the data stored in the database adheres to the defined format and constraints.
  • Validation:- Prevents invalid data entries by enforcing rules (e.g., storing text in a numeric column is not allowed).
  • Optimization:- Helps optimize storage and query performance by allocating appropriate space and resources.
  • Ease of Manipulation:- Facilitates efficient data retrieval, comparisons, and transformations.
  • Memory Efficiency:- Allocates storage based on the size and type of data.

Oracle SQL Data Types

Data Type Description Purpose Limitations
CHAR(size) Fixed-length character string. Pads extra spaces if the string is shorter than the defined size. To store text or alphanumeric data of fixed length. Maximum size is 2,000 bytes. Inefficient for storing variable-length data.
VARCHAR2(size) Variable-length character string. The size specifies the maximum length (in bytes or characters). To store text or alphanumeric data of varying lengths. Maximum length is 32,767 bytes in PL/SQL and 4,000 bytes in SQL.
CLOB Character Large Object, used to store large text data up to 4 GB. To store large text documents, XML, or JSON data. Slower operations compared to standard text data types; requires LOB-specific functions.
NUMBER(p,s) Numeric data type with precision (p) and scale (s). Precision is the total number of digits, and scale is the number of digits after the decimal. Suitable for integers, decimals, and floating-point values. Precision and scale must be defined for specific applications.
FLOAT(p) Floating-point number with a precision of up to p. To store approximate numeric values. Precision and accuracy may vary depending on the hardware.
BINARY_FLOAT A single-precision floating-point number (32-bit). To store approximate numeric values with low precision. Lower precision and accuracy than BINARY_DOUBLE.
BINARY_DOUBLE A double-precision floating-point number (64-bit). To store approximate numeric values with high precision. Consumes more storage than BINARY_FLOAT.
DATE Stores date and time values (up to seconds) in the format DD-MON-YYYY HH24:MI:SS. Useful for applications requiring date and time storage.Useful for applications requiring date and time storage. Cannot store fractions of seconds; limited to a range from 4712 BC to 9999 AD.
TIMESTAMP(n) Extends DATE by adding fractional seconds (up to n, where n is 0 to 9). To store high-precision date and time values. Fractional seconds increase storage size.
TIMESTAMP WITH TIME ZONE Extends TIMESTAMP by including a time zone offset. To store date and time values with time zone information. Time zone offsets need to be managed; increases storage requirements.
INTERVAL YEAR TO MONTH Represents a period in years and months. Useful for tracking durations or differences in months. Cannot represent finer granularity like days or seconds.
INTERVAL DAY TO SECOND Represents a time interval in days, hours, minutes, seconds, and fractional seconds. To measure precise differences between timestamps. Limited to the precision specified; cannot handle larger time intervals.
RAW(size) Stores variable-length binary data in hexadecimal format. To store binary data that does not require processing. Maximum size is 2,000 bytes; cannot perform arithmetic or character functions.
BLOB Binary Large Object, used to store large binary data up to 4 GB. Ideal for storing multimedia files (images, videos). Similar limitations as CLOB; requires more disk space.
LONG Stores variable-length character data up to 2 GB. Historically used for large text storage. Deprecated; cannot be indexed or used in functions like WHERE clauses. Use CLOB instead.
ROWID Represents a unique address for a row in a table. Useful for identifying rows directly in internal operations. Cannot be relied upon for long-term or logical row identification.
UROWID Extends ROWID to include addresses for rows stored in index-organized tables. Used in distributed database systems. Limited to specific use cases, primarily advanced database applications.
XMLType Used for storing XML data. Ideal for applications working with structured XML documents. Complex to query and process; requires additional XML functions and storage space.
BOOLEAN (PL/SQL) Stores logical values (TRUE, FALSE, or NULL). Common in procedural logic within PL/SQL. Not supported in SQL directly; limited to PL/SQL contexts.


Points to Remember

  • For character and binary data types, Oracle recommends using VARCHAR2 and RAW over CHAR and LONG for efficiency.
  • Use modern types like CLOB, BLOB, and XMLType instead of legacy types like LONG.
  • Always choose the data type based on the specific requirements of precision, storage, and performance.
  • Properly define the size and scale to avoid storage and performance issues.
  • Always choose a data type based on expected data and business requirements.
  • Avoid using legacy types (e.g., LONG) in new designs.
  • Define size (size, precision, scale) to optimize storage and prevent errors.

Languages Within Oracle SQL

Oracle SQL can be broadly classified into the following four SQL language components.


Language Component Purpose Key Commands
Data Query Language (DQL) Retrieve data from the database SELECT
Data Manipulation Language (DML) Used to modify data in the database INSERT, UPDATE, DELETE
Data Definition Language (DDL) Used for creating and modifying database objects like tables, indexes, and views. CREATE, ALTER, DROP, TRUNCATE
Data Control Language (DCL) Manage user access and permissions GRANT, REVOKE
Transaction Control Language (TCL) Manage transactions in the database COMMIT, ROLLBACK, SAVEPOINT


1. Data Query Language (DQL):

DML statements can range from simple queries to complex multi-clause commands. Here are the components

  • Basic Purpose : Used to fetch and query data from the database.
  • Key Command: SELECT
components Purpose Example
Expressions Used to calculate or derive values. SELECT Price * Quantity AS TotalCost FROM ORDERS;
Clauses Specify the purpose or limits of a statement, like WHERE, GROUP BY, or ORDER BY. SELECT ProductID, SUM(Sales) FROM SALES GROUP BY ProductID ORDER BY SUM(Sales) DESC;
Predicates Define conditions for filtering rows. SELECT CustomerID,customer_name FROM CUSTOMER WHERE Age > 30 AND City = 'Chicago'
Logical Connectives Combine multiple conditions (e.g., AND, OR, NOT). SELECT CustomerID,customer_name FROM CUSTOMER WHERE City = 'New York' OR City = 'Los Angeles'
Aggregate Functions Perform calculations across rows (e.g., SUM, AVG, COUNT). SELECT COUNT(*) AS TotalCustomers FROM CUSTOMER WHERE City = 'New York';
Subqueries Queries embedded within other queries. SELECT FirstName, LastName FROM CUSTOMER WHERE CustomerID IN (SELECT CustomerID FROM ORDERS WHERE Total > 500);

2. Data Definition Language (DDL):

Purpose:

Data Definition Language (DDL) is a part of SQL used to create, modify, and delete database structures. It defines what the database will look like and how it will store information.

  • It deals with the basic elements of a database, like tables, views, schemas, and catalogs.
  • Creates tables, databases, and other structures.
  • Changes or deletes existing database structures.
  • DDL commands define how data is stored and organized within a relational database.

Key Commands:

  • CREATE : Used to create new tables, schemas, views, or databases.
    CREATE TABLE Students (ID INT, Name VARCHAR(100), Age INT);
  • ALTER : Used to modify the structure of an existing table (e.g., add, remove, rename or change data type columns).
    ALTER TABLE Students ADD COLUMN Grade CHAR(1);
  • DROP: Used to delete tables, schemas, or databases when they are no longer needed.
    DROP TABLE Students;

    3. Data Manipulation Language (DML)

    Purpose :

    Manipulation Language (DML) is a subset of SQL used to manage and manipulate the actual data stored in a database.

    • DML is used to handle the actual data inside the database.
    • It helps you add, update, delete, or retrieve information.
    • Unlike DDL (Data Definition Language), which defines database structure, DML focuses on the contents within those structures.

    Why is DML Important in SQL?

    • DML bridges the gap between data storage and real-world application requirements.
    • It allows for the dynamic and interactive management of data, which is crucial for businesses, applications, and decision-making processes.

    Key Commands :

    • INSERT : Adds new rows of data to a table.
      INSERT INTO CUSTOMER (CustomerID, FirstName, LastName, City) VALUES (101, 'Yash', 'Man', 'New York');
    • UPDATE :Modifies existing data in a table.
      UPDATE CUSTOMER SET City = 'Los Angeles' WHERE CustomerID = 101;
    • DELETE :Removes specific rows of data from a table based on a condition.
      DELETE FROM CUSTOMER WHERE CustomerID = 101;
    • SELECT : Retrieves data from one or more tables. It is also subset of DQL.
      SELECT FirstName, LastName, City FROM CUSTOMER WHERE City = 'New York';

    Best Practices to Write DML Statements:

    • Break Down Complex Queries - Analyze and test components of complex queries step by step.
    • Use Conditions (WHERE) Thoughtfully - Prevent unintended data manipulation by always specifying conditions where needed.
    • Test Queries on Sample Data - Run queries on a small dataset before applying them to the entire database.
    • Comment Your Code - Use comments to explain logic for future reference.

    Note :Avoid Modifying Data Directly. Always take a backup before running UPDATE or DELETE commands.


    Importance of DML:


    • Data Interaction: Provides mechanisms to interact directly with data stored in relational databases.
    • Fine-Tuned Control: Enables precise control over what data to retrieve, update, or delete.
    • Dynamic Data Handling: Essential for applications that require real-time data updates and retrieval.

    4. Data Control Language (DCL)

    Data Control Language (DCL) is a subset of SQL that focuses on managing and securing access to the database and ensuring that database operations occur reliably. DCL commands are used to control permissions, manage transactions, and safeguard data integrity.


    DCL Commands:
    Command Purpose Usage Example
    GRANT Assigns specific permissions or privileges to users or roles. Depends on user and depatment GRANT SELECT, INSERT ON Employees TO User1;
    REVOKE Removes previously granted permissions from users or roles. Depends on user and depatment REVOKE INSERT ON Employees FROM User1;

    Data Integrity and Security with DCL

    Preventing Data Corruption

    • SQL transactions ensure that operations are logged and can be rolled back in case of errors.
    • Logging minimizes risks during failures, as incomplete transactions can be undone.

    Managing Multi-User Environments

    • DCL restricts simultaneous conflicting operations by isolating user actions.
    • Example Problems Addressed:
      • Lost Updates: When one user's changes overwrite another's without knowledge.
      • Dirty Reads: When a user reads uncommitted changes made by another user.
      • Inconsistent Data: When changes are partially visible to other users.

    What is User Role?

    • user roles - are a way to group and manage permissions for multiple users within a database system. Instead of assigning permissions individually to each user, roles simplify the process by allowing database administrators to assign permissions to roles, and then assign those roles to users.
    • Authentication - Ensures that only authorized users can access the database.
    • Authorization - Controls what actions an authenticated user can perform.

    Advantages of Roles:

    • Centralized Access Control - Simplifies permission management by grouping users with similar access requirements.
    • Enhanced Security - Avoids granting excessive permissions directly to users.
    • Scalability - Easily add or remove users from a role as team compositions change.

    User Roles in few SQL Systems

      1. SQL Server
      • Predefined roles - db_owner, db_reader, db_writer.
      • Custom roles - Supported.
      2. Oracle
      • Supports roles with the CREATE ROLE command.
      • Example predefined roles: CONNECT, RESOURCE, DBA.
      3. PostgreSQL
      • Combines roles and users. Roles can log in if given login privileges.
      • Uses GRANT and REVOKE for role management.
      4. MySQL
      • Introduced roles in version 8.0.
      • Roles can be created, granted privileges, and assigned to users.
      5. MongoDB
      • Role-based access control (RBAC) system with built-in roles like read, readWrite, and custom roles.

    Advanced Features of DCL

    • Role Management - DCL allows grouping privileges into roles that can be assigned to users
    • Protection of Database Objects
      • Tables - Control who can see or modify table data.
      • Columns - Restrict access to specific attributes.
      • Views - Grant access to derived or aggregated data.
      • Domains and Constraints - Protect schema-level objects like constraints and types.

    5. Transaction Control Language (TCL)

      Transaction Control Language (TCL) is a subset of SQL that manages transactions in a database. Transactions are sequences of SQL operations performed as a single logical unit of work. TCL commands ensure that these transactions maintain data integrity and consistency.

    Key Features

    • Atomicity - Ensures that all operations in a transaction are completed successfully. If any operation fails, the entire transaction is rolled back.
    • Consistency - Guarantees that a transaction brings the database from one valid state to another, maintaining defined rules and constraints.
    • Isolation - Ensures that transactions are executed independently of one another.
    • Durability - Once a transaction is committed, changes are permanent even in case of a system failure.
    TCL Commands
    Command Description Syntax
    COMMIT Saves all the changes made during the transaction permanently in the database. COMMIT;
    ROLLBACK Reverts all changes made during the current transaction, restoring the database to its previous state. ROLLBACK;
    SAVEPOINT Creates a checkpoint within a transaction to enable partial rollbacks. SAVEPOINT sp1;
    SET TRANSACTION Sets transaction properties like isolation levels. SET TRANSACTION READ ONLY;

    COMMIT

    • Purpose - Saves all the changes made during the transaction permanently in the database.
    • Use Case - Finalizing successful operations.
    • Example
      • BEGIN TRANSACTION;
      INSERT INTO Employees (ID, Name, Department) VALUES (1, 'Alice', 'HR');
      UPDATE Employees SET Department = 'Finance' WHERE ID = 1;
      COMMIT;
      In the above example:
      • The transaction inserts and updates records.
      • The COMMIT statement makes these changes permanent.

    ROLLBACK

    • Purpose - Reverts all changes made during the current transaction, restoring the database to its previous state.
    • Use Case - Used when errors occur or when a transaction must be aborted.
    • Example
      • BEGIN TRANSACTION;
      INSERT INTO Employees (ID, Name, Department) VALUES (2, 'Bob', 'IT');
      UPDATE Employees SET Department = 'Marketing' WHERE ID = 2;
      ROLLBACK;
      In the above example:
      • Any changes made by the INSERT and UPDATE statements are undone by ROLLBACK

    SAVEPOINT

    • Purpose - Creates a savepoint or checkpoint within a transaction. You can roll back to a specific savepoint instead of rolling back the entire transaction.
    • Use Case - Used for partial rollback within a transaction.
    • Example
      • BEGIN TRANSACTION;
      INSERT INTO Employees (ID, Name, Department) VALUES (3, 'Charlie', 'Sales');
      SAVEPOINT sp1;
      UPDATE Employees SET Department = 'Operations' WHERE ID = 3;
      ROLLBACK TO sp1;
      COMMIT;
      In the above example:
      • The INSERT operation is saved with SAVEPOINT sp1.
      • The UPDATE operation is undone with ROLLBACK TO sp1.
      • The transaction is committed with only the INSERT operation.

    SET TRANSACTION

    • Purpose - Sets properties for a transaction, such as isolation level.
    • Use Case - Used to control how data modifications and reads interact in a multi-user environment.
    • Example
      • SET TRANSACTION READ ONLY;
      SELECT * FROM Employees WHERE Department = 'HR';
      In the above example:
      • The transaction is set to READ ONLY, ensuring no changes can be made to the data.

    Properties of Transactions

    TCL ensures that every transaction adheres to the ACID properties.

    Properties Description
    Atomicity Ensures that all operations in a transaction succeed or fail as a unit.
    Consistency Guarantees that a transaction leaves the database in a valid state.
    Isolation Ensures that transactions do not interfere with each other.
    Durability Ensures that committed changes persist, even in the event of a system crash.

    Real-World Use Cases

    Banking System

    • Transferring money between accounts involves multiple steps
      • Debit from one account.
      • Credit to another account.
    • TCL ensures that both steps succeed or fail as a unit to maintain consistency.

    E-Commerce Transactions

    • Processing an order involves:
      • Updating inventory.
      • Recording payment.
      • Generating invoices
    • Transactions ensure that all these steps are completed successfully, or none of them are applied.

    SELECT Statement in Oracle SQL

    The SELECT statement is one of the most fundamental and widely used commands in Oracle SQL.


    • It is part of the Data Query Language (DQL) and is used to retrieve data from one or more tables, views, or other database objects.
    • It allows you to retrieve specific rows and columns from a table or set of tables, and it can be executed in various ways to access data exactly as required.
    • The SELECT statement in Oracle SQL is used to retrieve data from one or more tables, views, or other database objects.
    • It is one of the most fundamental and commonly used commands in SQL.

    Syntax of the SELECT Statement

    SELECT column1, column2, ...
    FROM table_name
    [WHERE condition]
    [GROUP BY column]
    [HAVING condition]
    [ORDER BY column [ASC |DESC ] ]
    FETCH FIRST;


    Features of SELECT in Oracle SQL

    Feature Description
    Column Selection Allows selection of specific columns or all columns (SELECT *).
    Aliases Assigns an alias to a column or table for better readability using AS. Example: SELECT col1 AS alias.
    Expressions Enables the use of arithmetic operations, functions, and concatenations in queries.
    Subqueries Allows embedding a query within another query. Example: SELECT * FROM employees WHERE salary > (SELECT AVG(salary) FROM employees);.
    Joins Combines rows from multiple tables based on related columns. Includes INNER, OUTER, CROSS, and SELF JOIN.
    Set Operators Combines results from multiple SELECT statements (e.g., UNION, INTERSECT, MINUS).
    Aggregate Functions Performs calculations on a set of values, returning a single result. Examples: SUM, AVG, MAX.
    Row Limiting Clause Limits the number of rows returned. Example: FETCH FIRST 5 ROWS ONLY.

    Key Components of SELECT

    Clause Purpose Example
    SELECT Specifies the columns to retrieve or expressions to evaluate. SELECT first_name, last_name FROM employees;
    DISTINCT Identifies the table(s) from which data is to be retrieved. You can use single table or multiple tables with Joins.
    FROM Specifies the table(s) or view(s) to query data from. SELECT * FROM employees;
    WHERE Filters rows based on specified conditions. SELECT * FROM employees WHERE salary > 5000;
    GROUP BY Groups rows sharing a common value in specified columns for aggregate functions. SELECT department_id, AVG(salary) FROM employees GROUP BY department_id;
    HAVING Filters grouped rows based on aggregate function conditions. SELECT department_id, AVG(salary) FROM employees GROUP BY department_id HAVING AVG(salary) > 5000;
    ORDER BY Sorts the result set by one or more columns in ascending (ASC) or descending (DESC) order. SELECT * FROM employees ORDER BY hire_date DESC;
    FETCH FIRST Limits the number of rows returned in the result set (introduced in Oracle 12c). SELECT * FROM employees ORDER BY salary DESC FETCH FIRST 5 ROWS ONLY;

    SELECT Scenarios

    Scenario 1:- (Retrieve Specific Columns) Fetch only specific columns, such as employee_name and department_id, from the employees table.

    SELECT employee_name, department_id
    FROM employees;

    Scenario 2:- (Retrieve Specific Columns) Fetch only specific columns, such as employee_name and department_id, from the employees table.

    SELECT *
    FROM customer;

    - - The asterisk symbol ( * ) is used to select all columns in a table.

    Scenario 3:- (WHERE) Retrieve employees from the employees table who belong to department 10.

    SELECT employee_id, employee_name, salary
    FROM employees
      WHERE department_id = 10;

    Scenario 4:- (WHERE and logical operators) Retrieve employees with a salary greater than 5000 in a specific department 10.

    SELECT *
    FROM employee
      WHERE salary > 5000 AND department_id = 10 ;

    Scenario 5:- (ORDER BY) Display all employees sorted by their salary date in descending order.

    SELECTfirst_name, salary
    FROM employee
      ORDER BY salary DESC ;


    - - By Default ORDER BY will sort in ascending order.

    Scenario 6:- (GROUP BY) Calculate the average salary for each department.

    SELECT department_id, AVG(salary) AS Avg_Salary
    FROM employee
      GROUP BY department_id ;

    Scenario 7:- (HAVING) Retrieve departments with an average salary greater than 5000.

    SELECT department_id, AVG(salary) AS Avg_Salary
    FROM employee
      GROUP BY department_id
        HAVING AVG(salary) > 5000 ;

    Scenario 8:- (GROUP BY) Retrieve the top 3 highest-paid employees.

    SELECT first_name, salary COUNT(*) AS Empcount
    FROM employee
      ORDER BY salary DESC
        FETCH FIRST 5 ROWS ONLY ;

    Scenario 9:- (DISTINCT) Find the distinct job roles available in the employees table.

    SELECT DISTINCT job_id
    FROM employee ;

    Scenario 10:- (Aliases ) Retrieve employee details but assign aliases to column names for better readability.

    SELECT emp_name AS "Employee Name",
    salary AS "Monthly Salary" FROM employee ;

    Scenario 11:- (Arithmetic Operations ) Calculate the annual salary of employees by multiplying their monthly salary by 12.

    SELECT employee_name,
    salary,
    salary * 12 AS "Annual Salary"
    FROM employee ;

    Scenario 12:- (Subqueries ) Find employees whose salary is above the average salary of all employees.

    SELECT employee_name,
    salary
    FROM employee
      WHERE salary > (
        SELECT AVG (salary) FROM employees ) ;

    Scenario 13:- (Joins ) Get the list of employees along with their department names from the employees and departments tables.

    SELECT e.employee_name,
    d.department_name
    FROM employee e
    JOIN departments d
      ON e.department_id = d.department_id ;

    Scenario 14:- ( Set Operators ) Find job IDs that are either in the employees table or in the jobs table, but not in both.

    SELECT job_id
    FROM employee
    MINUS
    SELECT job_id
    FROM jobs ;

    Scenario 15:- ( Built-In Functions ) Convert employee names to uppercase and calculate the length of each name.

    SELECT UPPER ( employee_name ) AS "Uppercase Name" ,
      LENGTH ( employee_name ) AS "Name Length"
    FROM employee ;

    Scenario 16:- ( Conditional Logic with CASE ) Categorize employees based on their salary range.

    SELECT employee_name,
      salary,
      CASE
        WHEN salary < THEN 'Low'
        WHEN salary BETWEEN 30000 AND 70000 THEN 'Medium'
        ELSE 'High'
      END AS "Salary Category"
    FROM employee ;

    Scenario 17:- ( Use of Grouping Sets ) Find the total salary grouped by department and job role, including subtotals for each department.

    SELECT department_id,
      job_id,
      salary,
      SUM ( salary ) AS "Total Salary"
      FROM employee
    GROUP BY GROUPING SETS ( ( department_id, job_id ), ( department_id ) ) ;

    Scenario 18:- ( JSON ) Query employee details stored in a JSON column.

    SELECT employee_data.json_value ( '$.name' ) AS "Employee Name",
      employee_data.json_value ( '$.department' ) AS "Department"
    FROM employee_table ;


    Common Errors in SELECT Statements

    Error Code Description
    ORA-00904 Invalid identifier: Occurs when a column or alias is misspelled or doesn't exist.
    ORA-00933 SQL command not properly ended: Typically caused by a syntax error in the query.
    ORA-01722 Invalid number: Happens when trying to compare a numeric column to a non-numeric value.
    ORA-00942 Table or view does not exist: Happens if the table name is incorrect or not accessible.


    Best Practices for SELECT Statements

    Best Practice Description
    Use Specific Columns Avoid using SELECT *; specify only required columns to reduce overhead.
    Use Aliases for Clarity Assign meaningful aliases to columns or tables for better readability. Example: SELECT e.name AS EmployeeName.
    Index Awareness Use indexed columns in the WHERE clause to improve query performance.
    Avoid Complex Calculations Avoid complex calculations in WHERE clauses if possible, as they can slow down query execution.
    Filter Data Early Apply filters (WHERE) to reduce the number of rows processed by subsequent operations.
    Leverage Bind Variables Use bind variables in dynamic queries to improve performance and security.
    Comment Queries Add comments to complex queries for clarity. Example: -- This query fetches top 5 employees by salary.


    Dos and Don’ts of the SELECT Statement in Oracle SQL

    Category Do's Don'ts
    General Usage Use specific column names instead of SELECT * to improve performance and clarity. Avoid using SELECT * unless all columns are explicitly required.
    Column Aliases Use meaningful aliases for columns to enhance readability in the result set. Don’t use vague or misleading aliases that can confuse the purpose of the query.
    Filtering Data
    • Use the WHERE clause to limit the data retrieved, reducing unnecessary rows.
    • Use logical operators (AND, OR) carefully to avoid redundant or conflicting conditions.
    • Avoid complex filters without indexes, as they can degrade performance.
    • Avoid hardcoding values excessively; use bind variables instead.
    Sorting Results Use ORDER BY judiciously, and sort only when necessary to avoid unnecessary overhead. Don’t assume default order; the database doesn’t guarantee row order without ORDER BY.
    Index Usage Use indexed columns in the WHERE, JOIN, or GROUP BY clauses for better performance. Don’t force full table scans on large datasets without considering performance impacts.
    Distinct Values Use DISTINCT only when necessary to eliminate duplicate rows. Don’t overuse DISTINCT, as it can add computational overhead unnecessarily.
    Pagination Use FETCH FIRST n ROWS ONLY or ROWNUM for limiting results in large datasets. Don’t fetch all rows when only a subset of data is required for analysis or display.
    Joins Use appropriate JOIN types and conditions to avoid Cartesian products. Don’t forget to specify join conditions, as it may lead to large, unintended datasets.
    Subqueries Use subqueries or Common Table Expressions (CTEs) to simplify complex queries. Don’t write deeply nested subqueries that are hard to debug or optimize.
    Aggregations Use GROUP BY with aggregate functions for summarizing data efficiently. Don’t use GROUP BY without understanding the data distribution and purpose.
    Performance Analyze execution plans using EXPLAIN PLAN to optimize query performance. Don’t ignore performance tuning for queries running on large datasets.
    Error Handling Validate column names and table references to avoid runtime errors. Don’t hard-code values in queries that are subject to change (use bind variables).
    Comments Add comments for complex queries to ensure maintainability. Don’t write queries without documentation, especially for large or critical operations.
    Formatting Format SQL queries for better readability and collaboration. Don’t write unformatted or poorly indented SQL, making it harder to debug or modify.

    CREATE Table

    • The CREATE TABLE statement in SQL is used to define a new table within a database.
    • It specifies the table’s structure, including its columns, data types, constraints, and default values.
    • Creating tables carefully with a well-thought-out design is crucial because it forms the foundation of a database's schema and ensures that data is stored, managed, and queried effectively.
    Note : Each SQL database (like Oracle, SQL Server, and MySQL) has its own set of supported data types, with slight variations in syntax, but the core purpose and functionality remain consistent.

    Sample tables and Datasets are Available at Resources


    Basic Syntax

    CREATE TABLE table_name (
    column1 Datatype constraint ,
    column2 Datatype constraint ,
    column3 Datatype ,
    column4 datatype ,
    ...........
    ) ;

    Examples of CREATE TABLE

    1. Creating a Simple Table Without Constraints

    CREATE TABLE employee (
    emp_id INT ,
    first_name VARCHAR(15) ,
    last_name VARCHAR(15) ,
    DOB DATE
    ) ;

    2. Creating a Table with Constraints and Default Values

    Oracle:
    CREATE TABLE employee (
    emp_id NUMBER(5) PRIMARY KEY ,
    first_name VARCHAR2(15) NOT NULL,
    last_name VARCHAR2(15) NOT NULL,
    DOB DATE DEFAULT SYSDATE,
    salary NUMBER( 8, 2) CHECK ( salary > 0)
    ) ;

    SQL Server:
    CREATE TABLE employee (
    emp_id INT PRIMARY KEY ,
    first_name NVARCHAR(15) NOT NULL,
    last_name NVARCHAR(15) NOT NULL,
    DOB DATE DEFAULT GETDATE( ),
    salary DECIMAL( 8, 2) CHECK ( salary > 0)
    ) ;

    MySQL:
    CREATE TABLE employee (
    emp_id INT PRIMARY KEY ,
    first_name VARCHAR(15) NOT NULL,
    last_name VARCHAR(15) NOT NULL,
    DOB DATE DEFAULT CURRENT_DATE,
    salary DECIMAL( 8, 2) CHECK ( salary > 0)
    ) ;

    3. Creating a Table with Foreign Key Constraints

    Oracle:
    CREATE TABLE department (
    dept_id NUMBER(5) PRIMARY KEY ,
    dept_name VARCHAR2(20) ,
    ) ;

    CREATE TABLE employee (
    emp_id NUMBER(5) PRIMARY KEY ,
    first_name VARCHAR2(15) NOT NULL,
    last_name VARCHAR2(15) NOT NULL,
    DOB DATE ,
    salary NUMBER( 8, 2) ,
    dept_id NUMBER(5),
    FOREIGN KEY (dept_id) REFERENCES

    8. Best Practices for Using CREATE TABLE

    1. Define Primary and Foreign Keys

    • Always define PRIMARY KEY constraints on tables for unique row identification, and use FOREIGN KEY constraints for establishing relationships between tables. This ensures data integrity.

    2. Choose Appropriate Data Types

    • Choose data types that match the data as closely as possible.
    • Avoid large data types if not needed (e.g., using VARCHAR(50) for short text fields instead of VARCHAR(255)).
    • Numeric columns should have sufficient precision but should be as compact as possible.

    3. Use Constraints to Enforce Data Integrity

    • Use NOT NULL on columns that require values.
    • UNIQUE constraints can enforce uniqueness.
    • CHECK constraints validate column values within specific ranges or conditions.

    4. Consider Default Values

    • Default values simplify data entry and can serve as placeholders when data is missing or optional.
    • Avoid hard-coding dates as defaults; use system functions like SYSDATE, GETDATE(), or CURRENT_DATE.

    5. Naming Conventions

    • Use consistent naming conventions for table and column names (e.g., snake_case or camelCase) to enhance readability.
    • Prefix foreign key columns with the table name they reference (e.g., department_id instead of just id).

    9. Do’s and Don’ts When Using CREATE TABLE

    Do's :-

    • Do document your schema : Add comments on tables and columns for clarity (some databases support COMMENT for this).
    • Do plan for scalability : Choose a table design that can accommodate potential growth.
    • Do optimize for indexing: When possible, design tables with columns that can efficiently support indexing.

    Don'ts :-

    • Don’t use overly large data types: Avoid VARCHAR(MAX) or TEXT unless necessary; they can hinder performance.
    • Don’t ignore normalization : Properly normalize data to avoid redundancy and potential anomalies in data storage.
    • Don’t mix data types: Avoid columns where inconsistent types are stored, like mixing text and numbers, to maintain data consistency.
