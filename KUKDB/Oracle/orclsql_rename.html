RENAME TABLE Statement in Oracle SQL

In Oracle SQL, the RENAME statement is used to change the name of an existing table, view, sequence, synonym, or other schema objects.


Unlike other RDBMSs like MySQL, Oracle does not support renaming multiple tables or renaming tables across different schemas.


The RENAME statement is a DDL (Data Definition Language) operation, which means it is automatically committed once executed and cannot be rolled back.


Syntax

Basic Syntax

RENAME old_table_name TO new_table_name ;
  • old_table_name – The current name of the table.
  • new_table_name – The new name for the table.

Key Points

  • The RENAME statement commits automatically — it cannot be rolled back.
  • After renaming, any existing indexes, constraints, and triggers remain associated with the renamed table.
  • The RENAME statement cannot be used on:
    • Tables in a different schema.
    • Materialized views, partitions, or cluster tables.
      • If there are dependent objects (like views, procedures, or synonyms), renaming the table will cause them to become invalid.
      • All permissions (grants) on the table remain after renaming.

Restrictions on RENAME

  • You cannot rename:
    • A table that is part of a cluster.
    • A table owned by another user.
    • A table referenced by a foreign key constraint from another table.
  • You cannot rename:
    • Synonyms for tables.
    • Materialized views.

Example

1. Rename a Table:- Renaming the employees table to staff

RENAME employees TO staff ;
  • Table employees is now referred to as staff.
  • All data, indexes, and triggers remain intact.

2. Rename a Sequence:- Renaming a sequence emp_seq to staff_seq.

RENAME emp_seq TO staff_seq ;
  • The sequence will retain its properties (like increment values).

3. Rename a Synonym:- Renaming a synonym emp_view to staff_view.


RENAME emp_view TO staff_view ;
  • The synonym will point to the same object under the new name.

4. Rename a View:- Renaming a view v_employee to v_staff

RENAME v_employee TO v_staff ;
  • The underlying query of the view remains unchanged.
  • If any objects depend on the view, they may become invalid.

5. Rename a Table with Constraints:- If the employees table has a primary key, foreign key, or other constraints, renaming will keep them intact.

RENAME employees TO staff ;
  • All constraints will be preserved.
  • If other tables reference employees with a foreign key, those references will break unless updated manually.

Difference Between RENAME and ALTER TABLE RENAME

Feature RENAME ALTER TABLE RENAME
Scope Renames table, sequence, synonym, or view Only renames a table or column
Syntax Complexity Simple syntax More complex
Rollback No rollback No rollback
Effect on Indexes/Triggers Retained Retained
Effect on Dependencies Dependencies may become invalid Dependencies may become invalid
Permissions Remains unchanged Remains unchanged
Supported Objects Tables, sequences, views, synonyms Tables, columns

Advantages of RENAME

Advantage Description
Simple to Use The RENAME statement is easy to write and execute.
Retains Indexes and Triggers Indexes and triggers remain valid after renaming.
Fast Operation Renaming is a metadata change and is executed quickly.
Works on Multiple Object Types Can be used on tables, sequences, synonyms, and views.
No Data Loss Data remains intact after renaming.

Disadvantages of RENAME

Disadvantage Description
Cannot Rename Across Schemas You cannot rename a table across different schemas.
No Rollback Since it’s a DDL operation, it auto-commits and cannot be rolled back.
Breaks Object Dependencies Objects (like views, procedures, or triggers) depending on the renamed table become invalid.
No Clustered Table Support Cannot rename a table that is part of a cluster.
No Partitioned Table Support Cannot rename partitions or subpartitions directly.

Limitations of RENAME

Limitation Description
Cannot Rename Columns Use ALTER TABLE to rename columns instead.
Foreign Key Reference Issue If a table is referenced by a foreign key, renaming will cause the reference to break.
Partitioned Tables Cannot rename partitioned tables or partitions.
Schema Limitation Cannot rename tables across different schemas.
Materialized Views Cannot rename materialized views directly.

Common Errors and Solutions

Error Code Cause Solution
ORA-01765: specifying table name does not exist Table does not exist. Ensure the table name is correct.
ORA-04043: object does not exist Attempt to rename an object that does not exist. Verify the object name.
ORA-02266: unique/primary keys referenced by foreign keys Table is referenced by a foreign key. Drop or disable the foreign key constraint.
ORA-00942: table or view does not exist Table is in a different schema. Rename tables only in the same schema.
ORA-01502: index or partition of such name exists Trying to rename an index or partition directly. Indexes and partitions cannot be renamed directly.

Do's and Don'ts of RENAME TABLE

Do's Don'ts
Ensure that no critical objects depend on the table before renaming. Don’t rename a table that is referenced by foreign keys without updating dependencies.
Use RENAME when you need to change the logical meaning of the table name. Don’t rename a table when it’s part of a materialized view or cluster.
Ensure that renaming does not impact application code or stored procedures. Don’t rename tables frequently in production environments without testing.
Use RENAME instead of ALTER TABLE when renaming views or sequences. Don’t rename a table involved in active transactions.

Best Practices

  • Use RENAME only when absolutely necessary — especially in production environments.
  • Always check for dependent objects (like views, triggers, and constraints) before renaming.
  • Rename tables in a development environment first to avoid breaking production dependencies.
  • Use ALTER TABLE if you need to rename a column instead of renaming the whole table.

6. Drop a Global Temporary Table:- You can drop a global temporary table like any other table.

DROP TABLE temp_sales ;
  • Drops the definition of the global temporary table.
  • Session-specific data is automatically deleted.

FLASHBACK AFTER DROP

If a table is dropped without the PURGE option, you can restore it using the FLASHBACK command


FLASHBACK TABLE employees TO BEFOREDROP ;
  • Recovers the table from the RECYCLEBIN.

List Tables in the Recycle Bin

SHOW RECYCLEBIN ;
  • Lists all objects in the recycle bin.

Data Dictionary View for Dropped Tables

You can check the list of dropped tables in the RECYCLEBIN using

SELECT object_name, original_name, type, droptime
FROM recyclebin ;
  • Lists all objects in the recycle bin.

How to Empty the Recycle Bin

You can remove all objects from the recycle bin using

PURGE RECYCLEBIN ;

How to Purge a Specific Table from the Recycle Bin

You can purge a specific table from the recycle bin using

PURGE TABL "BIN$xy+Vdd4BgW7gRAADGG3Lxg==$0" ;
- - Use the object name from the recyclebin.

Common Errors and Solutions

Error Code Cause Solution
ORA-00942: table or view does not exist The table does not exist. Ensure the table name is correct.
ORA-02449: unique/primary keys in table referenced by foreign keys A foreign key exists on the table being dropped. Use CASCADE CONSTRAINTS to drop dependent constraints.
ORA-08186: invalid timestamp specified Issue with flashback recovery. Ensure the table is in the RECYCLEBIN and flashback is supported.
ORA-38301: not a valid object in the recycle bin Attempt to purge a non-existent table from the recycle bin. Verify the table name using SHOW RECYCLEBIN.
ORA-00903: invalid table name Invalid table name specified. Use correct table name format.
ORA-00933: SQL command not properly ended Incorrect syntax. Fix the syntax.

Advantages and Disadvantages of DROP TABLE

Advantages Disadvantages
Frees up storage space immediately. Data is lost permanently if PURGE is used.
Helps in database cleanup by removing unused tables. If dropped without PURGE, recovery might lead to corruption if data is modified.
Ensures clean removal of dependent objects when CASCADE CONSTRAINTS is used. May cause invalidation of dependent objects (views, triggers).
FLASHBACK allows recovery if PURGE is not used. Performance issues if many objects are dropped simultaneously.
Helps in schema redesign by removing obsolete tables. Large tables with many indexes may take time to drop.

Limitations of DROP TABLE

Limitation Details
Recycle Bin Dependency FLASHBACK is not possible if the recycle bin is disabled or PURGE is used.
Foreign Key Constraints Requires CASCADE CONSTRAINTS if there are foreign key references.
Partitioned Tables Dropping a partitioned table drops all partitions and their data.
Materialized Views Dropping a table used in a materialized view causes the view to become invalid.
Rollback Not Supported A DROP TABLE operation cannot be rolled back using ROLLBACK.

Do’s and Don’ts of DROP TABLE

Do's Don'ts
Use DROP TABLE with PURGE only when permanent removal is intended. Don’t use DROP TABLE on active tables during business hours.
Use CASCADE CONSTRAINTS when dropping tables with foreign keys. Don’t drop system tables or Oracle-maintained objects.
Verify if the table is still required before dropping. Don’t drop a table referenced by other objects without reviewing dependencies.
Use FLASHBACK to recover tables when PURGE is not used. Don’t rely on FLASHBACK if the recycle bin is disabled.
Use DROP carefully in production environments. Don’t drop large tables without estimating the impact on performance.

Best Practices

  • Always back up data before dropping tables.
  • Use FLASHBACK to recover dropped tables if the recycle bin is enabled.
  • Use CASCADE CONSTRAINTS cautiously to avoid accidental removal of dependent objects.
  • Avoid dropping large tables during peak hours — it can cause locking and performance issues.
  • Always test in a development environment before executing in production.
