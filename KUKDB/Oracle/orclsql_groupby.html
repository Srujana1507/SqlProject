    GROUP BY Clause in Oracle SQL


    The GROUP BY clause in Oracle SQL is used to organize data into groups based on one or more columns.


    • It is typically used with aggregate functions (e.g., COUNT, SUM, AVG, MAX, MIN) to perform calculations on each group of data.
    • It is a powerful clause for aggregating and analyzing data.

    Syntax

    SELECT column1 ,column3 ,aggregate_function(column3)
    FROM table_name
    GROUP BY column1 ,column2 ;

    Purpose of GROUP BY

    Purpose Description
    Group Rows Categorize data based on one or more columns.
    Data Analysis Analyze large datasets by grouping rows and summarizing data.
    Aggregate Results Apply aggregate functions like SUM, COUNT, AVG, MAX, and MIN to grouped data.


    Key Rules for Using GROUP BY

    1. Columns in SELECT List: All columns in the SELECT clause that are not part of an aggregate function must be included in the GROUP BY clause.


    2. Aggregates Allowed: You can only use aggregate functions (e.g., SUM, COUNT) on columns not included in the GROUP BY list.


    3. Order Matters: The grouping order affects the result, but the order in the GROUP BY clause does not affect sorting



    Key Features of GROUP BY

    Feature Description
    Data Grouping Groups rows based on the values of specified columns.
    Aggregations Allows the use of aggregate functions (e.g., SUM, COUNT, AVG) to calculate grouped summaries.
    Column Selection Only columns in the GROUP BY clause or aggregate functions can appear in the SELECT list.
    Ordering Can be used with ORDER BY for sorting grouped results.
    Filtering Aggregated Data Use HAVING to filter grouped data based on aggregate conditions.


    Examples

    Scenario 1: Retrieve the total sales for each department.

    SELECT Department ,SUM(Sales) AS TotalSales
    FROM Employees
    GROUP BY Department ;

    Scenario 2: Count the number of employees in each department.

    SELECT Department ,COUNT(*) AS EmployeeCount
    FROM Employees
    GROUP BY Department ;

    Scenario 3: Groups employees by department_id, calculates the average salary, and filters departments with an average salary greater than 5000.

    SELECT department_id ,AVG(salary) AS average_salary
    FROM Employees
    GROUP BY department_id
    HAVING AVG(salary) > 5000 ;

    Scenario 4: Groups employees by both department_id and job_id, and counts the number of employees in each combination.

    SELECT department_id , job_id ,COUNT(*) AS emp_count
    FROM Employees
    GROUP BY department_id , job_id ;

    Scenario 5: ( Group by with Join and Subquery ) Find the total sales for each department, but only for departments located in the city of 'Hyderabad'.

    SELECT d.department_id , job_id ,SUM(s.sales_amount) AS total_sales
    FROM sales s
    JOIN departments d ON s.department_id = d.department_id
      WHERE d.location_id = (
        SELECT location_id
        FROM locations
          WHERE city = 'Hyderabad'
        )
      GROUP BY d.department_id ;

    Scenario 6: ( Group by with HAVING and Aggregate Function ) Identify departments where the number of employees exceeds the average number of employees across all departments.

    SELECT d.department_id , COUNT(*) AS employee_count
    FROM employees
    GROUP BY department_id
    HAVING COUNT(*) > ( SELECT AVG( dept_count )
        FROM ( SELECT COUNT(*) AS dept_count
          FROM employees GROUP BY department_id
          )
      ) ;

    Scenario 7: ( Group by with Conditional Aggregate ) Find the number of employees in each department, counting only those who have completed at least one project.

    SELECT d.department_id , COUNT( DISTINCT e.employee_id ) AS active_employee_count
    FROM employees e
    JOIN project_assignments p ON e.employee_id = p.employee_id
    GROUP BY e.department_id ;

    Scenario 8: ( Group by with NULLs ) Calculate the total sales grouped by customer, where orders with missing customer IDs (NULL) are labeled as "Guest." This ensures meaningful representation of guest checkouts in the results.

    SELECT NVL( TO_CHAR (customer_id) , COUNT'Guest' ) AS customer_group ,
      SUM (order_amount) AS total_sales
    FROM orders
    GROUP BY NVL ( customer_id, -1 ) ;

    Scenario 9: ( GROUP BY with Window Functions )Retrieve each department's total sales alongside each employee's contribution percentage.

    SELECT Department ,EmployeeID , Sales,
    (Sales * 1.0 / SUM(Sales) OVER (PARTITION BY Department ) ) * 100 AS ContributionPercentage
    FROM Employees ;

    Scenario 10: ( GROUP BY with ORDER BY )Retrieve Groups employees by department_id and display by total_salary in descending order.

    SELECT department_id , SUM(salary) AS total_salary
    FROM employees
    GROUP BY department_id
    ORDER BY total_salary ;

    Scenario 11: ( Nested Grouping )Find the maximum sales within each department, and then filter for departments where the maximum exceeds $5,000.

    WITH MaxSalesPerDept AS (
      SELECT department_id , MAX(Sales) AS MaxSales
      FROM employees
      GROUP BY department_id
      )
    SELECT *
    FROM MaxSalesPerDept
    WHERE MaxSales > 5000 ;

    Scenario 12: Group by a calculated field (e.g., age group).

    SELECT
      CASE
        WHEN Age < 30 THEN 'Under 30'
        WHEN Age BETWEEN 30 AND 50 THEN '30-50'
        ELSE 'Over 50'
      END AS AgeGroup
      COUNT( *) AS Count
    FROM employees
    GROUP BY
      CASE
        WHEN Age < 30 THEN 'Under 30'
        WHEN Age BETWEEN 30 AND 50 THEN '30-50'
        ELSE 'Over 50'
      END ;

    Common Errors with GROUP BY

    Error Cause Solution
    ORA-00979: Not a Group By Expression A column in the SELECT list is not included in the GROUP BY clause or an aggregate function. Include all non-aggregated columns in the GROUP BY clause.
    ORA-01722: Invalid Number Performing invalid operations (e.g., adding strings) or using mismatched data types. Ensure proper data types for operations in aggregate functions.
    Slow Performance Large datasets without indexes or excessive columns in GROUP BY. Optimize by indexing columns and limiting the grouping scope.


    Limitations of GROUP BY Clause

    Limitations Description
    Aliased Columns Aliases cannot be used in the GROUP BY clause; use the original column names.
    Aggregate Filters Filtering aggregate results requires the HAVING clause, not WHERE.
    LOB Data Types Columns with CLOB, BLOB, or similar data types cannot be grouped directly.
    Performance on Large Data Grouping on large datasets can be resource-intensive without proper indexing or optimization.


    Do's and Don'ts of GROUP BY Clause in Oracle SQL

    Category Do's Don'ts
    Syntax Use proper column names in the GROUP BY clause. Don’t use column aliases in the GROUP BY clause; use original column names.
    Column Selection Include only required columns in the GROUP BY clause to simplify query execution. Don’t group by unnecessary columns, as it increases query complexity and execution time.
    WHERE vs HAVING Use WHERE to filter rows before grouping and HAVING to filter aggregated results. Don’t use HAVING for conditions that can be handled by WHERE, as it affects performance.
    Null Handling Consider how NULL values are handled in grouped columns. Don’t ignore NULL values; they are treated as a separate group in the results.
    Sorting Use ORDER BY to sort the grouped results if required. Don’t assume GROUP BY results are automatically sorted (this behavior is non-standard).
    Data Type Compatibility Ensure data types in grouped columns are compatible for meaningful aggregation. Don’t group by incompatible or unnecessary data types like BLOB or CLOB.
    GROUP BY ROLLUP / CUBE Use advanced features like ROLLUP and CUBE for hierarchical or multidimensional grouping. Don’t use these features unnecessarily if a simple GROUP BY satisfies the requirement.
    Aggregate Functions Use aggregate functions (e.g., SUM, AVG) along with GROUP BY for meaningful results. Don’t mix non-aggregated columns in the SELECT clause without including them in GROUP BY.
    Joins Combine GROUP BY with joins for advanced queries. Don’t forget to qualify column names when using multiple tables to avoid ambiguity.
    Index Usage Use indexed columns in GROUP BY to enhance performance. Don’t expect indexing to help if functions or transformations are applied on GROUP BY columns.
    Subqueries Use subqueries or Common Table Expressions (CTEs) to pre-aggregate data if needed. Don’t use overly complex subqueries without analyzing their impact on performance.


    Best Practices for GROUP BY

    • Avoid GROUP BY on Columns with High Cardinality :- Grouping on unique columns (like primary keys) may result in no effective grouping.
    • Use HAVING for Aggregate Filters :-Apply aggregate filters with HAVING, not WHERE.
    • Optimize with Indexes :- Ensure that the columns in the GROUP BY clause are indexed for better performance.
    • Be Mindful of NULLs :- Null values are treated as a distinct group.
    • Combine GROUP BY with ORDER BY :- Use ORDER BY to sort grouped data for better readability.
    • Minimize Columns in GROUP BY :- Include only necessary columns to avoid generating overly granular groups.
    • Combine with WHERE :-Use WHERE to filter rows before grouping to improve query performance.
    • Use Meaningful Aliases :-Use descriptive aliases for calculated fields in the SELECT clause.
