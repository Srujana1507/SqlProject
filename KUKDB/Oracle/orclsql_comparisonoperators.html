Comparison Operators in Oracle SQL

Comparison operators are used in Oracle SQL to compare two values.


  • They return a Boolean result (TRUE, FALSE, or NULL).
  • These operators are commonly used in WHERE, HAVING, and other conditional clauses to filter or evaluate data.


Key Features of Comparison Operators

Feature Description
Basic Evaluation Compare two expressions or values for equality, inequality, or relative magnitude.
NULL Handling Some operators treat NULL differently, requiring special care with IS NULL.
Wide Applicability Usable in conditions, joins, subqueries, and more.
Combines with Logical Ops Often combined with logical operators (AND, OR, NOT) for complex conditions.


List of Comparison Operators

Operator Description Example
= Checks if two values are equal. salary = 5000
!= or <> Checks if two values are not equal. department_id != 10
> Checks if the left value is greater than the right value. salary > 10000
< Checks if the left value is less than the right value. salary < 5000
>= Checks if the left value is greater than or equal to the right value. hire_date >= '2023-01-01'
<= Checks if the left value is less than or equal to the right value. bonus <= 1000


Key Points

Operator Precedence:- Operators like = and <> are evaluated after logical operators like AND or OR. Parentheses can be used to control precedence.


Case Sensitivity:- Character comparisons are case-sensitive unless explicitly handled using functions like UPPER() or LOWER().


Behavior with NULLs

Comparison with NULL:

  • Any comparison involving NULL will always result in FALSE unless explicitly handled.
  • Use the IS NULL or IS NOT NULL operators.


Limitations

Limitations Explanation
NULL Comparisons Using = or <> with NULL always returns FALSE. Use IS NULL instead.
Precision Issues Comparisons involving floating-point numbers can result in rounding errors.
Performance Overhead Complex comparisons with large datasets can impact query performance.


Common Errors with Comparison Operators

Error Cause Solution
ORA-01722: Invalid Number Comparing a numeric column with a string that cannot be converted. Ensure consistent data types in the comparison.
ORA-00932: Inconsistent Datatypes Using incompatible data types in a comparison. Use explicit type conversion if required (e.g., TO_CHAR, TO_NUMBER).
NULL Evaluation Issues NULL values are not explicitly handled in comparisons. Use IS NULL or NVL to handle NULLs explicitly.
Data Type Mismatch Comparing incompatible data types (e.g., string and number). Ensure data types are compatible.
Precision Inaccuracy Floating-point comparisons failing due to rounding. Use rounding functions or approximations.


Best Practices for Comparison Operators

Practice Description
Use Explicit Comparisons Always specify the exact comparison to avoid ambiguity.
Avoid Hardcoding Values Use bind variables or parameterized queries to improve performance and security.
Combine with Logical Operators Combine comparison operators with AND, OR, or NOT for more complex conditions.


Do's and Don'ts

Do's Don'ts
Use IS NULL and IS NOT NULL for NULL evaluations. Avoid direct comparisons with NULL.
Use BETWEEN for inclusive range checks. Don’t assume = works for approximate floating points.
Combine comparison operators with logical operators for complex conditions. Avoid unnecessary comparisons that increase query cost.


Equal (=) Operator in Oracle SQL

The Equal (=) operator in Oracle SQL is one of the most fundamental comparison operators.


  • The = operator is a comparison operator used to check for equality between two values or expressions.
  • It is used to compare two values for equality.
  • If the values are equal, the condition evaluates to TRUE, and the corresponding rows are included in the result set.

Key Features of the Equal (=) Operator

Feature Description
Basic Equality Check Compares two values to determine if they are equal.
Data Type Support Works with numeric, character, date, and other data types.
Supports Literal Values Compares a column value with a constant (literal) value.
NULL Behavior Returns NULL if one or both values being compared are NULL. Use IS NULL to handle such cases.
Wide Usage Commonly used in SELECT, UPDATE, DELETE, WHERE, ON, and other SQL clauses.
Case-Sensitivity Comparisons involving strings are case-sensitive in Oracle SQL.
Column-to-Column Comparison Compares values between two columns in the same or different tables.

Syntax

column_name = value

( OR )

expression1 = expression2
expression1 and expression2: Can be column names, constants, or expressions.

Examples / Scenarios

Scenario 1:- ( Basic Example ) Retrieve employees who work in department 10.

SELECT employee_id, first_name, department_id
FROM Employees
WHERE department_id = 10 ;

Scenario 2:- ( Basic Example ) Retrieve employees whose job title is 'Manager'.

SELECT employee_id, first_name, last_name
FROM Employees
WHERE job_title = 'Manager' ;

Scenario 3:- ( With JOIN Condition ) Get the names of employees along with their department names.

SELECT e.employee_id, e.first_name, d.department_name
FROM employees e
JOIN departments d ON e.department_id = d.department_id ;

Scenario 4:- ( Column-to-Column Comparison ) Find employees whose salary matches their commission.

SELECT employee_id, salary, commi_pct
FROM employees
WHERE salary = commi_pct ;

Scenario 5:- ( Case-Sensitivity in Strings ) Retrieve employees whose last name is 'Uday' (case-sensitive).

SELECT employee_id, first_name, last_name
FROM employees
WHERE last_name = 'Uday' ;

Scenario 5.1:- ( Case-Sensitivity in Strings ) Retrieve customers with the name "Harsha" regardless of case.

SELECT customer_id, first_name
FROM customers
WHERE UPPER (first_name) = 'HARSHA' ;

Scenario 6:- ( with Subqueries ) Find employees whose salaries match the average salary of their departments.

SELECT employee_id, first_name, salary
FROM employees
WHERE salary = ( SELECT AVG( Salary ) FROM employees ;

Scenario 7:- ( Matching Products in Different Warehouses ) Retrieve products that are available in two different warehouses.

SELECT p1.product_id, p1.product_name, p1.warehouse_id AS warehouse_1, p2.warehouse_id AS warehouse_2
FROM products p1
JOIN products p2
    ON p1.product_id = p2.product_id
WHERE p1.warehouse_id <> p2.warehouse_id ;

Scenario 8:- Find employees who work in multiple departments with the same job title.

SELECT e1.employee_id, e1.department_id AS dept1, e2.department_id AS dept2
FROM employees e1
JOIN employees e2
    ON e1.employee_id = e2.employee_id
WHERE e1.department_id <> e2.department_id
    AND e1.job_id = e2.job_id ;

Behavior with NULL Values

  • The = operator does not handle NULL values as equal to anything (not even another NULL).
  • To compare NULL values, use the IS NULL operator instead.

Example :-

SELECT * FROM employees WHERE email = NULL ; -- No rows will return

SELECT * FROM employees WHERE email IS NULL ; - - Correct approach

Limitations of = Operator

Limitation Description
Cannot Handle NULLs Comparing with NULL using = always returns NULL. Use IS NULL or IS NOT NULL.
Case Sensitivity for Strings String comparisons are case-sensitive unless handled with functions like UPPER() or LOWER().
Implicit Data Type Conversion May result in performance overhead if implicit conversion is needed.
Data Type Restrictions Both operands must be of compatible data types; otherwise, an error occurs.

Common Errors with = Operator

Error Cause Solution
ORA-01722: Invalid Number Comparing numeric and non-numeric values. Ensure data types match or use explicit type casting (e.g., TO_NUMBER).
NULL Value Comparison Issues Using = to compare with NULL. Use IS NULL instead of = to handle NULL comparisons.
Case Sensitivity Mismatch Comparing strings with mismatched cases. Use UPPER() or LOWER() functions to standardize string comparison.
Data Type Mismatch Comparing incompatible data types (e.g., a string with a number). Ensure data types of both sides are compatible.

Do's and Don'ts of = Operator

Do's Don'ts
Use = for equality comparisons between values or columns. Don’t use = for comparing NULL; use IS NULL instead.
Use = in JOIN conditions to match columns from different tables. Don’t rely on implicit conversion of data types (e.g., comparing VARCHAR2 with NUMBER).
Handle case-sensitivity when comparing string values. Avoid assuming NULL equals anything; NULL comparisons always evaluate to FALSE.
Ensure data types match when using = for comparisons. Avoid comparing incompatible data types without explicit type conversion.


Not Equal (!= or <>) Operator in Oracle SQL

The Not Equal (!= or <>) operator is used in Oracle SQL to test whether two values are not equal.

  • If the values are not equal, the condition evaluates to TRUE, and the corresponding rows are included in the result set.

Key Features of != or <> Operator

Feature Description
Inequality Check Compares two values or expressions to see if they are not equal.
NULL Behavior Returns NULL if either or both values being compared are NULL.
Wide Usage Can be used in SELECT, WHERE, JOIN, HAVING, and other clauses.
Supports All Data Types Works with numbers, strings, dates, and other supported data types.
Synonymous Operators Both != and <> function identically in Oracle SQL.
Case-Sensitivity For strings, the comparison is case-sensitive in Oracle SQL.

Syntax

column_name != value
column_name <> value

( OR )

expression1 != expression2
expression1 <> expression2

Examples / Scenarios

Scenario 1:- ( Basic Inequality Check ) Retrieve employees who do not belong to department 10.

SELECT employee_id, first_name, department_id
FROM Employees
WHERE department_id != 10 ;

Scenario 2:- ( String Inequality ) Retrieve employees who are not in the 'IT_PROG' job role.

SELECT employee_id, first_name, last_name, job_id
FROM Employees
WHERE job_id != 'IT_PROG' ;

Scenario 2.1:- ( String Inequality ) Find products that are not in the category "Electronics".

SELECT product_id, product_name, category
FROM products
WHERE category <> 'Electronics' ;

Scenario 3:- ( Column-to-Column Comparison ) Find employees whose salary is not equal to their commission amount.

SELECT employee_id, salary, comm_pct
FROM Employees
WHERE salary <> comm_pct ;

Scenario 4:- ( Numeric Comparison ) Retrieve orders where the total amount is not 1000.

SELECT order_id, customer_id, total_amount
FROM orders
WHERE total_amount <> 1000 ;

Scenario 5:- ( Exclude Specific Departments ) Retrieve all employees who are not in departments 10, 20, or 30.

SELECT employee_id, department_id, salary
FROM employees
WHERE department_id NOT IN ( 10, 20, 30 ) ;

Scenario 6:- ( Inequality with Subquery ) Retrieve employees whose salaries are not equal to the average salary of their department.

SELECT employee_id, first_name, salary, department_id
FROM employees
WHERE salary != (
    SELECT AVG ( salary ) FROM employees e2
      WHERE e2.department_id = employees.department_id ) ;

Scenario 7:- ( Inequality in Joins ) Find orders placed by customers who are not from the same city as the company.

SELECT o.order_id, c.customer_name, c.city, co.company_city
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN company co ON c.city <> co.company_city ;

Scenario 8:- ( Inequality in Joins ) Find orders placed by customers who are not from the same city as the company.

SELECT o.order_id, c.customer_name, c.city, co.company_city
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN company co ON c.city <> co.company_city ;

Scenario 9:- ( with Date Comparison ) Find employees who were not hired in the year 2023.

SELECT employee_id, first_name, hire_date
FROM employees
WHERE EXTRACT ( YEAR FROM hire_date ) != 2023 ;

Scenario 10:- ( with Case Expression ) Label customers as "New" or "Returning" based on order count not equal to 1.

SELECT customer_id,
    CASE
      WHEN order_count != 1 THEN 'Returning'
      ELSE 'New'
    END AS customer_type
FROM customers ;


Limitations of != or <>

Limitation Description
Cannot Handle NULLs Directly Comparing with NULL using != or <> always returns NULL. Use IS NOT NULL for such cases.
Data Type Restrictions Both operands must have compatible data types; otherwise, an error will occur.
Case-Sensitivity for Strings String comparisons are case-sensitive, which can cause unexpected results if case is not handled.
Performance Concerns Using != or <> on indexed columns can sometimes bypass indexes, leading to slower queries.
Precision Issues in Floating-Point Inequality comparisons with floating-point numbers can be affected by rounding.

Common Errors with != or <>

Error Cause Solution
ORA-01722: Invalid Number Comparing numeric columns with non-numeric values. Ensure consistent data types for both operands.
Comparison with NULL Using != or <> to compare NULL values. Use IS NOT NULL for checking non-NULL values.
Data Type Mismatch Comparing incompatible data types (e.g., a string with a number). Ensure data types are compatible.
Case-Sensitivity Mismatch Comparing strings with mismatched cases. Use UPPER() or LOWER() functions to standardize case in comparisons.

Do's and Don'ts

Do's Don'ts
Use != or <> to filter out rows with non-matching values. Don’t use != or <> to compare NULL; use IS NOT NULL instead.
Ensure data type compatibility between the compared values. Avoid assuming strings with different cases will be considered unequal (case-sensitive).
Combine != or <> with logical operators (AND, OR, NOT) for more complex queries. Don’t use != or <> without understanding the impact on query performance.
Combine with logical operators for complex conditions. Avoid using inequality unnecessarily, which can reduce performance.


Greater Than (>) Operator in Oracle SQL

The Greater Than (>) operator in Oracle SQL is a comparison operator used to filter or compare rows where one value is greater than another.


  • It evaluates whether the value on the left side is greater than the value on the right side.
  • If the condition is met, it returns TRUE; otherwise, it returns FALSE.

Key Features

Feature Description
Numeric Comparison Used to compare numeric values for filtering or evaluation.
String Comparison Compares strings based on their lexicographical order.
Date and Timestamp Comparison Compares date and timestamp values.
NULL Handling Returns FALSE if either operand is NULL.
Works in Joins and Subqueries Can be used in joins, subqueries, and complex SQL conditions.
Wide Usage Can be used with SELECT, WHERE, HAVING, JOIN, and other clauses.

Syntax

column_name > value

( OR )

expression1 > expression2

Behavior with NULL Values

  • If either operand is NULL, the result of the comparison is FALSE.
  • To handle NULL explicitly, use the NVL() function or COALESCE() to provide a default value.

SELECT * FROM Employees
WHERE salary > NULL ; -- No rows will return
SELECT * FROM Employees
WHERE salary IS NULL ; -- Correct approach

Examples / Scenarios

Scenario 1:- ( Basic Numeric Comparison ) Retrieve employees with a salary greater than 50,000.

SELECT employee_id, first_name, salary
FROM Employees
WHERE salary > 50000 ;

Scenario 2:- ( String Comparison ) Find products with names greater than 'M' alphabetically.

SELECT product_id, product_name
FROM products
WHERE product_name > 'M' ;

Scenario 3:- ( Date Comparison ) Retrieve orders placed after January 1, 2023.

SELECT order_id, customer_id, order_date
FROM orders
WHERE order_date > TO_DATE ( '2023-01-01', 'YYYY-MM-DD' ) ;

Scenario 4:- ( With Subquery ) Find employees whose salaries are greater than the department's average salary.

SELECT employee_id, first_name, salary
FROM employees
WHERE salary > ( SELECT AVG (salary) FROM employees ) ;

Scenario 5:- ( With JOINs ) Retrieve product orders where the quantity ordered is greater than the available stock.

SELECT o.order_id, p.product_id, o.quantity, p.stock
FROM orders o
JOIN products p ON o.product_id = p.product_id
WHERE o.quantity > p.stock ;

Scenario 6:- ( With Aggregate Functions ) Retrieve product orders where the quantity ordered is greater than the available stock.

SELECT department_id, COUNT (*) AS emp_count
FROM employees
GROUP BY department_id
HAVING COUNT (*) > 5 ;

Scenario 7:- Retrieve regions where the total sales exceed the sales in the 'North' region.

SELECT region_name, total_sales
FROM sales_regions
WHERE total_sales > (
    SELECT total_sales
    FROM sales_regions
    WHERE region_name = 'North'
) ;

Scenario 8:- ( Using CASE ) Categorize products as "High Stock" or "Low Stock" based on a stock threshold of 100.

SELECT product_id, product_name,
    CASE
      WHEN stock > 100 THEN 'High Stock'
      ELSE 'Low Stock'
    END AS stock_status
FROM products ;

Limitations

Limitation Description
Cannot Handle NULLs The > operator does not evaluate NULL values, resulting in no rows being returned.
Case-Sensitivity for Strings String comparisons are case-sensitive, which can lead to unexpected results.
Performance Issues Can cause performance issues if used on unindexed columns or with functions applied to columns.

Common Errors with > Operator

Error Cause Solution
ORA-01722: Invalid Number Comparing numeric values with non-numeric data. Ensure both operands are of compatible numeric types.
NULL Value Handling Using > with NULL values results in no rows being returned. Use NVL() or COALESCE() to replace NULL values with default values.
Case-Sensitivity in Strings String comparisons are case-sensitive. Use UPPER() or LOWER() for consistent case handling.

Do's and Don'ts of > Operator

Do's Don'ts
Use > for numeric, string, or date comparisons where appropriate. Don’t use > to compare NULL values; handle NULL explicitly.
Use > with subqueries to implement dynamic filters. Don’t assume strings of different cases will compare accurately without handling case.
Ensure both operands are of compatible data types to avoid runtime errors. Avoid unnecessary functions on indexed columns in > conditions to maintain performance.
Combine > with logical operators (AND, OR, NOT) for complex conditions. Avoid comparing incompatible data types without explicit conversion (e.g., DATE vs VARCHAR).

Best Practices for > Operator

Practice Description
Explicit NULL Handling Use NVL() or COALESCE() to provide default values for NULL before comparison.
Normalize String Comparisons Use UPPER() or LOWER() to ensure consistent string comparisons.
Use with Subqueries Combine > with subqueries to create dynamic and flexible filters.
Avoid Unnecessary Functions Avoid applying functions to columns in > conditions to prevent index bypass.
Optimize Performance Ensure that indexed columns are used in the > conditions for optimal query performance.

Greater Than or Equal To (>=) Operator in Oracle SQL

The Greater Than or Equal To (>=) operator in Oracle SQL is a comparison operator used to retrieve rows where the value in the left-hand operand is either greater than or equal to the value in the right-hand operand.


If the condition is true, it returns TRUE; otherwise, it returns FALSE.


Key Features

Feature Description
Inclusive Comparison Ensures the value is greater than or equal to the given threshold.
Supports Multiple Data Types Can be used with numbers, dates, and strings.
NULL Behavior Returns NULL if any operand is NULL.
Wide Usage Applicable in WHERE, HAVING, JOIN, and other clauses.

Syntax

column_name >= value

( OR )

expression1 >= expression2

Behavior with NULL Values

  • Comparisons involving NULL always return FALSE.
  • To include rows with NULL explicitly, use functions like NVL or COALESCE to provide default values.

SELECT * FROM Employees
WHERE salary >= NULL ; -- No rows will return
SELECT * FROM Employees
WHERE NVL (salary, 0) >= 5000 ; -- Correct usage

Examples / Scenarios

Scenario 1:- ( Basic Numeric Comparison ) Retrieve employees with a salary of 60,000 or higher.

SELECT employee_id, first_name, salary
FROM Employees
WHERE salary >= 60000 ;

Scenario 2:- ( String Comparison ) Retrieve products where the product name is alphabetically greater than or equal to 'H'.

SELECT product_id, product_name
FROM products
WHERE product_name >= 'H' ;

Scenario 3:- ( Date Comparison ) Retrieve orders placed on or after July 1, 2023.

SELECT order_id, order_date, customer_id
FROM orders
WHERE order_date >= TO_DATE ( '2023-07-01', 'YYYY-MM-DD' ) ;

Scenario 4:- ( With Subquery ) Retrieve employees whose salaries are greater than or equal to the average salary in their department.

SELECT employee_id, first_name, salary
FROM employees
WHERE salary >= ( SELECT AVG (salary) FROM employees ) ;

Scenario 5:- ( Combining Conditions ) Find customers whose total purchase amount is greater than or equal to 10,000 and who joined after January 1, 2022.

SELECT customer_id, first_name, total_purchases, join_date
FROM customers
WHERE total_purchases >= 10000 AND join_date >= TO_DATE( '2023-07-01', 'YYYY-MM-DD' ) ;

Scenario 6:- Retrieve employees who have been with the company for 5 or more years.

SELECT employee_id, hire_date, SYSDATE - hire_date AS years_with_company
FROM employees
WHERE (SYSDATE - hire_date) >= 5 * 365 ;

Scenario 7:- ( With JOINs ) Retrieve product orders where the ordered quantity is greater than or equal to the minimum stock level.

SELECT o.order_id, o.product_id, o.quantity, p.min_stock
FROM orders o
JOIN products p ON o.product_id = p.product_id
WHERE o.quantity >= p.min_stock ;

Scenario 8:- ( With Aggregate Functions ) Retrieve product orders where the quantity ordered is greater than the available stock.

SELECT department_id, SUM (salary) AS total_salary
FROM employees
GROUP BY department_id
HAVING SUM (salary) >= 1000000 ;

Scenario 9:- ( Compare Dates in Subqueries ) Retrieve orders placed on or after the earliest order date in 2023.

SELECT order_id, order_date
FROM orders
WHERE order_date >= (
    SELECT MIN (order_date)
    FROM orders
    WHERE EXTRACT ( YEAR FROM order_date) = 2023
) ;

Scenario 10:- ( Using CASE ) Categorize employees based on whether their salaries are above or equal to 75,000.

SELECT employee_id, first_name, salary,
    CASE
      WHEN salary >= 75000 THEN 'High Salary'
      ELSE 'Standard Salary'
    END AS salary_category
FROM employees ;

Limitations of >= Operator

Limitation Description
NULL Handling Comparisons with NULL always return FALSE.
Case-Sensitivity for Strings String comparisons are case-sensitive unless explicitly normalized using UPPER() or LOWER().
Index Optimization Indexes might not be utilized if columns are wrapped in functions or expressions.
Performance Concerns Using >= on large datasets or unindexed columns can lead to slower query performance.

Common Errors with >= Operator

Error Cause Solution
ORA-01722: Invalid Number Comparing numeric columns with non-numeric data. Ensure operands have compatible numeric data types.
NULL Value Handling Using >= with NULL returns no rows. Use NVL or COALESCE to handle NULL explicitly.
Date Format Issues Comparing dates without proper conversion. Use TO_DATE for consistent date comparisons.
Data Type Mismatch Comparing incompatible types (e.g., string and number). Ensure both operands have matching data types.

Do's and Don'ts of >= Operator

Do's Don'ts
Use >= for numeric, string, or date comparisons to include the boundary value. Don’t use >= with NULL; handle NULL values explicitly using NVL or COALESCE.
Ensure consistent data types between both operands. Avoid applying functions to indexed columns when using >= to maintain query performance.
Combine >= with logical operators (AND, OR, NOT) for complex filters. Don’t assume string comparisons are case-insensitive; account for case differences.

Best Practices for >= Operator

Practice Description
Explicit NULL Handling Use NVL or COALESCE to ensure NULL values are replaced with defaults.
Leverage Indexing Ensure that indexed columns are used in the >= condition for better performance.
Normalize String Comparisons Apply UPPER or LOWER to standardize case for string comparisons.
Avoid Functions on Columns Avoid using functions on columns in >= conditions to prevent index bypass.
Use with Subqueries Leverage subqueries to create dynamic filters with the >= operator.


Less Than or Equal To (<=) Operator in Oracle SQL

The Less Than or Equal To (<=) operator in Oracle SQL is a comparison operator used to filter or compare rows where the left-hand operand is either less than or equal to the right-hand operand.


If the condition is true, it returns TRUE; otherwise, it returns FALSE.


Key Features

Feature Description
Inclusive Comparison Ensures the value is less than or equal to the given threshold.
Supports Multiple Data Types Can be used with numbers, dates, and strings.
Versatility Can be used in WHERE, HAVING, JOIN, and other SQL clauses.
Numeric Comparison Filters rows where numeric values are less than or equal to a specified value.
String Comparison Compares strings based on lexicographical order (character-by-character).
Works in Joins and Subqueries Can be used in complex queries involving joins, subqueries, or logical operators.

Syntax

column_name <= value

( OR )

expression1 <= expression2

Behavior with NULL Values

  • If either operand is NULL, the result of the comparison is FALSE.
  • Handle NULL values explicitly using NVL() or COALESCE() to avoid unexpected results.

SELECT * FROM Employees
WHERE salary <= NULL ; -- No rows will return
SELECT * FROM Employees
WHERE NVL (salary, 0) <= 5000 ; -- Correct usage

Examples / Scenarios

Scenario 1:- ( Basic Numeric Comparison ) Retrieve employees with a salary of 40,000 or less.

SELECT employee_id, first_name, salary
FROM Employees
WHERE salary >= 40000 ;

Scenario 2:- ( String Comparison ) Retrieve products where the product name is alphabetically less than or equal to 'U'.

SELECT product_id, product_name
FROM products
WHERE product_name <= 'U' ;

Scenario 3:- ( Date Comparison ) Retrieve orders placed on or before June 30, 2023.

SELECT order_id, order_date, customer_id
FROM orders
WHERE order_date >= TO_DATE ( '2023-06-30', 'YYYY-MM-DD' ) ;

Scenario 4:- ( With Subquery ) Retrieve employees whose salaries are less than or equal to the average salary of their department.

SELECT employee_id, first_name, salary
FROM employees
WHERE salary <= ( SELECT AVG (salary) FROM employees ) ;

Scenario 5:- ( Combining Conditions ) Find customers who spent less than or equal to $5,000 or joined on or before January 1, 2020.

SELECT customer_id, first_name, total_purchases, join_date
FROM customers
WHERE total_purchases <= 5000 OR join_date >= TO_DATE( '2020-01-01', 'YYYY-MM-DD' ) ;

Scenario 6:- Retrieve orders where the delivery time was 7 days or fewer. years.

SELECT order_id, delivery_days
FROM orders
WHERE delivery_days <= 7 ;

Scenario 7:- ( With JOINs ) Retrieve orders where the ordered quantity is less than or equal to the maximum stock level of the products.

SELECT o.order_id, o.product_id, o.quantity, p.max_stock
FROM orders o
JOIN products p ON o.product_id = p.product_id
WHERE o.quantity <= p.max_stock ;

Scenario 8:- ( With Aggregate Functions ) Get departments where the average salary is less than or equal to 75,000.

SELECT department_id, AVG (salary) AS average_salary
FROM employees
GROUP BY department_id
HAVING AVG (salary) <= 75000 ;

Scenario 9:- ( Using CASE ) Categorize customers based on whether their total purchases are below or equal to 10,000.

SELECT customer_id, first_name, total_purchases,
    CASE
      WHEN total_purchases <= 10000 THEN 'Low Spender'
      ELSE 'High Spender'
    END AS spending_category
FROM customers ;

Limitations

Limitation Description
NULL Comparisons If any operand is NULL, the result is NULL.
Index Optimization Indexes might not be utilized if columns are wrapped in functions or expressions.
Case Sensitivity for Strings String comparisons are case-sensitive unless normalized using UPPER() or LOWER().

Common Errors

Error Cause Solution
NULL Comparison Comparing a NULL value using <= results in NULL. Use IS NOT NULL to handle NULL values.
Date Format Issues Comparing dates without proper conversion. Use TO_DATE for consistent date comparisons.
Data Type Mismatch Comparing incompatible types (e.g., string and number). Ensure both operands have matching data types.

Do's and Don'ts of <= Operator

Do's Don'ts
Use <= for numeric, string, or date comparisons where an upper limit is required. Don’t use <= with NULL without handling NULL values explicitly.
Use <= in conjunction with logical operators like AND, OR, and subqueries. Don’t assume case-insensitivity in string comparisons; handle case explicitly.
Ensure both operands have compatible data types for comparison. Avoid applying functions to columns in the <= condition, as it can bypass indexes.

Best Practices for <= Operator

Practice Description
Explicit NULL Handling Use NVL() or COALESCE() to replace NULL with default values.
String Normalization Use UPPER() or LOWER() for consistent case in string comparisons.
Leverage Indexing Ensure columns used in <= conditions are indexed for better performance.
Avoid Functions on Columns Avoid applying functions directly to columns in the condition to ensure indexes are utilized.
Combine with Subqueries Use <= in subqueries to dynamically define upper bounds for filtering.
