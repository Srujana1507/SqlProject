Foreign Key

A Foreign Key is a column or a set of columns in a table that establishes a link between the data in two tables.


It references the Primary Key or a Unique Key in another table, enforcing referential integrity by ensuring that the value in the foreign key column matches a valid entry in the referenced table.


It is used to enforce referential integrity by ensuring that the value in one table corresponds to a value in another table (the parent table).


Key Points

Aspect Details
Behavior Ensures data consistency between related tables by enforcing valid references.
Relationships Foreign Keys create relationships between tables (one-to-one, one-to-many, many-to-many).
Referential Integrity Ensures that the value in the child table matches a valid value in the parent table.
Parent-Child Relationship
  • Parent Table: The table containing the referenced Primary Key.
  • Child Table: The table containing the Foreign Key column.
Cascading Actions
  • ON DELETE CASCADE: Automatically deletes rows in the child table if the corresponding row in the parent table is deleted.
  • ON UPDATE CASCADE: Updates rows in the child table if the corresponding row in the parent table is updated.
Constraint Foreign Key constraints prevent invalid data entry into the child table.

Syntax

1. Defining a Foreign Key During Table Creation.

CREATE TABLE table_name (
    Column1 DataType,
    Column2 DataType,
    CONSTRAINT fk_name FOREIGN KEY (child_column)
    REFERENCES parent_table (parent_column) ) ;

2. Defining a Foreign Key on DELETE and UPDATE

CREATE TABLE table_name (
    Column1 DataType,
    Column2 DataType,
    FOREIGN KEY (Column1) REFERENCES ParentTable(ParentColumn)
    ON DELETE CASCADE
    ON UPDATE CASCADE ) ;

3. Adding a Foreign Key to an Existing Table.

ALTER TABLE ChildTable
    ADD CONSTRAINT FK_ChildTable FOREIGN KEY (Column1)
    REFERENCES ParentTable(ParentColumn)
    ON DELETE SET NULL ;

4. Dropping a Foreign Key.

ALTER TABLE ChildTable
    DROP CONSTRAINT fk_name ;

Types of Relationships Using Foreign Keys

Type Description
one-to-one A record in one table is linked to exactly one record in another table.
one-to-many A record in one table is linked to multiple records in another table.
many-to-many Implemented using a junction table with Foreign Keys referencing both related tables.

Behavior of Foreign Key

Operation Behavior
Insert Invalid Value Throws an error if the value in the child table does not exist in the parent table.
Delete Parent Row Behavior depends on ON DELETE action: CASCADE, SET NULL, RESTRICT, or NO ACTION.
Update Parent Row Behavior depends on ON UPDATE action: CASCADE, SET NULL, RESTRICT, or NO ACTION.

Advantages of Foreign Key

Advantage Description
Data Consistency Ensures valid data references between tables.
Referential Integrity Prevents orphaned records in child tables.
Enforced Relationships Simplifies database design by creating clear relationships between tables.
Cascading Operations Automates updates or deletions, reducing manual intervention.

Disadvantages of Foreign Key

Disadvantage Description
Performance Impact Foreign Key constraints can slow down insert, update, and delete operations in large datasets.
Complexity Can make schema design more complex, especially with multiple levels of relationships.
Cascading Risks Cascading deletes/updates can unintentionally remove or modify large amounts of data.
Dependency Issues Inserting or deleting rows may require careful order of operations due to dependencies.

Examples

Scenario 1:- (Basic Foreign Key Implementation) Each employee belongs to a valid department.

CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY ,
    DepartmentName VARCHAR(100)) ;


CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID) ) ;

Scenario 2:- (Cascade Deletion ) If a department is deleted, all employees in that department should also be removed.

CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY ,
    DepartmentName VARCHAR(100)) ;


CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID) ON DELETE CASCADE ) ;

Scenario 3:- (Prevent Deletion of Parent Records ) Do not allow deletion of a department if it has employees associated with it.

CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY ,
    DepartmentName VARCHAR(100)) ;


CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID) ON DELETE RESTRICT ) ;


Scenario 4:- ( Using Composite Foreign Keys ) Ensure that each order detail corresponds to a valid order and product combination.

CREATE TABLE Orders (
    OrderID INT,
    ProductID INT,
    PRIMARY KEY (OrderID, ProductID) ) ;

CREATE TABLE OrderDetails (
    DetailID INT PRIMARY KEY ,
    OrderID INT,
    ProductID INT,
    Quantity INT,
    FOREIGN KEY ( OrderID, ProductID ) REFERENCES Orders( OrderID, ProductID ) ) ;

Scenario 5:- ( Foreign Key with SET NULL ) If a department is deleted, set the DepartmentID of employees in that department to NULL.

CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY ,
    DepartmentName VARCHAR(100) ) ;


CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID) ON DELETE SET NULL ) ;

Scenario 6:- Adding a Foreign Key to an Existing Table.

ALTER TABLE Employees
    ADD CONSTRAINT fk_department FOREIGN KEY (department_id) REFERENCES departments(department_id) ;

Scenario 7:- Dropping a Foreign Key.

---SQL Server and PostgreSQL

ALTER TABLE Employees
    DROP CONSTRAINT fk_department ;

Scenario 8:- ( Many-to-Many Relationship Using a Junction Table ) A student can enroll in multiple courses, and a course can have multiple students.

CREATE TABLE Students (
    StudentID INT PRIMARY KEY ,
    StudentName VARCHAR(100)) ;


CREATE TABLE Courses (
    CourseID INT PRIMARY KEY ,
    CourseName VARCHAR(100)) ;


CREATE TABLE Enrollments (
    StudentID INT,
    CourseID INT,
    EnrollmentDate DATE,
    PRIMARY KEY (StudentID, CourseID),
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID),
    FOREIGN KEY (CourseID) REFERENCES Courses(CourseID) ) ;

Common Errors with FOREIGN KEY

Error Explanation Solution
No Matching Parent Key The value in the foreign key column does not exist in the parent table. Ensure the referenced value exists in the parent table.
Referential Integrity Violation Attempt to delete/update a parent row referenced by the child table. Use cascading actions or prevent deletion of parent rows in use.
Foreign Key Already Exists Attempt to add a foreign key that already exists. Check existing constraints before adding a new one.
Data Type Mismatch Mismatch between parent and child column data types. Ensure matching data types and lengths in both tables.
Circular Reference Two tables reference each other in foreign keys. Avoid circular dependencies in schema design.

Performance Hints for Foreign Keys

Hint Description
Match Data Types Parent and child columns must have identical data types.
Index the Parent Column Index the referenced column (primary/unique key) for better performance.
Define Cascading Actions Judiciously Use ON DELETE CASCADE and ON UPDATE CASCADE carefully to prevent unintended data loss.
Normalize Database Schema Use foreign keys to avoid redundancy and maintain normalization.
Validate Relationships Ensure data consistency between parent and child tables before defining foreign keys.

Do's and Don'ts with FOREIGN KEY

Do's Don'ts
Use foreign keys to enforce data integrity. Don’t reference non-unique or nullable columns in the parent table as foreign keys.
Index the parent table's referenced column. Don’t ignore cascading actions; understand their implications on updates and deletes.
Validate data consistency before adding. Don’t leave orphaned rows in the child table when deleting parent rows without cascading actions.
Document relationships in schema design. Don’t create unnecessary foreign keys that increase query complexity without adding value.
