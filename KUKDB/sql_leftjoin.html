LEFT JOIN or LEFT OUTER JOIN

A LEFT JOIN (also called LEFT OUTER JOIN) in SQL is used to retrieve all rows from the left table and the matching rows from the right table.


If no match is found, NULL values are returned for columns from the right table.


Key Characteristics of LEFT JOIN

1. All Rows from the Left Table:- Every row from the left table appears in the result, regardless of whether a match exists in the right table.


2. NULLs for Non-Matches:- When no match is found in the right table, NULL values are returned for its columns.


3. Versatility:- Useful when you need to identify records in one table that do not have corresponding entries in another.


Syntax

SELECT left_table.column1, right_table.column2, . . .
FROM left_table
LEFT JOIN right_table
ON left_table.common_column = right_table.common_column ;

Advantages and Disadvantages of Left Join

Advantages Disadvantages
Preserves All Left Table Rows:- Ensures every row from the left table is included in the result. Performance Issues:- Can be slow with large datasets if join columns are not indexed.
Highlights Missing Relationships:- Useful for identifying rows in the left table without matches in the right table. NULL Complications:- Includes many NULL values for unmatched rows, requiring careful handling.
Versatile for Reporting:- Ideal for scenarios where complete data from the left table is required. Redundant Data:- May lead to duplication if the right table contains multiple matching rows for a single left table row.
Simplifies Null Handling:- Easy to check unmatched rows using conditions like IS NULL. Complexity in Queries:- Can make queries harder to read and debug if combined with multiple joins or subqueries.
Useful in Outer-Dependent Relationships:- Handles optional relationships effectively, such as "customers with or without orders." Increased Memory Usage:- Joins on large tables with many unmatched rows can consume more memory.


Examples:-

Scenario 1:- Fetch the names of employees along with their department names. Include employees without departments.

SELECT e.employee_id, e.name AS employee_name, d.department_name
FROM employees e
LEFT JOIN departments d
    ON e.department_id = d.department_id ;

Scenario 2:- Show all products and the order IDs of orders they are part of. Include products without any orders.

SELECT p.product_id, p.product_name, o.order_id
FROM products p
LEFT JOIN orders o
    ON p.product_id = o.product_id ;

Scenario 3:- Retrieve all customers and their payment details, if available.

SELECT c.customer_id, c.customer_name, p.payment_date, p.amount
FROM customers c
LEFT JOIN payments p
    ON c.customer_id = p.customer_id ;

Scenario 4:- List employees who are not assigned to any project.

SELECT e.employee_id, e.name AS employee_name
FROM employees e
LEFT JOIN project_assignments pa
    ON e.employee_id = pa.employee_id
WHERE pa.project_id IS NULL ;

Scenario 5:- List all courses along with the students enrolled, including courses with no students.

SELECT c.course_id, c.course_name, s.name AS student_name
FROM courses c
LEFT JOIN enrollments e
    ON c.course_id = e.course_id
LEFT JOIN students s
    ON e.student_id = s.student_id ;

Scenario 6:- Retrieve the total stock of each product across all warehouses, including products with zero or missing stock in certain warehouses.

SELECT p.product_id, p.product_name,
    COALESCE( SUM(w.stock_quantity), 0 ) AS total_stock
FROM products p
LEFT JOIN warehouse_stock w
    ON p.product_id = w.product_id
GROUP BY p.product_id, p.product_name ;

Scenario 7:-Retrieve all products and their average sales per region, including products with no sales. Filter the results to show only those products whose average sales per region are below a threshold (e.g., $500).

SELECT
    p.product_id,
    p.product_name,
    r.region_name,
    COALESCE( AVG( s.sale_amount ), 0 ) AS avg_sales
FROM products p
LEFT JOIN sales s
    ON p.product_id = s.product_id
LEFT JOIN regions r
    ON s.region_id = r.region_id
GROUP BY p.product_id, p.product_name, r.region_name
HAVING COALESCE(AVG(s.sale_amount), 0) < 500 ;

Scenario 8:- Generate a report of all users and their subscription details for the current month. Include users who haven’t subscribed yet.

SELECT
    u.user_id,
    u.name AS user_name,
    s.subscription_date,
    s.subscription_plan
FROM users u
LEFT JOIN ksubscriptions s
    ON u.user_id = s.user_id
    AND s.subscription_date BETWEEN DATEADD( MONTH ,DATEDIFF( MONTH , 0, GETDATE()), 0)
    AND DATEADD( MONTH ,DATEDIFF( MONTH , 0, GETDATE()) + 1, 0) - 1 ;

Scenario 9:- Identify customers with orders where shipment dates exceeded the promised delivery dates, including orders without shipments.

SELECT
    c.customer_id, c.customer_name, o.order_id, o.promised_delivery_date, s.shipment_date
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
LEFT JOIN shipments s
    ON o.order_id = s.order_id
WHERE s.shipment_date > o.promised_delivery_date
    OR s.shipment_date IS NULL ;

Scenario 10:- Rank all customers and products by sales, including those with no sales data.

SELECT *,

    RANK() OVER ( PARTITION BY p.product_id ORDER BY total_sales DESC ) AS sales_rank
FROM (
    SELECT p.product_id,p.product_name,c.customer_name, SUM (s.amount) AS total_sales FROM products p LEFT JOIN sales s
      ON p.product_id = s.product_id
      LEFT JOIN customers c
        ON s.customer_id = c.customer_id
      GROUP BY p.product_id, p.product_name, c.customer_name )ranked ;

Scenario 11:- Retrieve sales representatives and their rolling 3-month sales totals, including those with no sales in the period.

WITH SalesData AS (
    SELECT
      s.rep_id,
      s.sale_date,
      s.amount,
      DATEPART( MONTH , s.sale_date ) AS sale_month
    FROM sales s
) ,
RollingSales AS (
    SELECT
      sd.rep_id,
      SUM( sd.amount ) OVER ( PARTITION BY sd.rep_id ORDER BY sd.sale_month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW ) AS rolling_total
    FROM SalesData sd
)
SELECT
    sr.rep_id,
    sr.rep_name,
    rs.rolling_total
FROM sales_representatives sr
LEFT JOIN RollingSales rs
    ON sr.rep_id = rs.rep_id ;

Common Errors with LEFT JOIN

Error Explanation Solution
Forgetting NULL Handling Rows from the right table with no match will have NULL values. Use WHERE column IS NULL to handle missing data when required.
Filtering in WHERE Instead of ON Adding right table filters in the WHERE clause negates the effect of the LEFT JOIN. Place filters on the right table in the ON clause instead of WHERE.
Incorrect Join Columns Using the wrong columns in the join condition results in incorrect or empty results. Verify the logical relationship between the tables and columns used in the join condition.
Performance Issues Joining large tables without indexes leads to slow queries. Ensure proper indexing on join columns and filter unnecessary data before the join.
Ambiguous Column Names When tables have columns with the same name, the query throws an ambiguity error. Use table aliases or fully qualify column names in the query.


Performance Hints for LEFT JOIN

Hint Description
Index Join Columns Create indexes on the columns used in the ON clause to speed up the join operation.
Filter Before Join Use subqueries or Common Table Expressions (CTEs) to filter rows before performing the LEFT JOIN.
Avoid Unnecessary Joins Exclude unrelated tables to minimize complexity and execution time.
Use Explain Plan Check the query execution plan to identify bottlenecks and improve query design.


Do's and Don'ts for LEFT JOIN

Do's Don'ts
Use LEFT JOIN when you need all rows from the left table, even if no match exists in the right table. Don’t use LEFT JOIN when you only need matching rows; use INNER JOIN instead.
Ensure join columns are indexed for better performance. Don’t filter right table rows in the WHERE clause; it will act like an INNER JOIN.
Use IS NULL to identify missing matches in the right table. Don’t assume all rows from the left table will have a match in the right table.
Use table aliases to improve query readability and avoid ambiguity. Don’t join unnecessary tables, as it increases complexity and impacts performance.
Test your query with sample data to validate the join logic. Don’t forget to review execution plans for complex joins involving large datasets.
