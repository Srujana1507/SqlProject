Materialized Views


What is a Materialized View?

A Materialized View is a database object that contains the results of a query and allows faster access to data by avoiding re-execution of complex queries.


  • Unlike a regular view (which is a virtual table), a materialized view contains actual data, making it faster to retrieve large or complex query results and can be refreshed periodically or on demand.
  • It is commonly used in scenarios requiring frequent access to aggregated or precomputed data.

Syntax

CREATE MATERIALIZED VIEW view_name
[BUILD IMMEDIATE | BUILD DEFERRED]
[REFRESH FAST | REFRESH COMPLETE | REFRESH FORCE | REFRESH ON DEMAND | REFRESH ON COMMIT ]
AS
    SELECT column1, column2, . . .
    FROM
    WHERE condition ;


Key Points

Aspect Details
Definition Materialized views store query results physically on disk, unlike regular views that execute the query dynamically each time they are accessed.
Usage Ideal for precomputing expensive queries, aggregations, or joins on large datasets to improve performance.
Refresh Modes
  • FAST:- Refreshes only changed data using logs.
  • COMPLETE:- Rebuilds the entire view.
  • FORCE:- Chooses between FAST or COMPLETE automatically.
Build Options
  • IMMEDIATE:- Builds the materialized view immediately after creation.
  • DEFERRED:- Builds it later when the first refresh occurs.
Refresh Timing
  • ON DEMAND:- Refreshes manually when triggered.
  • ON COMMIT:- Refreshes automatically when changes occur in the base tables.
Indexes Can have indexes for faster querying, unlike regular views.
Storage Requires additional storage since the data is physically stored on disk.


Advantages of Materialized View

Advantage Explanation
Performance Improvement Speeds up complex queries by avoiding repeated computation and directly fetching precomputed results.
Aggregated Data Storage Stores pre-aggregated results, reducing the load on the base tables.
Reduced Server Load Minimizes the need to recompute heavy queries.
Reduced Query Complexity Simplifies application queries by encapsulating complex logic within the materialized view.
Periodic or On-Demand Refresh Keeps data up to date based on refresh intervals or manual triggers.
Scalability Enhances query performance in data-intensive applications and large-scale databases.
Optimized Aggregation Ideal for analytical and reporting use cases involving complex calculations.
Flexibility in Refreshing Data Allows refresh modes to balance accuracy and performance based on application needs.


Basic Scenarios

Scenario 1:- (Precomputed Regional Sales Summary) Summarize sales data by region to improve performance in reporting.

CREATE MATERIALIZED VIEW regional_sales_summary_mv
REFRESH COMPLETE
AS
    SELECT
      region, SUM(sales) AS total_sales
    FROM sales_data
    GROUP BY region ;


Scenario 2:- (Frequent Access to Recent Orders)Create a materialized view to quickly retrieve orders placed in the last 7 days.

CREATE MATERIALIZED VIEW Latest_orders_mv
REFRESH ON DEMAND
AS
    SELECT
      order_id, customer_id, order_date, total_amount
    FROM Orders
    GROUP BY order_date > SYSDATE - 7 ;


Scenario 3:- (Regional Customer Summary)Create a materialized view that precomputes the number of customers in each region.

CREATE MATERIALIZED VIEW RegionalCustomerSummary_mv
BUILD IMMEDIATE
REFRESH FAST ON COMMIT
AS
    SELECT
      RegionID,
      COUNT(CustomerID) AS TotalCustomers
    FROM Customers
    GROUP BY RegionID ;


Scenario 4:- (Frequently Accessed Product Details)Create a materialized view to store product details for high-traffic queries.

CREATE MATERIALIZED VIEW ProductDetails_mv
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
AS
    SELECT
      ProductID,
      ProductName,
      Price,
      Category
    FROM Products ;


Comprehensive Scenarios

Scenario 1:- (Frequently Accessed Product Details)Create a materialized view to store product details for high-traffic queries.

CREATE MATERIALIZED VIEW sales_performance_mv
REFRESH FAST
AS
    SELECT
      category,
      SUM(sales) AS total_sales,
      COUNT(order_id) AS total_orders
    FROM Orders
    WHERE order_date >= TRUNC(SYSDATE, 'Q')
    GROUP BY category ;


Scenario 2:- (Sales Growth Analysis)Precompute sales growth percentage for reporting.

CREATE MATERIALIZED VIEW SalesGrowth_mv
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
AS
    SELECT
      Year ,
      SUM(SaleAmount) AS TotalSales,
      LAG( SUM(SaleAmount) ) OVER ( ORDER BY Year ) AS PreviousYearSales,
      ((SUM(SaleAmount) - LAG(SUM(SaleAmount)) OVER ( ORDER BY Year ) ) /
      LAG(SUM(SaleAmount)) OVER ( ORDER BY Year ) ) * 100 AS GrowthPercentage
    FROM Sales
    GROUP BY Year ;


Scenario 3:- (Data Warehousing (Star Schema)) Precompute aggregated metrics for faster reporting in a star schema.

CREATE MATERIALIZED VIEW StarSchemaMetrics_mv
BUILD IMMEDIATE
REFRESH COMPLETE ON DEMAND
AS
    SELECT
      d.DateID,
      p.ProductID,
      SUM( f.SaleAmount ) AS TotalSales,
      COUNT( f.SaleID ) AS TotalTransactions
    FROM
      FactSales f
    JOIN
      DimDate d ON f.DateID = d.DateID
    JOIN
      DimProduct p ON f.ProductID = p.ProductID
    GROUP BY
      d.DateID, p.ProductID
    ;


Scenario 4:- (Revenue Impact of Promotions) Calculate revenue impact by comparing sales during promotional periods to regular sales periods.

CREATE MATERIALIZED VIEW promo_revenue_impact_mv
REFRESH COMPLETE
AS
    SELECT
      promotion_id,
      SUM(
        CASE WHEN is_promo = 1 THEN sales
        ELSE 0
        END ) AS promo_sales,
      SUM(
        CASE WHEN is_promo = 0 THEN sales
        ELSE 0
        END ) AS regular_sales
    FROM
      sales_data
    GROUP BY
      promotion_id
    ;


Scenario 5:- (Multi-Dimensional Revenue and Profit Analysis) Create a materialized view that calculates revenue, profit margins, and growth rates across multiple dimensions (region, product category, and quarter) for the last 3 years. This view supports business intelligence tools by providing pre-aggregated data for faster analysis.

CREATE MATERIALIZED VIEW revenue_profit_analysis_mv
BUILD IMMEDIATE
REFRESH COMPLETE
AS
    SELECT
      region,
      category,
      TO_CHAR(order_date, 'YYYY-Q') AS quarter,
      SUM( sales_amount ) AS total_revenue,
      SUM(sales_amount - cost_amount) AS total_profit,
      ROUND(( SUM( sales_amount - cost_amount ) / NULLIF( SUM( cost_amount), 0 )) * 100, 2 ) AS profit_margin ,
      ROUND((SUM(sales_amount) -
      LAG(SUM(sales_amount)) OVER ( PARTITION BY region, category ORDER BY TO_CHAR(order_date, 'YYYY-Q'))) /
      NULLIF ( LAG(SUM(sales_amount)) OVER ( PARTITION BY region, category ORDER BY TO_CHAR(order_date, 'YYYY-Q')), 0)
      * 100, 2) AS revenue_growth
FROM
    sales_data
WHERE
    order_date >= ADD_MONTHS(TRUNC(SYSDATE, 'YYYY'), -36)
GROUP BY
    region, category, TO_CHAR(order_date, 'YYYY-Q')
;


Scenario 6:- (Real-Time Fraud Detection Metrics) Monitor potential fraudulent transactions by creating a materialized view that tracks transaction anomalies in real-time. The view identifies customers with unusually high transaction amounts compared to their average, flagging them for further review.

CREATE MATERIALIZED VIEW fraud_detection_metrics_mv
BUILD IMMEDIATE
REFRESH FAST
AS
    SELECT
      t.customer_id,
      COUNT(t.transaction_id) AS total_transactions,
      AVG(t.amount) AS avg_transaction_amount,
      MAX(t.amount) AS highest_transaction_amount,
        CASE
          WHEN MAX(t.amount) > ( AVG( t.amount) * 3 ) THEN 'High Risk'
          WHEN MAX(t.amount) > ( AVG( t.amount) * 2 ) THEN 'Medium Risk'
          ELSE 'Low Risk'
        END AS fraud_risk_level
    FROM
      transactions t
    JOIN
      customer_profiles c ON t.customer_id = c.customer_id
    WHERE
      t.transaction_date >= SYSDATE - 30 - - Last 30 days
    GROUP BY
      t.customer_id
    ;


Common Errors

Error Explanation Solution
ORA-12008: Error in Refresh Path Occurs during refresh due to issues in base table configuration or missing logs. Check if the base table has necessary materialized view logs for FAST refresh.
ORA-12015: Cannot Create FAST Refresh Happens if the query is not eligible for FAST refresh (e.g., lacks primary key or uses unsupported clauses). Simplify the query or use COMPLETE refresh mode.
Insufficient Storage Space Materialized views consume disk space and may exceed allocated storage limits. Monitor and allocate sufficient storage for materialized views.
Stale Data in View Data may become outdated if the refresh is not frequent enough. Use REFRESH ON COMMIT or schedule frequent manual refreshes.
Performance Overhead During Refresh Heavy refresh operations may impact database performance. Schedule refresh operations during low-traffic periods.


Hints to Write Materialized Views

Hint Explanation
Choose Appropriate Refresh Mode Use FAST refresh for incremental updates and COMPLETE refresh for full rebuilds.
Use Materialized View Logs Enable logs on base tables to improve refresh performance.
Index Key Columns Add indexes to frequently queried columns to speed up query execution.
Monitor View Usage Regularly analyze materialized view usage to determine if it's still relevant and cost-effective.
Partition Large Tables Partition base tables to improve refresh performance for large datasets.
Filter Unnecessary Data Use WHERE clauses to limit the data stored in the view.
Schedule Refresh Intervals Optimize refresh times during low database traffic.


Do's and Don'ts

Do's Don'ts
Use materialized views for complex queries accessed frequently. Don't use materialized views for data that changes constantly unless necessary.
Regularly refresh materialized views to maintain data accuracy. Avoid nesting materialized views within other materialized views unless explicitly required.
Use ON COMMIT refresh mode for near real-time updates. Don't store unnecessary columns or excessive data in materialized views to save storage space.
Monitor query performance and rebuild views as needed. Avoid creating materialized views with overly complex queries that are hard to maintain.
Test refresh performance on production-like data. Don't rely solely on materialized views for critical operations without considering refresh overhead.
