RIGHT JOIN or RIGHT OUTER JOIN

A RIGHT JOIN (also known as a RIGHT OUTER JOIN) retrieves all rows from the right table and the matching rows from the left table.


If no match exists in the left table, the result will include NULL values for the columns from the left table.


Syntax

SELECT left_table.column1, right_table.column2, . . .
FROM left_table
RIGHT JOIN right_table
ON left_table.common_column = right_table.common_column ;

Key points

Key Point Description
Behavior The query preserves all rows from the right table and includes NULL values for columns from the left table where there is no match.
Usage Used when you want to ensure that no data is excluded from the right table, even if there is no matching record in the left table.
Alternative RIGHT JOIN is less common than LEFT JOIN. In most scenarios, RIGHT JOIN can be rewritten as LEFT JOIN by swapping the tables.

Examples

Scenario 1:- Retrieve all orders, including those without a matching customer.

SELECT o.OrderID, o.Amount, c.CustomerName
FROM Customers c
RIGHT JOIN Orders o
ON c.CustomerID = o.CustomerID ;

Scenario 2:- List all departments, including those without assigned employees.

SELECT d.DepartmentName, e.EmployeeID, e.Name
FROM Employees e
RIGHT JOIN Departments d
ON e.DepartmentID = d.DepartmentID ;

Scenario 3:- Retrieve orders with customer and shipping info — only if shipping exists.

SELECT o.OrderID, o.Amount, c.CustomerName, s.ShippingDate
FROM Customers c
RIGHT JOIN Orders o
ON c.CustomerID = o.CustomerID
RIGHT JOIN Shipping s ON o.OrderID = s.OrderID ;

Scenario 4:- Calculate total revenue per supplier for all sold products.

SELECT s.SupplierName, SUM( p.Price * od.Quantity ) AS TotalRevenue
FROM Suppliers s
RIGHT JOIN Products p
ON s.SupplierID = p.SupplierID RIGHT JOIN OrderDetails od
ON p.ProductID = od.ProductID GROUP BY s.SupplierName ;

Scenario 5:- Retrieve orders that do not have any associated customers.

SELECT o.OrderID, o.Amount
FROM Customers c
RIGHT JOIN Orders o
ON c.CustomerID = o.CustomerID
WHERE c.CustomerID IS NULL ;

Scenario 6:- List all orders and the most recent shipping date for each, even if shipping has not occurred.

SELECT o.OrderID, o.Amount, s.ShippingDate
FROM
    ( SELECT OrderID, MAX(ShippingDate) AS ShippingDate
    FROM Shipping
    GROUP BY OrderID ) s
RIGHT JOIN Orders o ON s.OrderID =o.OrderID ;

Scenario 7:- Retrieve all orders and their customer's total purchase amount, including orders without customers.

SELECT o.OrderID, o.Amount, SUM(o.Amount)
OVER ( PARTITION BY c.CustomerID ) AS TotalSpent FROM Customers c
RIGHT JOIN Orders o
ON c.CustomerID = o.CustomerID ;

Scenario 8:- Retrieve all deliveries and their associated suppliers, including deliveries missing supplier details or with inactive suppliers.

SELECT d.delivery_id, d.delivery_date, s.supplier_id, s.supplier_name, s.supplier_status
FROM suppliers s
RIGHT JOIN deliveries d
ON s.supplier_id = d.supplier_id
WHERE s.supplier_id IS NULL OR s.supplier_status = 'Inactive' ;

Scenario 9:- Identify products that were not sold during a specific time period by comparing the inventory with sales data.

SELECT i.product_id, i.product_name
FROM sales s
RIGHT JOIN inventory i
ON s.product_id = i.product_id
GROUP BY i.product_id,i.product_name
HAVING SUM (
    CASE WHEN s.sale_date BETWEEN '2024-01-01' AND '2024-12-31' THEN 1 ELSE 0 END ) = 0 ;

Scenario 10:- Compare department average salary with company-wide average salary.

WITH CompanyAverage AS
( SELECT AVG(salary) AS overall_avg_salary FROM employees)
SELECT d.department_id, d.department_name, AVG( e.salary ) AS Dept_Avg_Salary
FROM employees e
RIGHT JOIN departments d
ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name
HAVING AVG( e.salary ) <
( SELECT overall_avg_salary FROM CompanyAverage ) ;

Scenario 11:- Retrieve all offices and the benefits provided, including offices with no employees.

SELECT o.office_id, o.office_name, b.benefit_id, b.benefit_name,
COALESCE( e.employee_count, 0 ) AS employee_count
FROM benefits b
RIGHT JOIN offices o
ON b.office_id = o.office_id LEFT JOIN (
SELECT office_id, COUNT( * ) AS employee_count
FROM employees
GROUP BY office_id ) e
ON o.office_id = e.office_id ;

Common Errors with RIGHT JOIN

Error Explanation Solution
Incorrect or missing ON clause Without a proper ON clause, results may be incorrect or produce a Cartesian product. Always define the correct condition in the ON clause to match related columns.
NULL values causing calculation issues Columns from the left table may have NULL values, which can impact aggregates or filters. Use functions like COALESCE() to handle NULLs gracefully.
Misplaced filtering of right table rows Applying filters to the right table in the WHERE clause can exclude required rows from the output. Place such filters in the ON clause to retain unmatched rows.
Over-reliance on RIGHT JOIN RIGHT JOIN can sometimes confuse readers or be less intuitive. Consider switching table positions and using LEFT JOIN for better clarity.
Ambiguous Column Names Columns with the same name in both tables cause ambiguity errors. Use table aliases or fully qualify column names in the query.
Unnecessary Complexity Using RIGHT JOIN when a LEFT JOIN with swapped table order would suffice. Evaluate whether a LEFT JOIN with reordered tables achieves the same result more clearly.


Performance Hints for RIGHT JOIN

Hint Description
Index Join Columns Ensure the columns in the ON clause are indexed to improve join performance.
Filter Data Before the Join Use subqueries or Common Table Expressions (CTEs) to filter data before performing the RIGHT JOIN.
Avoid Joining Large Tables Unnecessarily Limit the number of rows in both tables by filtering or using pre-aggregated data.
Use Execution Plans Analyze the query's execution plan to identify and resolve bottlenecks in the join.
Select Only Needed Columns Avoid using SELECT * to reduce the data size being processed and transferred.


Do's and Don'ts for RIGHT JOIN

Do's Don'ts
Use RIGHT JOIN when all rows from the right table are required, even without matches in the left table. Don’t use RIGHT JOIN if a LEFT JOIN with reordered tables suffices; it can be clearer.
Handle NULL values properly in the left table. Don’t filter right table rows in the WHERE clause if you want unmatched rows in the results.
Verify the join logic to ensure accurate relationships. Don’t join unrelated or excessively large datasets without filtering or proper design.
Use table aliases to simplify queries and improve readability. Don’t forget to check query performance, especially for complex or multi-table RIGHT JOINs.
Test with small datasets to validate the query logic before scaling up. Don’t assume all rows from the left table will have corresponding matches in the right table.
