Check

A Check Constraint in SQL is used to specify a condition that must be met for the data to be inserted or updated in a table.


It enforces domain integrity by restricting the types of data that can be stored in a column.


Key Points

Aspect Details
Purpose To enforce specific conditions or rules on data in a column or table.
Behavior Enforces the rule during INSERT and UPDATE operations.
Multiple Constraints Multiple CHECK constraints can be defined on a single column or table.
Scope Can reference one or multiple columns in the same table.
Non-Referential Cannot reference columns in other tables, only the current table.
Validation Ensures that data entered into a column meets predefined criteria.
Cannot Reference Other Tables The condition must be self-contained to the table where it is defined.

Syntax

1. Defining a CHECK Constraint During Table Creation

CREATE TABLE table_name (
    column_name data_type CHECK ( condition ) ) ;

2. Adding a CHECK Constraint to an Existing Table

ALTER TABLE table_name
    ADD CONSTRAINT constraint_name CHECK ( condition ) ;

3. Dropping a CHECK Constraint

---SQL and Oracle
ALTER TABLE table_name
    DROP CONSTRAINT constraint_name ;

Advantages of Check Constraints

Advantage Description
Data Validation Ensures data adheres to specific rules, reducing data quality issues.
Simplifies Application Logic Moves validation logic from application code to the database layer.
Automatic Enforcement Automatically enforces rules during data manipulation (insert/update).
Customizable Rules Allows for precise control of acceptable data formats and ranges.

Examples

Scenario 1:- Validating Age Range for Employees.

CREATE TABLE employees (
    employee_id INT PRIMARY KEY ,
    name VARCHAR(100),
    age INT CHECK ( age >= 18 AND age <= 65) ) ;

Scenario 2:- Restricting Positive Values for Salary.

CREATE TABLE jobs (
    job_id INT PRIMARY KEY ,
    job_title VARCHAR(100),
    salary DECIMAL(10, 2) CHECK (salary > 0) ) ;

Scenario 3:- Allowing Only Specific Values for Gender. (Ensure that the Gender column only accepts values 'M', 'F', or 'O'.)

CREATE TABLE students (
    student_id INT PRIMARY KEY ,
    name VARCHAR(100),
    gender CHAR(1) CHECK ( gender IN ('M', 'F', 'O')) ) ;

Scenario 4:- Enforcing Valid Email Format.

---SQL
CREATE TABLE users (
    user_id INT PRIMARY KEY ,
    email VARCHAR(255) CHECK (POSITION ('@' IN email)>1) ) ;

Scenario 5:- Ensuring Date Consistency.

CREATE TABLE projects (
    project_id INT PRIMARY KEY ,
    project_name VARCHAR(100),
    start_date DATE,
    end_date DATE,
    CHECK (end_date > start_date) ) ;

Scenario 6:- Adding a CHECK Constraint to Existing Table.

ALTER TABLE products
    ADD CONSTRAINT chk_price_positive CHECK (price > 0) ;

Scenario 7:- Ensure that the Age column in the Users table contains values between 18 and 60.

CREATE TABLE Users (
    UserID INT PRIMARY KEY ,
    UserName VARCHAR(100),
    Age INT,
    CONSTRAINT CHK_Age CHECK (Age BETWEEN 18 AND 60) ) ;

Scenario 8:- (Limiting Character Length) Ensure that ProductCode in the Products table does not exceed 10 characters.

CREATE TABLE Products (
    ProductID INT PRIMARY KEY ,
    ProductCode VARCHAR(20),
    CONSTRAINT CHK_ProductCode CHECK (CHAR_LENGTH (ProductCode) <= 10 ) ) ;

Scenario 9:- Ensure that the JoiningDate column does not contain future dates.

CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    JoiningDate DATE,
    CONSTRAINT CHK_JoiningDate CHECK ( JoiningDate <= CURRENT_DATE) ) ;

Scenario 10:- Custom Validation Ensure that Discount is less than Price.

CREATE TABLE Sales (
    SaleID INT PRIMARY KEY ,
    Price DECIMAL(10, 2),
    Discount DECIMAL(10, 2),
    CONSTRAINT CHK_Discount CHECK (Discount <= Price) ) ;

Scenario 11:- Using IN Allowing Only Specific Categories.

CREATE TABLE product_categories (
    product_id INT PRIMARY KEY ,
    category VARCHAR(50) CHECK (category IN ('Electronics', 'Furniture', 'Clothing')) ) ;

Cascading Scenarios with CHECK Constraints

Although CHECK constraints don't inherently support cascading actions (like cascading updates or deletes associated with foreign keys), cascading logic can be enforced indirectly through triggers or procedural logic.


Scenario 1:- ( Cascading Validation Between Two Columns )

CREATE TABLE employees (
    employee_id INT PRIMARY KEY ,
    job_type VARCHAR(20) CHECK ( job_type IN ('Permanent', 'Contract')),
    work_hours INT,
      CHECK (
        (job_type = 'Permanent' AND work_hours <= 40) OR
        (job_type = 'Contract' AND work_hours <= 60) )) ;


---Ensure that if an employee's job type is "Permanent," their work hours cannot exceed 40 hours per week, but if the job type is "Contract," work hours can go up to 60 hours per week.

Scenario 2:- Ensure that Salary is greater than 5000 for managers and 3000 for staff.

CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY ,
    EmployeeName VARCHAR(100),
    Designation VARCHAR(50),
    Salary DECIMAL(10, 2),
    CONSTRAINT CHK_SalaryDesignation CHECK (
      (Designation = 'Manager' AND Salary >= 5000) OR
      (Designation = 'Salesman' AND Salary >= 3000) ) ) ;

Scenario 3:- Ensure that for a project table, the completion_date must not be later than 30 days after the due_date to prevent excessive delays.

---postgreSQL and MYSQL

CREATE TABLE Projects (
    project_id INT PRIMARY KEY ,
    project_name VARCHAR(100),
    due_date DATE,
    completion_date DATE,
    CHECK (completion_date <= due_date + INTERVAL '30 DAY') ) ;

Common Erros with CHECK

Error Explanation Solution
Condition Is Always True/False Constraint condition does not provide meaningful validation. Ensure the CHECK condition is logically sound and aligns with the data model.
Violation During Data Insert/Update Attempt to insert/update a value that violates the constraint. Correct the data to satisfy the condition or revise the CHECK constraint.
Referencing Other Tables CHECK constraints cannot reference columns from other tables. Use triggers or procedures if cross-table validation is required.
Unsupported Functions Certain database functions cannot be used in CHECK. Ensure the condition only uses valid expressions and operators.

Performance Hints for CHECK

Hint Description
Define Clear Rules Ensure conditions are logical and relevant to the data.
Combine with Other Constraints Use CHECK alongside primary keys, foreign keys, and NOT NULL constraints for comprehensive validation.
Test Before Adding Validate existing data in the table against the new CHECK condition before applying it.
Use Descriptive Names Provide meaningful names for constraints for easier management and debugging.
Avoid Overcomplexity Keep conditions simple to avoid performance issues during data validation.

Do's and Don'ts with CHECK

Do's Don'ts
Use CHECK constraints to enforce rules. Don’t use CHECK constraints for cross-table validations; use triggers instead.
Test the constraint logic before applying. Don’t define overly complex conditions that affect performance.
Combine with other constraints as needed. Don’t use unsupported functions or operators in the CHECK condition.
Keep the condition readable and simple. Don’t apply a CHECK constraint without understanding its impact on existing data.
