Primary Key

A Primary Key is a column or a combination of columns in a table that uniquely identifies each row. It ensures that:


  • Each row in the table is unique.
  • No NULL values are allowed in the Primary Key column(s).

Key Points

Aspect Details
Uniqueness Each value in the Primary Key column must be unique.
NOT NULL Primary Key columns cannot contain NULL values.
Single Column or Composite A Primary Key can consist of a single column or a combination of columns (composite key).
Automatic Indexing Most databases automatically create a unique index on the Primary Key column(s) for fast lookups.
One Primary Key per Table Each table can have only one Primary Key.

Syntax

1. Defining a Primary Key During Table Creation

CREATE TABLE table_name (
    column_name data_type PRIMARY KEY ,
    other_column data_type ) ;

2. Composite Primary Key:

CREATE TABLE table_name (
    Column1 DataType,
    Column2 DataType,
    OtherColumn DataType,
    PRIMARY KEY (Column1, Column2) ) ;

3. Adding a Primary Key to an Existing Table:

ALTER TABLE table_name
    ADD CONSTRAINT PK_TableName PRIMARY KEY (ColumnName) ;

Behavior of Primary Key

Scenario Behavior
Inserting Duplicate Values Throws an error if a duplicate value is inserted into the Primary Key column.
NULL Values Throws an error if a NULL value is inserted into the Primary Key column.
Composite Key Ensures uniqueness across the combination of the specified columns.

Advantages of Primary Key

Advantage Description
Enforces Uniqueness Ensures each row in a table is unique.
Prevents NULL Values Ensures that every row has a valid value for the key column(s).
Supports Relationships Acts as a parent key for creating relationships between tables.
Improves Query Performance Automatically creates an index, improving the performance of queries involving the Primary Key.

Examples

Scenario 1:- Each user should have a unique UserID to identify them.

CREATE TABLE Users (
    UserID INT PRIMARY KEY , FullName VARCHAR(100),
    Email VARCHAR(150) ) ;

Scenario 2:- Composite Primary Key (Ensure that a combination of OrderID and ProductID is unique in the OrderDetails table.)

CREATE TABLE OrderDetails (
    OrderID INT,
    ProductID INT,
    Quantity INT,
    PRIMARY KEY ( OrderID, ProductID ) ) ;

Scenario 3:- Auto-Incrementing Primary Key (Use an auto-incrementing EmployeeID as the Primary Key for a table.)

CREATE TABLE Employees (
    EmployeeID INT AUTO_INCREMENT PRIMARY KEY ,
    FirstName VARCHAR(50),
    LastName VARCHAR(50),
    HireDate DATE ) ;

Scenario 4:- Adding a Primary Key to an Existing Table ( Add a Primary Key to the InvoiceID column of an existing Invoices table.)

ALTER TABLE Invoices
    ADD CONSTRAINT PK_Invoice PRIMARY KEY (InvoiceID) ;

Scenario 5:- Composite Primary Key for Unique Orders.

CREATE TABLE order_details (
    order_id INT,
    product_id INT,
    quantity INT,
    CONSTRAINT pk_order_details PRIMARY KEY (order_id, product_id) ) ;

Scenario 6:- Dropping an Existing Primary Key.

---SQL Server / PostgreSQL

ALTER TABLE employees
    DROP CONSTRAINT pk_employee_id ;

Scenario 7:- Auto-Incrementing Primary Key for Unique Identification.

CREATE TABLE products (
    product_id INT IDENTITY (1,1) PRIMARY KEY , product_name VARCHAR(100), price DECIMAL(10, 2)) ;

Scenario 8:- (Establish Relationships Between Tables) Create a Primary Key in the Departments table and reference it as a Foreign Key in the Employees table.

CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY , DepartmentName VARCHAR(100) ) ;
CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY , FirstName VARCHAR(50),
    LastName VARCHAR(50),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID) ) ;

Scenario 9:- (Primary Key with Partitioned Table) Create a table for transaction data where the TransactionID serves as the Primary Key and data is partitioned by Year.

CREATE TABLE Transactions (
    TransactionID INT NOT NULL ,
    amount DECIMAL(10,2),
    TransactionDate DATE NOT NULL, PRIMARY KEY (TransactionID,TransactionDate) )
    PARTITION BY RANGE ( YEAR (TransactionDate)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025) ) ;

Common Errors with PRIMARY KEY

Error Explanation Solution
Duplicate Key Value Attempt to insert a duplicate value in the primary key column. Ensure unique values before insertion.
NULL Value in Primary Key Column Attempt to insert a NULL value in the primary key column. Assign a valid, non-NULL value to the column.
Multiple Primary Keys in One Table Attempt to define more than one primary key for a table. Ensure only one primary key constraint is defined.
Primary Key Already Defined Attempt to add a primary key when one already exists. Check existing constraints before adding.
Foreign Key Reference Errors Inconsistent or missing reference to the primary key in related tables. Validate relationships and data consistency before defining constraints.

Performance Hints for PRIMARY KEY

Hint Description
Choose Columns Wisely Use columns that are stable, unique, and not likely to change frequently (e.g., ID fields).
Avoid Composite Keys If Possible refer single-column primary keys for simplicity unless composite keys are necessary.
Auto-Increment for IDs Use auto-incrementing columns (e.g., IDENTITY in SQL Server, SERIAL in PostgreSQL) for primary keys.
Avoid NULL and Redundancy Ensure that the column(s) defined as primary keys are non-NULL and not redundant.
Normalize Properly Use primary keys to ensure normalized table structures and avoid anomalies.

Do's and Don'ts with PRIMARY KEY

Do's Don'ts
Use primary keys to uniquely identify rows. Don’t use columns that may have duplicate or NULL values as primary keys.
Combine with foreign keys for relationships. Don’t use composite keys unnecessarily unless they truly represent unique combinations.
Use meaningful column names for keys. Don’t use columns with frequently changing values as primary keys (e.g., names, phone numbers).
Ensure uniqueness in data before defining. Don’t define a primary key on columns without considering database relationships and indexing.
