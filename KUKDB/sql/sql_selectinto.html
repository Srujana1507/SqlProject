SELECT INTO

SELECT INTO copies data from one table into a new table. The new table is created on the fly, inheriting column names and data types from the source table.


This is useful for creating backups, archiving data, or preparing subsets of data for analysis.


Key Features

Feature Description
New Table Creation Creates a new table dynamically without requiring a CREATE TABLE statement.
Data Copying Copies selected data (rows and columns) from an existing table.
Copies structure and data Copies both the schema and the data.
Data Types The new table inherits data types of the source table columns.
Flexibility Supports filters (e.g., WHERE, JOIN, etc.) to insert specific data into the new table.
Efficient for backups or subsets No need to manually create the table structure.
Does Not Work Everywhere In some databases (e.g., MySQL), SELECT INTO is not supported; INSERT INTO ... SELECT is used instead.
Temporary Tables Often used to create temporary tables for intermediate processing.


Syntax

SELECT column1, column2, . . .
    INTO new_table
    FROM existing_table
    WHERE condition ;


Behavior

  • The new table is created with the same structure (column names and data types) as the columns in the query.
  • If a table with the same name already exists, the query fails.
  • It does not copy indexes, constraints, or triggers from the source table.


Basic Scenarios

Scenario 1:- ( Copy All Data ) Create a view that shows customer names and their contact details (phone and email).

SELECT *
    INTO CustomersBackup
      FROM Customers ;


Scenario 2:- ( Copy Filtered Data ) Create a new table ActiveCustomers and copy data for only active customers.

SELECT CustomerID, CustomerName, Email
    INTO ActiveCustomers
      FROM Customers
        WHERE Status = 'Active' ;


Scenario 3:- ( Copy with Aggregate ) Create a new table SalesSummary with aggregated sales data by product.

SELECT ProductID, SUM(SaleAmount) AS Total_Sales
    INTO Sales_Summary
      FROM Sales
        GROUP BY ProductID ;


Scenario 4:- ( Archiving Completed Orders ) Archive orders that were completed before 2024.

SELECT order_id, customer_id, order_date
    INTO orders_archive
      FROM orders
        WHERE order_status = 'Completed'
          AND order_date < '2024-01-01' ;


Scenario 5:- ( Copying Table Structure Without Data ) Create a new table with the same structure as the original without data.

SELECT *
    INTO new_empty_table
      FROM existing_table
        WHERE 1 = 0 ;


Advanced Scenarios

Scenario 1:- ( Using JOIN ) Create a new table CustomerOrders that combines customer and order details.

SELECT c.CustomerID, c.CustomerName, o.OrderID, o.OrderDate, o.TotalAmount
    INTO Customer_Orders
      FROM Customers c
        JOIN Orders o ON c.CustomerID = o.CustomerID ;


Scenario 2:- (Partitioned Data Copy ) Create a table Orders 2024 to store orders from 2024.

SELECT *
    INTO Orders2024
      FROM Orders
        WHERE YEAR (OrderDate) = 2024 ;


Scenario 3:- ( Copy Data with Calculations ) Create a new table EmployeeSalaries with calculated annual salaries.

SELECT EmployeeID, EmployeeName, Salary, (Salary * 12) AS AnnualSalary
    INTO EmployeeSalaries
      FROM Employees ;


Scenario 4:- ( Copy and Transform Data ) Create a new table ProductCategories with unique product categories.

SELECT DISTINCT CategoryID, CategoryName
    INTO ProductCategories
      FROM Products ;


Scenario 5:- ( Exporting Monthly Sales Data for Reporting ) Export sales data for the last month into a new table for reporting purposes.

SELECT order_id, product_id, total_amount, order_date
    INTO monthly_sales_report
      FROM orders
        WHERE order_date >= DATEADD( MONTH , -1, GETDATE() ) ;


Scenario 6:- ( Temporary Table for ETL Processing ) Create a temporary table to store transformed customer data during ETL.

SELECT customer_id, UPPER(name) AS customer_name,
    CONCAT(city, ', ', state) AS location
INTO #transformed_customers
    FROM customers
      WHERE active_status = 'Active' ;


Scenario 7:- ( Backup Before Major Schema Changes ) Before adding a new column to a critical table, create a backup.

SELECT *
    INTO orders_backup
FROM orders ;

-- Proceed with schema modification
ALTER TABLE orders ADD COLUMN discount_rate DECIMAL(5, 2) ;


Scenario 8:- (Combining Historical and Current Data ) Create a table combining historical and current sales data for trend analysis.

SELECT *
INTO sales_trend_data
FROM (
    SELECT
      order_id,
      customer_id,
      total_amount,
      'Historical' AS data_type
    FROM historical_sales
    UNION ALL
    SELECT
      order_id,
      customer_id,
      total_amount,
      'current' AS data_type
    FROM current_sales
) combined_sales ;


Complex Scenarios

Scenario 1:- (Multi-Step Data Transformation for Business Intelligence ) Create a table that calculates yearly revenue growth for each product category by transforming and aggregating data from multiple tables.

-- Step 1: Extract yearly revenue data for each category
SELECT
    p.category_id,
    p.category_name,
    YEAR (order_date) AS year,
    SUM(total_amount) AS total_revenue
INTO yearly_revenue_data
FROM orders o
JOIN products p ON o.product_id = p.product_id
GROUP BY p.category_id,p.category_name, YEAR (order_date) ;

-- Step 2: Calculate revenue growth compared to the previous year
SELECT
    category_id,
    category_name,
    year,
    total_revenue,
    LAG(total_revenue) OVER ( PARTITION BY category_id ORDER BY year ) AS previous_year_revenue,
    CASE
      WHEN LAG(total_revenue) OVER ( PARTITION BY category_id ORDER BY year ) IS NOT NULL
      THEN (total_revenue - LAG(total_revenue) OVER ( PARTITION BY category_id ORDER BY year ) ) * 100.0 /
        LAG(total_revenue) OVER ( PARTITION BY category_id ORDER BY year )
      ELSE NULL
    END AS revenue_growth_percentage
INTO revenue_growth_analysis
FROM yearly_revenue_data ;


Scenario 2:- (Dynamic Data Backup with Partitioning ) Backup customer order data into separate tables based on geographical regions dynamically.

-- Step 1: Create a table for regions with their respective customer IDs.

SELECT DISTINCT region, customer_id
INTO region_customer_mapping
FROM customers ;

-- Step 2: Generate a backup table for each region.

DECLARE @region_name NVARCHAR(50) ;
DECLARE @query NVARCHAR(MAX);

DECLARE region_cursor
CURSOR FOR
SELECT DISTINCT region
FROM region_customer_mapping ;

OPEN region_cursor ;
FETCH NEXT FROM region_cursor INTO @region_name ;

WHILE @@FETCH_STATUS = 0
BEGIN
    SET @query =
      N' SELECT o.*
      INTO ' + QUOTENAME(@region_name + '_orders_backup') + '
      FROM orders o
      JOIN region_customer_mapping r ON o.customer_id = r.customer_id
      WHERE r.region = ''' + REPLACE(@region_name ,'''','''''')+'''';


    EXEC sp_executesql @query ;

    FETCH NEXT FROM region_cursor INTO @region_name ;
END ;

CLOSE region_cursor ;
DEALLOCATE region_cursor ;


Advantages of SELECT INTO

Advantage Description
Simplified Table Creation Eliminates the need for a separate CREATE TABLE statement.
Efficient Data Copy Combines table creation and data insertion in one operation.
Dynamic Structures Automatically inherits column data types from the source table.
Query Filtering Allows selective data copying using WHERE clauses and joins.
Flexible Usage Useful for backups, temporary tables, or creating subsets of data for analysis.


Common Errors with SELECT INTO

Error Description Solution
Table Already Exists Cannot create a new table if a table with the same name already exists. Ensure the table name is unique or use INSERT INTO instead.
Insufficient Permissions User lacks permission to create tables or select from the source table. Grant appropriate CREATE TABLE and SELECT permissions.
Column Ambiguity Columns in the query have the same name due to joins or aliases not used. Use proper aliases for columns in the SELECT statement.
Unsupported Constructs Certain constructs like subqueries with LIMIT may not be supported. Simplify the query or use a temporary table as an intermediate step.
Data Type Conversion Issues Implicit data type conversion may fail (e.g., string to integer). Ensure that the data types of selected columns are compatible with the new table requirements.
Unsupported in Database SELECT INTO is not supported in MySQL. Use INSERT INTO ... SELECT as an alternative.


Performance Hints for SELECT INTO

Hint Description
Filter Unnecessary Data Use WHERE clauses to copy only the required rows.
Avoid Large Data Sets Copying large tables can be resource-intensive. Limit data using filters.
Use Joins Effectively Optimize joins to avoid excessive computations before copying data.
Create Indexes After Copy Create indexes on the new table after the data is copied to improve performance.
Use Temporary Tables if Needed
  • For short-term data needs, consider creating temporary tables instead.
  • Use SELECT INTO #TempTable for temporary data storage.


Do's and Don'ts with SELECT INTO

Do's Don'ts
Use it for quick backups or data exports. Don’t use it where INSERT INTO ... SELECT is more appropriate.
Verify data before copying large tables. Don’t rely on SELECT INTO for production backups; use proper backup tools.
Ensure target table doesn’t already exist. Avoid using SELECT INTO in databases where it isn’t supported (e.g., MySQL).
Test queries on smaller datasets. Don’t assume the new table inherits constraints like primary keys or indexes.
Ensure appropriate permissions are granted. Don’t ignore data type compatibility.


Database-Specific Behaviors of SELECT INTO

Database Support SELECT INTo ? Note
SQL Server Fully Supported Automatically creates the new table. Commonly used for temporary tables (#TempTable).
Oracle Not Supported Use CREATE TABLE AS SELECT (CTAS) as an alternative.
MySQL Not Supported Use INSERT INTO ... SELECT or CREATE TABLE ... SELECT.
PostgreSQL Fully Supported Commonly used for data exports and creating intermediate tables.
SQLite Not Supported Use CREATE TABLE AS SELECT instead.
