Correlated Subqueries

A correlated subquery is a subquery that depends on values from the outer query for their execution.


  • A correlated subquery is executed repeatedly, once for each row evaluated by the outer query.
  • This creates a dependency between the subquery and the outer query.

Key Features

  • Dependency:- The subquery uses values from the outer query, making it "correlated" or linked.
  • Execution:- The subquery runs once for each row processed by the outer query.
  • Performance:- They can be less efficient compared to regular subqueries or joins because they involve repeated execution.

Syntax

SELECT column1, column2, . . .
FROM table1 outer_alias
WHERE column1 operator ( SELECT column_name
        FROM table2 inner_alias
        WHERE outer_alias.column_name = inner_alias.column_name ) ;

How It Works

  • The outer query iterates through its rows.
  • For each row in the outer query, the subquery executes using the current row's values.
  • The results of the subquery are used in the outer query's processing.

Basic Scenarios

1. Correlated Subquery in WHERE Clause

Scenario 1:- Find Employees Earning Above the Department Average

SELECT Name, DepartmentID, Salary
FROM Employees E
WHERE Salary > ( SELECT AVG(Salary)
FROM Employees E2 WHERE E2.DepartmentID = E.DepartmentID ) ;

- - For each row in the Employees table (outer query), the subquery calculates the average salary for that employee's department.
- - The main query then compares the employee's salary to their department's average.

Scenario 2:- Find Customers Who Placed More Than 3 Orders

SELECT CustomerID, Name
FROM Customers C
WHERE ( SELECT COUNT(*) FROM Orders O WHERE O.CustomerID = C.CustomerID ) > 3 ;

- - For each customer in the Customers table (outer query), the subquery counts the number of orders they have placed in the Orders table.
- - The main query filters customers with more than three orders.

2. Correlated Subquery in SELECT Clause

Scenario:- Retrieve each employee details along with total salary of their department

SELECT e1.employee_id, e1.name, e1.salary,
( SELECT SUM( e2.salary ) FROM employees e2
WHERE e1.department_id = e2.department_id ) AS department_total_salary
FROM employees e1 ;

- - For each employee (e1), the subquery calculates the total salary for the employee's department (e1.department_id).

3. Identify Products with Above-Average Sales

Scenario: Identify products with above average price within their category

SELECT ProductID, ProductName
FROM Products P
WHERE Price > ( SELECT AVG(Price) FROM Products P2 WHERE P2.CategoryID = P.CategoryID) ;

- - The subquery calculates the average price for products in the same category.
- - The main query filters products priced above their category average.

4. Correlated Subquery in UPDATE Statement

Scenario :- Increase the salary of employees whose salary is below their department's average.

UPDATE employees e1
SET salary = salary * 1.10
WHERE salary < ( SELECT AVG( e2.salary ) FROM employees e2 WHERE e1.department_id = e2.department_id ) ;

- - The subquery calculates the average salary for the department of each employee.
- - If the employee’s salary is below the average, it is increased by 10%.

5. Correlated Subquery in DELETE Statement

Scenario :- Delete products that have not been ordered.

DELETE FROM products p1
WHERE NOT EXISTS
( SELECT 1 FROM orders o WHERE o.product_id = p1.product_id ) ;

- - The subquery checks if a product (p1.product_id) exists in the orders table.
- - If no matching order exists, the product is deleted.

6. Correlated Subquery with NOT IN

Scenario :- Find employees who are not managers.

SELECT employee_id, name
FROM employees e1 WHERE e1.employee_id NOT IN
( SELECT DISTINCT manager_id FROM employees e2 WHERE e2.manager_id IS NOT NULL ) ;

- - The subquery retrieves all manager IDs.
- - The outer query excludes employees whose IDs appear in the manager list.

Advanced Scenarios

1. Aggregation with Correlated Subqueries

Scenario :- Find departments where all employees earn above $50,000.

SELECT department_id
FROM departments d WHERE NOT EXISTS
( SELECT 1 FROM employees e WHERE e.department_id = d.department_id AND e.salary < 50000 ) ;

- - The subquery ensures no employee in a department earns less than $50,000.
- - The outer query retrieves the department IDs.

2. Complex Filtering

Scenario :- Identify customers who have ordered more than their region's average order quantity.

SELECT c.customer_id, c.name
FROM customers c WHERE EXISTS
( SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
AND o.quantity > ( SELECT AVG( o2.quantity )
FROM orders o2 WHERE o2.region_id = o.region_id ) ) ;

Common Uses of Correlated Subqueries

  • Filtering Rows Based on Related Data:- E.g., Find employees working in a department with fewer than 10 people.
  • Performing Calculations Per Group:- E.g., Rank items based on a specific metric within a category.
  • Dynamic Comparisons:- E.g., Compare rows against dynamically calculated values like averages, maximums, or sums.

Performance Considerations

  • Execution Cost:- Each iteration of the outer query triggers the execution of the subquery. For large datasets, this can be costly.
  • Optimization:- Rewrite correlated subqueries as JOINs or use window functions where possible to improve performance.
  • Indexes:- Ensure that columns used in the correlated subquery conditions are indexed.

Do's and Don'ts with Correlated Subqueries

Do's

  • Use correlated subqueries for dynamic comparisons that require the outer query's context.
  • Ensure proper indexing of the columns involved in the subquery for better performance.
  • Use them for complex business logic when alternatives like joins are not viable.

Don'ts

  • Avoid correlated subqueries for large datasets unless absolutely necessary, as they can significantly slow down performance.
  • Do not use them when equivalent joins or window functions can achieve the same results more efficiently.
  • Minimize nesting levels to keep queries readable and maintainable.

Advantages and Disadvantages of Corelated Subqueries

Advantages

  • Simplicity in handling row-specific logic.
  • Useful for situations requiring row-by-row processing.
  • Enhances readability for straightforward comparisons.

Disadvantages

  • Can lead to performance degradation with large datasets.
  • Harder to debug and optimize compared to JOINs or window functions.
  • Often less efficient than alternative query designs.

Best Practices with Correlated Subqueries

1. Limit Subquery Results:-

  • Reduce the scope of the subquery by limiting their result set.

2. Use EXISTS for Better Performance

  • Replace IN with EXISTS when checking for existence.
- - Using EXISTS
SELECT Name
FROM employees E
WHERE EXISTS ( SELECT 1
        FROM Departments D
        WHERE D.DepartmentID = E.DepartmentID AND D.Location = 'New York' ;

3. Test on Sample Data

  • Always test on small datasets before applying to large tables.
