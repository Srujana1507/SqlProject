Transaction Control Language (TCL)

What is a Transaction?

  • A transaction in SQL is a group of one or more operations that are executed as a single logical unit of work.
  • A transaction ensures that either all the operations are successfully completed, or none of them are applied, maintaining data consistency and integrity.

Key Properties of Transactions (ACID)

Property Description
Atomicity Guarantees that either all operations succeed or none are applied.
Consistency Ensures the database remains valid before and after the transaction.
Isolation Ensures that concurrent transactions do not interfere with each other.
Durability Makes committed changes permanent, even after system failures.

Transaction Control Language (TCL)

  • Transaction Control Language (TCL) in SQL is used to manage and control transactions in a database.
  • It provides commands to ensure proper execution, commit changes, or roll back in case of failures.

Why We Need TCL

  • Data Integrity: Ensures consistent data updates, even during complex transactions.
  • Error Handling:Allows reversing or confirming operations based on success or failure or failure.
  • Concurrency control: Safely manages transactions when multiple users access the database simultaneously.
  • Critical use cases: Vital for domains like banking, e-commerce, inventory management, and booking systems where transactional reliability is key.

TCL Commands

Command Description
COMMIT Saves all changes in a transaction permanently.
ROLLBACK Reverts changes since last COMMIT or SAVEPOINT.
SAVEPOINT Marks a point to which you can ROLLBACK if needed.

Advantages of Using TCL

Advantage Description
Ensures Data Integrity Prevents partial updates on failure.
Provides Flexibility Allows partial rollbacks using SAVEPOINT.
Supports Concurrent Transactions Enables multiple safe transactions.
Improves Error Handling Transactions can be rolled back to handle failures gracefully.
Facilitates Complex Operations Ideal for multi-step processes.

Performance Hints to Improve Transactions

Hint Description
Minimize transaction duration Keep transactions short to reduce contention and improve concurrency.
Use proper isolation levels Choose the appropriate isolation level to balance consistency and performance.
Avoid locks on large data sets Use indexed queries and limit locks to necessary rows only.
Use savepoints judiciously Avoid excessive savepoints as they can increase transaction overhead.
Commit frequently in large operations Break large operations into smaller transactions and commit frequently to reduce resource usage.

Common Errors with Transactions

Error Description Solution
Uncommitted Transactions Forgetting to commit a transaction leads to locks and unavailability of resources. Always ensure transactions are committed or rolled back explicitly.
Invalid Savepoint Attempting to roll back to a non-existent or invalid savepoint. Create savepoints at appropriate stages and verify their existence before rolling back.
Deadlocks Two transactions block each other by holding resources the other needs. Minimize transaction duration and order resource access consistently.
Isolation Level Misconfiguration Setting an inappropriate isolation level causes performance issues or data anomalies. Use isolation levels suited for the operation (e.g., READ COMMITTED for most scenarios).
Nested Transactions Mismanagement Failing to handle nested transactions properly causes unintended rollbacks or commits. Use savepoints and explicit rollbacks to manage nested transactions.

Do’s and Don’ts with TCL

Do's Don'ts
Use explicit COMMIT and ROLLBACK to ensure proper transaction control. Don’t leave transactions open as they can cause locks.
Implement error handling mechanisms within transactions. Don’t use a high isolation level unnecessarily; it can degrade performance.
Break large transactions into smaller ones for better performance. Don’t include unrelated operations in the same transaction.
Test transactions thoroughly in development environments. Don’t forget to use savepoints for complex transactions.
Monitor transaction logs for troubleshooting and auditing. Don’t ignore deadlock or timeout errors; investigate them immediately.


COMMIT

  • Saves all modifications made in the current transaction to the database permanently.
  • After a COMMIT, the changes cannot be undone.

Syntax

COMMIT ;

Key Points

  • Automatically ends the transaction.
  • Implicit COMMIT is triggered automatically after DDL commands like CREATE, ALTER, or DROP in most RDBMS systems.

Advantages

  • Ensures data consistency by permanently saving changes.
  • Improves performance in multi-transaction environments by finalizing completed operations.
  • Simplifies auditing and tracking of data changes.
  • Helps in maintaining a clear boundary between operations in transactional workflows.
  • Enables sharing committed changes with other users and processes.

Examples

Scenario 1:- Ensures the new order is saved permanently.

INSERT INTO orders ( order_id, customer_id, amount )
VALUES ( 101, 1, 500.00 ) ;
COMMIT ;

Scenario 2:- ( Batch Insert with Error Handling ) Inserts multiple records in one transaction.

BEGIN TRANSACTION ;
INSERT INTO employees (id, name) VALUES (1, 'Harsha') ;
INSERT INTO employees (id, name) VALUES (2, 'Uday') ;
COMMIT ;

Scenario 3:- ( Completing a Payment ) Ensure changes made during a transaction (e.g., deducting an amount from one account and adding it to another) are permanently saved.

BEGIN TRANSACTION ;
UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountID = 101 ;
UPDATE Accounts SET Balance = Balance + 1000 WHERE AccountID = 102 ;
COMMIT ;

Scenario 4:- (Automatic Commit after DDL Command ) The CREATE command automatically commits the transaction.

CREATE TABLE audit_logs (
log_id INT PRIMARY KEY ,
log_message VARCHAR(255)
) ;

Scenario 5:- ( COMMIT After a Conditional Operation ) Deletes orders with low amounts and commits only if rows were affected.

BEGIN TRANSACTION ;
DELETE FROM orders WHERE amount < 50 ;
IF @@ROWCOUNT > 0
BEGIN
    COMMIT ;
END ;

Scenario 6:- ( Committing Changes in a Loop ) Logging System with Auto-Increment Messages.

BEGIN TRANSACTION ;
DECLARE @counter INT = 1 ;
WHILE @counter <= 10
BEGIN
    INSERT INTO logs (log_message) VALUES ('Log ' + CAST(@counter AS VARCHAR)) ;
    SET @counter = @counter + 1 ;
END ;
COMMIT ;

Common Errors with COMMIT

Error Explanation Solution
Cannot commit when auto-commit is on Auto-commit mode prevents explicit COMMIT. Disable auto-commit before using COMMIT.
Transaction already committed Attempting to commit an already committed transaction. Ensure no redundant commits are issued.
Changes not visible Changes seem not saved due to misinterpretation of isolation. Verify isolation level and ensure proper usage.

Do's and Don'ts with COMMIT

Do's Don'ts
Always COMMIT after successful transactions. Avoid implicit commits when explicit ones are needed.
Confirm all changes before issuing COMMIT. Don’t commit unless data integrity is confirmed.

ROLLBACK

  • Undoes changes made in the current transaction since the last COMMIT or to a specified SAVEPOINT.

Syntax

ROLLBACK ;

Key Points

  • Reverts the database to its last consistent state.
  • Changes made after the last COMMIT are discarded and not saved to the database.

Advantages

  • Prevents incorrect or incomplete data from being saved in case of errors.
  • Allows recovery from application or user errors during transaction execution.
  • Ensures database integrity by undoing uncommitted changes.
  • Helps maintain compliance with business rules and constraints.
  • Avoids potential cascading failures in dependent transactions.

Examples

Scenario 1:- Reverses a deletion if executed incorrectly.

DELETE FROM orders WHERE amount > 1000 ;
ROLLBACK ;

Scenario 2:- ( Rollback After a Failed Operation ) Reverts price updates in case of an error.

BEGIN TRANSACTION ;
UPDATE products SET price = price * 0.9 WHERE category = 'electronics' ;
IF @@ERROR > 0
    ROLLBACK ;
ELSE
    COMMIT ;

Scenario 3:- ( Rollback After Multiple Changes ) Undoes both the insert and update.

BEGIN TRANSACTION ;
    INSERT INTO employees ( id, name ) VALUES (3, 'Harsha') ;
    UPDATE employees SET name = 'Harsha' WHERE id = 3 ;
ROLLBACK ;

Scenario 4:- Rollback with Conditional Check.

BEGIN TRANSACTION ;
DELETE FROM orders WHERE customer_id = 1 ; IF NOT EXISTS ( SELECT * FROM orders WHERE customer_id = 1 )
    ROLLBACK ;
ELSE
    COMMIT ;

Scenario 5:- (Rollback After Exception Handling) Reverts changes if any statement fails.

BEGIN TRY
BEGIN TRANSACTION ;
    INSERT INTO accounts ( id, balance ) VALUES (1, 1000) ;
    UPDATE accounts SET balance = balance - 500 WHERE id = 1 ;
COMMIT ;
END TRY
BEGIN CATCH
    ROLLBACK ;
END CATCH ;

Scenario 6:- (Rollback After Exception Handling) Reverts changes if any statement fails.

BEGIN TRANSACTION ;
UPDATE Inventory SET Stock = Stock - 5 WHERE ProductID = 2001 ;
IF ( SELECT Stock FROM Inventory WHERE ProductID = 2001 ) < 0
THEN
    ROLLBACK ;
ELSE
    COMMIT ;
END IF ;


Common Errors with ROLLBACK

Error Explanation Solution
Transaction already rolled back Attempting to rollback a completed transaction. Ensure rollback occurs within transaction.
No transaction to rollback Issuing ROLLBACK outside of a transaction scope. Start a transaction before rollback.
Savepoint not found Rolling back to an invalid or non-existent savepoint. Verify savepoint existence.


Do's and Don'ts with ROLLBACK

Do's Don'ts
Use ROLLBACK to handle transaction errors. Don’t issue ROLLBACK unnecessarily.
Combine with SAVEPOINT for partial undoing. Avoid nested rollbacks without clear logic.

SAVEPOINT

  • Sets a point within a transaction to which you can rollback without affecting earlier changes.

Syntax

SAVEPOINT savepoint_name ; ROLLBACK TO savepoint_name ;


Advantages

  • Provides finer control by allowing partial rollbacks within a transaction.
  • Enhances error recovery in complex transactions.
  • Reduces overhead by avoiding full transaction rollbacks when only specific steps fail.
  • Makes debugging and fixing issues in multi-step processes easier.
  • Allows reusing transactional logic in modular or iterative workflows.

Examples


Scenario 1:- (Basic Savepoint Usage) Rolling Back Low-Value Order Adjustments.

BEGIN TRANSACTION ; DELETE FROM orders WHERE amount < 50 ;
SAVEPOINT sp_low_amounts ;
UPDATE orders SET amount = amount * 1.1 WHERE amount BETWEEN 50 AND 100 ;
ROLLBACK TO sp_low_amounts ;

Scenario 2:- (Partial Rollback) Undoing Partial Customer Data Changes.

BEGIN TRANSACTION ;
INSERT INTO customers ( id, name ) VALUES (1, 'Uday') ;
SAVEPOINT sp_insert ;
DELETE FROM orders WHERE customer_id = 1 ;
ROLLBACK TO sp_insert ;

Scenario 3:- (Savepoint for Error Recovery) Error Recovery in Account Transactions.

BEGIN TRANSACTION ;
INSERT INTO accounts ( id, balance ) VALUES (1, 500) ;
SAVE TRANSACTION sp_insert ;
BEGIN TRY
    UPDATE accounts SET balance = balance - 1000 WHERE id = 1 ;
    COMMIT ;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION sp_insert ;
END CATCH ;


Scenario 4:- (Savepoint in Iterative ) Iterative Processing with Partial Rollbacks.

DO $$
DECLARE
i INT;
BEGIN
    FOR i IN 1 . . 10 LOOP
      INSERT INTO logs (log_message) VALUES ( 'Log ' || i ) ;
      SAVEPOINT sp_log_insert ;
    END LOOP ;
    ROLLBACK TO sp_log_insert ; COMMIT ;
END ;
$$ ;
COMMIT ;

Scenario 5:- (Partial Rollback in Order Processing ) Allow rolling back part of a transaction while keeping earlier changes intact..

BEGIN TRANSACTION ;
    UPDATE Orders SET Status = 'Processing' WHERE OrderID = 5001 ;
    SAVEPOINT BeforePayment ;
    UPDATE Payments SET Status = 'Completed' WHERE PaymentID = 7001 ;

- - If an error occurs
ROLLBACK TO BeforePayment ;
COMMIT ;


Common Errors with SAVEPOINT

Error Explanation Solution
Savepoint not found. Attempting to rollback to an invalid savepoint. Double-check savepoint name.
Transaction already committed. Trying to rollback to a savepoint after commit. Ensure savepoint rollback happens before.
Savepoint not released. Savepoints left without proper rollback or release. Manage savepoints efficiently.


Do's and Don'ts with SAVEPOINT

Do's Don'ts
Use SAVEPOINT for complex transaction handling. Don’t overuse savepoints, leading to confusion.
Label savepoints with meaningful names. Avoid creating multiple savepoints unnecessarily.
