VIEWS

A View is a virtual table in SQL that is based on the result set of a SQL query.


  • It does not store the data itself but displays data dynamically retrieved from the underlying base tables.
  • Views act as a layer of abstraction, providing a simplified, customized, or secured representation of the data.

Key Features

Feature Description
Virtual Table Does not store data; retrieves data from the underlying tables dynamically.
Customizable Output Allows creating tailored representations of data by filtering or joining.
Security Restricts access to specific columns or rows by exposing only selected data.
Reusable Query Logic Encapsulates complex SQL queries, making them reusable and simpler to manage.
Performance Optimization Improves performance by simplifying frequently executed queries.


Advantages of Views

Advantage Explanation
Simplify Complex Queries Encapsulates complicated joins and aggregations, making them easier to use.
Enhance Security Limits user access to sensitive data by exposing only necessary columns or rows.
Increase Productivity Reduces redundancy by reusing query logic, saving time for developers and analysts.
Provide Data Abstraction Offers a high-level, user-friendly representation of the underlying database structure.
Facilitate Migration Acts as an interface to maintain application compatibility during schema changes.
Modifiability Allows updates, deletions, and inserts (if conditions are met).


Syntax

1. Basic Syntax for Creating a View

CREATE VIEW view_name AS
    SELECT column1, column2, . . .
    FROM table_name
    WHERE condition ;


2. Modifying an Existing View (if supported by the database)

Some databases allow altering a view directly; others require dropping and recreating it.

CREATE OR REPLACE VIEW view_name AS
    SELECT column1, column2, . . .
    FROM table_name
    WHERE condition ;

3. Syntax to Drop a View

Deletes the view from the database.

DROP VIEW view_name ;


4. Creating a View with the WITH CHECK OPTION

This ensures data integrity by preventing updates or inserts that violate the view's conditions.

CREATE VIEW view_name AS
    SELECT column1, column2, . . .
    FROM table_name
      WHERE condition
    WITH CHECK OPTION ;

Behavior of Views

Aspect Behavior
Definition A view is a virtual table representing the result of a SQL query. It does not store data physically but dynamically retrieves data from the underlying base tables.
Data Retrieval Data in a view is fetched in real-time from the underlying tables. Any updates to the base tables are reflected in the view.
Dependency Views depend on the schema and data of the underlying tables. Changes in table structure (e.g., column deletion) can break the view.
Data Modifications In general, views allow INSERT, UPDATE, and DELETE operations, but only if the view adheres to certain rules (e.g., no aggregates or joins).
Performance Impact Views simplify complex queries but can introduce performance overhead if poorly optimized or involving large datasets. Indexed or materialized views can improve performance.
Security Views can restrict access by exposing only specific columns or rows, acting as a layer of abstraction for users with limited permissions.
Usage in Queries Views can be queried like a table and used in joins, subqueries, or aggregation to simplify query logic.
Constraints Constraints like WITH CHECK OPTION enforce consistency, ensuring that data modifications respect the view's filtering conditions.
Materialized Views In some databases (e.g., Oracle, PostgreSQL), materialized views store query results physically, improving performance for frequent and complex queries.
Limitations Views cannot include certain SQL clauses (e.g., ORDER BY without TOP in SQL Server). Nested or overly complex views can be hard to manage and maintain.


Types of Views

Type Description
Simple View Based on a single table without complex logic.
Complex View Involves multiple tables, joins, or aggregation functions.
Inline View A subquery in the FROM clause treated as a temporary view for the query's scope.
Materialized View Physically stores data for faster access (supported by Oracle, PostgreSQL, etc.).


Basic Scenarios

Scenario 1:- Create a view that shows customer names and their contact details (phone and email).

CREATE VIEW CustomerContacts_vw AS
    SELECT CustomerID, CustomerName, PhoneNumber, Email
    FROM Customers ;


Scenario 2:- Show active customer data with selected details like customer ID, name, and email.

CREATE VIEW CustomerSummary_vw AS
    SELECT customer_id, name, email
    FROM Customers
      WHERE status = 'Active' ;


Scenario 3:- Restrict access to confidential employee data by exposing only selected columns to authorized users.

CREATE VIEW EmployeeData_vw AS
    SELECT employee_id, name, department_id
    FROM Employees
      WHERE access_level = 'Confidential' ;


Scenario 4:- Create a view to display all products with their names, categories, and prices.

CREATE VIEW ProductPrice_vw AS
    SELECT ProductID, ProductName, Category, Price
    FROM Products ;


Scenario 5:- (With JOINs) Combine product and sales information to show product names, sales dates, and sales amounts.

CREATE VIEW ProductSales_vw AS
    SELECT p.product_name, s.sales_date, s.sales_amount
    FROM Products p
    JOIN Sales s ON p.product_id = s.product_id ;


Complex Scenarios

Scenario 1:- (Employee Performance Analysis) Create a view that displays employee details along with their total sales for the month. Only include employees with sales greater than $10,000 and group the data by department.

CREATE VIEW EmpPerformance_vw AS
    SELECT
      e.EmployeeID, e.Name, d.DepartmentName,
      SUM(s.SaleAmount) AS TotalSales
    FROM
      Employees e
    JOIN
      Departments d ON e.DepartmentID = d.DepartmentID
    JOIN
      Sales s ON e.EmployeeID = s.EmployeeID
    WHERE
      s.SaleDate BETWEEN '2023-12-01' AND '2023-12-31'
    GROUP BY
      e.EmployeeID, e.Name, d.DepartmentName
    HAVING
      SUM(s.SaleAmount) > 10000
    ORDER BY
      d.DepartmentName, TotalSales DESC ;


Scenario 2:- (Product Availability by Region) Create a view that lists products along with the regions where they are available, the total stock in each region, and the stock status (Low, Medium, High).

CREATE VIEW ProductReview_vw AS
    SELECT
      p.ProductID, p.ProductName, r.RegionName,
      SUM( s.StockQuantity ) AS TotalStock,
      CASE
        WHEN SUM( s.StockQuantity ) < 50 THEN 'Low'
        WHEN SUM( s.StockQuantity ) BETWEEN 50 AND 200 THEN 'Medium'
        ELSE 'High'
      END AS StockStatus
    FROM
      Products p
    JOIN
      Stocks s ON p.ProductID = s.ProductID
    JOIN
      Regions r ON s.RegionID = r.RegionID
    GROUP BY
      p.ProductID, p.ProductName, r.RegionName
    ORDER BY
      TotalStock DESC ;


Scenario 3:- (With Sub Queries ) Identify high-value customers by calculating total spending and filtering those who placed more than ten orders.

CREATE VIEW HighProfileCustomers_vw AS
    SELECT
      c.customer_id, c.name,SUM(o.order_amount) AS TotalSpent
      FROM Customers c
    JOIN Orders o ON c.customer_id = o.customer_id
    GROUP BY c.customer_id,c.name
    HAVING
    COUNT (o.order_id) > 10;


Scenario 4:- (With UNION ) Display the hierarchical structure of departments by recursively finding parent-child relationships.

CREATE VIEW DepartmentHierarchy_vw AS
WITH RECURSIVE DeptCTE AS (
    SELECT
      department_id, department_name, parent_department_id
    FROM Departments
      WHERE parent_department_id IS NULL
    UNION ALL
      SELECT
        d.department_id, d.department_name, d.parent_department_id
      FROM Departments d
    INNER JOIN DeptCTE cte ON d.parent_department_id = cte.department_id
    )
SELECT * FROM DeptCTE ;


Scenario 5:- (Active Subscriptions View) Create a view to list active subscriptions along with customer details and their subscription status.

CREATE VIEW ActiveSubscriptions_vw AS
SELECT
    s.SubscriptionID, c.CustomerName, s.StartDate, s.EndDate, CASE
      WHEN s.EndDate >= CURRENT_DATE THEN 'Active'
      ELSE 'Expired'
    END AS SubscriptionStatus
FROM
    Subscriptions s
JOIN Customers c ON s.CustomerID = c.CustomerID
WHERE
    s.StartDate <= CURRENT_DATE;

Common Errors with VIEWS

Error Explanation Solution
Invalid column name A referenced column in the view no longer exists in the base table. Update the view definition or table schema.
Cannot perform INSERT/UPDATE View is not updatable due to joins or derived columns. Use INSTEAD OF triggers if needed.
Recursive View Definition Circular dependency detected when referencing the view itself. Avoid self-referencing in view creation.
WITH CHECK OPTION violation Insert or update operation violates the condition of WITH CHECK OPTION. Ensure the condition aligns with the update.
View already exists Attempting to create a view with an existing name. Drop the view or use CREATE OR REPLACE.

Performance Hints for writing a View

Hint Explanation
Limit Columns and Rows Retrieve only the necessary columns and rows to reduce data load.
Optimize Query Performance Avoid using computationally expensive operations like nested queries or non-indexed columns.
Use Descriptive Names Name views to reflect their purpose or logic for better maintainability.
Leverage Indexes on Base Tables Ensure indexed columns are used to improve performance of queries referencing the view.
Avoid Nested Views Refrain from creating views that depend on other views to avoid performance degradation.
Keep Queries Modular Break down complex logic into smaller, reusable views.
Materialized Views for Large Data Use materialized views for complex, computationally expensive queries to improve performance.

Do’s and Don’ts with VIEWS

Do's Don'ts
Use views to encapsulate frequently used complex queries. Don’t use views as a replacement for stored tables for large datasets.
Create views to enforce data security and access control. Don’t create nested views unnecessarily as they can degrade performance.
Test views after modifying underlying tables or schema. Don’t assume that views improve performance without understanding the query execution plan.
Use materialized views for static, computationally expensive data. Don’t rely on views for heavy transactional operations.
Use WITH SCHEMABINDING to prevent table modifications that could break the view. Don’t rely on views for high-performance-critical operations without testing.
Use WITH CHECK OPTION for data integrity. Don’t use views for direct bulk data manipulation if it impacts base tables heavily.
Document view logic for clarity. Avoid exposing sensitive data via views inadvertently.
